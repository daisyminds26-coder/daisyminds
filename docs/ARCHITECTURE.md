# Daisy Minds LMS — Architecture

**Status:** V1 baseline architecture. Items marked **⚠ Pending Confirmation** are working defaults chosen to unblock design work — see [PROJECT-UNDERSTANDING-REPORT.md](./PROJECT-UNDERSTANDING-REPORT.md) §10 for the open questions driving them. They must be confirmed before the corresponding module is built.

---

## 1. Architectural Style

Daisy Minds LMS is built as a **modular monolith**:

- One Express.js backend process, organized into strictly bounded feature modules (one per domain: Auth, Students, Courses, Batches, etc.).
- One React SPA frontend, organized by feature, consuming the backend over REST.
- Deployed as a single deployable unit per tier (API, frontend) — not microservices.

**Why a modular monolith and not microservices:** the team, infra (single Hostinger VPS), and current scale (10k students / 2k concurrent) do not justify microservices' operational cost (service discovery, distributed tracing, network-call overhead, multiple deploy pipelines). A modular monolith gets the maintainability benefits (clear boundaries, independent testability, low coupling) without that cost, and specific modules (e.g., live classes, notifications) can be extracted into standalone services later **if** they become scaling bottlenecks — the module boundaries defined below are drawn so that extraction is possible without a rewrite.

**Tenancy model — ⚠ Pending Confirmation (see PROJECT-UNDERSTANDING-REPORT.md Q1):** V1 is built **single-tenant** (one organization: Daisy Minds itself). No `organizationId` scoping exists in the data model. If multi-organization support is later confirmed as a requirement, this is a schema-and-authorization migration, not a full rewrite, provided module boundaries below are respected (no cross-module direct DB queries).

## 3. Backend Structure (Express.js)

**Layered at the top level, feature-organized within each layer.** The top-level folders group by technical role (`controllers/`, `services/`, `repositories/`, `models/`, `routes/`, `validators/`); within each of those, files are named or sub-foldered per domain (e.g. `services/students/student.service.ts` or `student.service.ts` — one file per module, never a shared "god" file per layer). This satisfies CLAUDE.md's "Feature-based Architecture" principle at the file-organization grain while keeping a shallow, predictable top-level tree. No module imports another module's repository/model directly; cross-module reads go through the other module's exported service, and cross-module side effects go through domain events (§5), never direct writes to another module's collection.

There is no DI framework (no NestJS, no Inversify). Dependencies are wired **manually via factory composition** — a service is constructed with its repository passed in, a controller with its service — plain constructor/function parameters, no decorators, no reflection metadata. See §13 for the rationale.

```
backend/
├── src/
│   ├── server.ts             # process entry — starts the HTTP server + infra connections, handles graceful shutdown
│   ├── app.ts                  # Express app assembly: middleware chain, route mounting — exported, not started
│   ├── config/                 # env (Zod-validated), database, redis, cloudinary, logger, swagger — all typed
│   ├── controllers/            # thin request handlers — one file per domain once modules exist
│   ├── services/                # business logic — one file per domain
│   ├── repositories/             # Mongoose data access — one file per domain
│   ├── models/                    # Mongoose schemas — one file per domain
│   ├── routes/                     # Express Routers, mounted onto app.ts — one file per domain
│   ├── middlewares/                 # cross-cutting Express middleware (error-handler, not-found, request-id, request-logger, validate, rate-limit)
│   ├── validators/                   # Zod schemas for request validation — one file per domain
│   ├── types/                         # shared TypeScript types/interfaces
│   ├── utils/                          # api-error, api-response, async-handler, and small shared helpers
│   ├── queues/                         # BullMQ connection + queue registration
│   ├── jobs/                            # BullMQ processors
│   └── docs/                             # OpenAPI schema fragments/registrations
├── tests/
│   ├── unit/
│   └── integration/
└── scripts/
```

Per-domain flow (once a module exists, e.g. `students`): `validators/student.validator.ts` (Zod schemas) → `routes/student.routes.ts` (binds `Router`, applies `validate()` + auth middleware per route) → `controllers/student.controller.ts` (thin — reads the already-validated request, calls the service, sends the response via `utils/api-response.ts` — no business logic) → `services/student.service.ts` (business logic) → `repositories/student.repository.ts` (Mongoose queries) → `models/student.model.ts` (Mongoose schema/model). Controllers never touch Mongoose models directly (per CLAUDE.md: "Controllers thin, Business logic in Services").

### 4.1 Frontend architectural decisions (Phase 3)

- **Routing:** React Router v7 in Data Router mode (`createBrowserRouter`), not Framework Mode — no RSC, no server actions, no file-based routing. Every route is lazily loaded via the `lazy` route field (native code-splitting, no manual `React.lazy`/`Suspense` boilerplate per route). Each dashboard area's shell (`DashboardLayout` + `Sidebar`/`Header`/command palette) is itself behind a lazy per-area wrapper (`routes/layouts/*`) so visiting `/login` never downloads the authenticated-shell bundle.
- **Theme:** `ThemeProvider` is real (owns the `<html>` root attribute and mobile browser-chrome color) but currently supports only `'light'` — dark mode is explicitly out of scope for V1 (UI-DESIGN-SYSTEM.md §10) and isn't built speculatively. The `.dark` CSS variables already exist in `index.css`, so enabling it later is additive.
- **Role-aware navigation is UI-only filtering** (`shared/lib/nav.ts#filterNavByRole`): it hides nav items a role shouldn't see, but is never the authorization boundary, consistent with SECURITY.md §3.
- **Every nav destination has a route today.** Modules not yet built (Students, Courses, Batches, …) resolve to a shared `ComingSoonPage` rather than a 404, so the full navigation/route tree can be verified end-to-end before each module lands.

### 4.2 Frontend authentication architecture (Phase 4)

Connects the Phase 3 UI/route foundation to the real backend (`backend/src/routes/auth.routes.ts`) — every fact below was confirmed by reading that implementation directly, not assumed.

- **State split — deliberate, not accidental duplication:** `shared/lib/auth-session-store.ts` (Zustand) holds only `{status, accessToken}`. It lives in `shared/lib`, not `features/auth/stores`, because `shared/lib/api-client.ts`'s refresh interceptor needs synchronous, non-React access to the current token (`useAuthSessionStore.getState()`) and `shared/` must never import from `features/*`. `features/auth/stores/auth-store.ts` re-exports the same store so feature/component code still reaches it through the feature's own barrel. The user *profile* (email, role, permissions, status) lives exclusively in TanStack Query's `['auth','me']` cache — never copied into Zustand — because `GET /auth/login`'s response body doesn't include `permissions` (only `GET /auth/me` does), so the profile query is the only correct single source of truth for it.
- **Token storage:** access token in memory only, never `localStorage`/`sessionStorage`/logs. Refresh token is the backend's httpOnly/Secure(prod)/SameSite=Strict cookie (`refresh_token`, path-scoped to `/api/v1/auth`) — the frontend never reads or constructs it. Verification/reset tokens are read once from the URL (`useSearchParams`), held only in local component state, and stripped from browser history via `setSearchParams({}, {replace:true})` immediately after being captured.
- **Bootstrap:** `features/auth/hooks/use-auth-bootstrap.ts` calls `POST /auth/refresh` exactly once on app mount. Success sets `status:'authenticated'` + the access token; any failure (no cookie, expired, revoked — all indistinguishable 401s by backend design) sets `status:'unauthenticated'`. `RequireAuth`/`RequireGuest` both render `PageLoader` while `status==='loading'`, so a valid session is never flashed to `/login` and an invalid one never flashes protected content.
- **Refresh queue** (`shared/lib/api-client.ts`): a single module-level `refreshPromise` — the first `401` (on any endpoint except the public auth endpoints themselves, and never while a logout call is in flight) creates it and every concurrent `401` awaits the same promise, so N simultaneous expired-token requests trigger exactly one `POST /auth/refresh`. Each original request is retried at most once (`config._retry`). A refresh failure resets the auth store and broadcasts `SESSION_INVALIDATED`; the redirect to `/login` is never imperative from inside the client — it falls out naturally from `RequireAuth` re-rendering on the state change. `403` responses are passed straight through and never attempt a refresh.
- **Route guards** (`shared/guards/`) are UI-only (SECURITY.md §3 — never the security boundary): `RequireAuth` (redirects unauthenticated → `/login`, preserving `location.state.from`), `RequireGuest` (redirects an authenticated user away from `/login` etc. to their role dashboard), `RequireRole`/`RequirePermission` (read from `useCurrentUser()`, redirect to `/unauthorized` on mismatch). The backend's `requireAuth`/`requireRole`/`requirePermission` middleware remains authoritative in every case.
- **Post-login redirect / open-redirect guard** (`features/auth/utils/redirect.ts#resolvePostLoginPath`): returns the user to `location.state.from.pathname` only if it starts with `/` (not `//…`) *and* falls within their own role's area prefix (`/admin`, `/trainer`, `/student`); anything else — including a different role's area — falls back to that role's dashboard root.
- **Multi-tab sync** (`shared/lib/multi-tab-sync.ts`): `BroadcastChannel('daisy-minds-auth-sync')`, falling back to a `storage` event on browsers without it. Broadcasts only an event name (`LOGOUT`/`LOGOUT_ALL`/`SESSION_INVALIDATED`) plus an originating-tab id used to suppress self-delivery — never the access token. `features/auth/hooks/use-auth-tab-sync.ts` applies another tab's event locally (reset store + clear query cache) without re-broadcasting or calling any `/auth/*` endpoint.
- **Backend contract gaps found and resolved:** the `LOCKED` login response originally returned the same `401 UNAUTHORIZED` code as a wrong password (only the message text differed), which API-STANDARDS.md's own rule (branch on `code`, never `message`) made unusable. Fixed with a small, additive backend change — `ApiError.locked()` — giving `LOCKED` a distinct `ACCOUNT_LOCKED` code plus a `details.lockedUntil` timestamp (see API-STANDARDS.md §3, SECURITY.md §2). `DEACTIVATED` remains deliberately indistinguishable from a wrong password (SECURITY.md §5's anti-enumeration design) — the frontend does not attempt to show a dedicated "account deactivated" screen, since doing so would itself be the enumeration leak the backend is protecting against.

## 5. Cross-Cutting Communication: Domain Events

Modules that need to react to another module's actions (e.g., Notifications reacting to "enrollment created", Audit Logs reacting to "user role changed", Analytics reacting to "quiz submitted") subscribe to **internal domain events** published via a single shared instance of Node's built-in `events.EventEmitter` (added under `src/utils/` when the first cross-module listener is actually needed — not pre-scaffolded during initialization), not by calling into each other's services directly.

Example event flow (descriptive, not code): `EnrollmentsService` completes an enrollment → emits `enrollment.created` → `NotificationsModule` and `AuditLogModule` each have a listener that reacts independently. This keeps Notifications and Audit Logs — the two most cross-cutting modules — decoupled from every producer module, directly addressing the coupling risk raised in the understanding report.

For actions that must survive a process restart or need retry/backoff (sending an email, generating a certificate PDF, processing a payment webhook), the event listener enqueues a **BullMQ job** rather than doing the work inline.

## 6. Background Jobs (BullMQ + Redis)

Queue definitions and the BullMQ connection live in `src/queues/`; the processors that consume them (`Worker` instances) live in `src/jobs/` — kept separate so a queue can be enqueued-to from anywhere without pulling in worker/processing code, and so processors can be run in a separate process later if a queue becomes a scaling bottleneck. The BullMQ Redis connection is dedicated (`maxRetriesPerRequest: null`, per BullMQ's own requirement) and never shared with the general-purpose caching Redis client in `config/redis.ts`.

| Queue | Producers | Purpose |
|---|---|---|
| `notifications` | Enrollment, Fees, Attendance, Assignments, Live Classes | Async email/SMS/push delivery, with retry |
| `certificates` | Results, Certificates | PDF generation + Cloudinary upload on course completion |
| `reports` | Reports, Analytics | Long-running aggregation/export jobs, avoids blocking request threads |
| `payments-reconciliation` | Payments | Webhook processing, retry on gateway callback failures |
| `media-processing` | Learning Player | React to Cloudinary transcoding webhooks, update lesson readiness state |

Jobs are idempotent (safe to retry) and use a dead-letter/failed-job inspection process — no job silently drops on failure.

## 7. Caching (Redis)

Redis is used for two distinct purposes and these are **not** the same Redis logical database in production: BullMQ queues, and application cache (course catalog listings, published curriculum trees, dashboard aggregate counts). Cache entries are keyed by resource + version/updatedAt and invalidated on the relevant domain event (e.g., `course.updated` invalidates `course:{id}` and any list caches containing it) — not by TTL alone, to avoid serving stale data after edits.

## 8. Media & File Storage (Cloudinary)

- All uploads (video lessons, images, assignment submissions, certificates) go through **signed, short-lived upload credentials** issued by the backend — the frontend never holds a Cloudinary API secret.
- Video access for enrolled content uses **signed, time-limited delivery URLs**, not public URLs — see [SECURITY.md](./SECURITY.md) §6.
- Cloudinary's transcoding webhooks feed the `media-processing` queue so lesson "ready" state reflects actual transcode completion, not just upload completion.
- **First implementation — student profile photos (Phase 6):** `cloudinary-upload.service.ts` (`generateSignedUploadParams`/`verifyUploadedAsset`/`deleteAsset`) is the reference implementation of the pattern described above — see §15 for the full request flow. General video/transcoding-webhook support remains unbuilt; this is upload-only (no transformations/webhooks yet).

## 9. Live Classes — Session Scheduling **Implemented (Phase 12)**; Managed Video-Conferencing Vendor ⚠ Pending Confirmation

Phase 12 implements the full session-scheduling, join, and attendance workflow (§27) — but still no WebRTC/SFU technology is named in the tech stack (CLAUDE.md/PRD), and a general-purpose Node.js API process remains an inappropriate media server. The `live-meeting-provider.service.ts` adapter interface (`LiveMeetingProvider`) is built and used everywhere a meeting link is created/cancelled, but only `ManualLinkProvider` (an admin-pasted HTTPS URL) is a real implementation — `GOOGLE_MEET`/`ZOOM`/`MICROSOFT_TEAMS` are schema-forward-compatible enum values only, resolved to the same manual-link behavior today. **Recommendation unchanged:** integrate a managed video-conferencing SDK (e.g., 100ms, Agora, or Twilio Video) as a new adapter implementation when a vendor is chosen — a service-layer change, not a migration, since the adapter boundary and provider enum already exist. This remains a build-vs-buy decision needing stakeholder sign-off before real provider credentials are wired in.

## 10. Payments — ⚠ Pending Confirmation

No payment gateway is named. **Recommendation:** Razorpay (strong UPI/netbanking support for the India market, hosted checkout keeps the platform out of PCI-DSS card-data scope). Integrated behind a `PaymentGatewayAdapter` interface in the `payments` module for the same reason as above.

## 11. Notifications — Multi-Channel

The `notifications` module is a thin dispatcher over channel adapters (`EmailAdapter`, `SmsAdapter`, `PushAdapter`, `InAppAdapter`). Vendor for email/SMS is **⚠ Pending Confirmation** (recommendation: a transactional email provider such as Resend/SES, and an India-focused SMS provider such as MSG91). Because dispatch is event-driven (§5) and queued (§6), the module can be built and stubbed with a `LogAdapter` before a vendor is chosen, without blocking dependent modules.

## 12. Scalability Path

| Stage | Approach |
|---|---|
| V1 launch | Single Hostinger VPS, PM2 in **cluster mode** (one worker per CPU core) behind Nginx — gives multi-process concurrency on one box without infra changes |
| Growth | Horizontal scale: additional VPS instances behind Nginx/Cloudflare load balancing; MongoDB Atlas tier upgrade + read replicas for Reports/Analytics (§ DATABASE.md) |
| Live Classes at scale | Delegated entirely to the managed provider (§9) — this is precisely why building it in-house is not recommended; conferencing concurrency must not depend on the API VPS's capacity |

Capacity planning against the PRD's stated NFRs (10,000+ students, 2,000+ concurrent, 99.9% uptime) requires load testing before Production Deployment (Phase 20) — no load-testing step currently exists in the roadmap; see ROADMAP.md Phase 19.

## 13. Architecture Decision Records (Summary)

| Decision | Choice | Rationale |
|---|---|---|
| Backend architecture style | Modular monolith | Matches team/infra scale; avoids premature microservices cost |
| Backend framework | Express.js, no DI container | Minimal, unopinionated, smallest dependency surface; layered module structure (router → controller → service → repository) delivers the same separation of concerns NestJS would enforce, via convention instead of a framework |
| Dependency wiring | Manual composition where each domain's route file is wired up (repository → service → controller) | No reflection/decorator-based DI needed at this scale; keeps wiring explicit and easy to trace, at the cost of writing it by hand instead of a container doing it |
| Request validation | Zod schemas + a shared `validate()` middleware | Same validation library as the frontend (one mental model across the stack); Zod schemas double as the OpenAPI source via `zod-to-openapi` (API-STANDARDS.md §10) |
| Module communication | Direct service calls (sync reads) + domain events (async side effects) | Prevents tight coupling, especially for Notifications/Audit/Analytics |
| Tenancy | Single-tenant V1 | Matches PRD's "Multi-Tenant White Label" exclusion; ⚠ pending explicit confirmation |
| Background processing | BullMQ on Redis | Already in stack; natural fit for retryable async work |
| Live classes | Managed SDK via adapter interface | Building WebRTC/SFU in-house is out of scope for this team/infra |
| Payments | Gateway-hosted checkout via adapter interface | Avoids PCI-DSS card-data scope |
| Caching invalidation | Event-driven, not TTL-only | Avoids serving stale data after writes |
| Student soft-delete | Deletes the linked `user`, never the `students` profile document | Preserves academic-history integrity for future enrollment/attendance/grade records referencing `Student._id` (DATABASE.md §3.2) |
| Student ID generation | Atomic `counters` collection (`$inc` via `findOneAndUpdate`), one global sequence never reset per year | Concurrency-safe by construction; avoids the year-boundary edge case a per-year-reset counter would introduce |
| Student list/export query | Single `$lookup`+`$facet` aggregation across `students`+`users` | Filtering/search genuinely spans both collections (auth/profile split is deliberate, DATABASE.md §1); avoids N+1 or an in-memory join |
| Government ID (Aadhaar) storage | Not implemented this phase | Flagged as a high-risk business/legal decision (consent, encryption, retention) pending confirmation, not an engineering default |
| Academic-document upload | Metadata-ready schema fields only (`documentUrl`/`documentPublicId`, always `null`); no upload endpoint | Explicitly deferred per task scope; profile-photo upload is the reference implementation to extend from later |
| Trainer ID generation | Same atomic `counters` collection as students, new `_id: 'trainer'` sequence, format `DM-TRN-{year}-{6-digit}` | Reuses a proven concurrency-safe primitive instead of a parallel implementation |
| Trainer lifecycle/sessions/audit | Calls `userRepository`/`userSessionRepository`/`auditLogRepository` directly, same as students | A trainer **is** a `users` document (`role: TRAINER`) plus a profile satellite — no parallel auth system, no duplicated guard logic |
| Trainer weekly availability | Structured recurring day/time-range slots (`dayOfWeek`+`startTime`+`endTime`+`timeZone`+`type`), not a live calendar | Phase 7 scope explicitly excludes live-class scheduling; a recurring-slot model is the right shape for "when is this trainer generally available" without building a calendar engine |
| IANA timezone validation | `Intl.DateTimeFormat(undefined, {timeZone: value})` construction (try/catch), not `Intl.supportedValuesOf('timeZone').includes(value)` | The latter's canonical list contains legacy ICU aliases (e.g. `Asia/Calcutta`) instead of modern preferred names (e.g. `Asia/Kolkata`), false-negative-rejecting a standard, commonly-used identifier |
| Trainer salary/compensation | No field added to the schema at all | Explicit Phase 7 scope exclusion — payroll is a distinct future module, not a flag on the profile |
| Dashboard metrics query strategy | Direct `Promise.all`-parallelized aggregations against `users`/`students`/`trainers`/`audit_logs` in a dedicated `dashboard.repository.ts` — no new collection | The dashboard has no state of its own; introducing a persisted "dashboard stats" collection would just be a second, driftable source of truth for numbers the source collections already hold |
| Dashboard caching | A thin, best-effort Redis wrapper (`dashboard-cache.service.ts`) that no-ops on any Redis error or disconnection | No cache-service abstraction existed yet (Redis was previously only used for the health check); a best-effort cache needs no test mock and never makes the dashboard *less* available than an uncached one |
| Dashboard visualizations | Custom accessible bar-lists (`DistributionCard`), not a charting library | No chart library was installed; 2-5-bucket distributions don't justify one, and a bar-list guarantees every value is visible as text, not just color/length |
| Dashboard "recent activity" audit access | `recentActivity` is `null` for `ADMIN`, populated for `SUPER_ADMIN` — one endpoint, permission-aware response shaping | Mirrors the students/trainers modules' `requireRole('SUPER_ADMIN')` carve-out for sessions/audit; avoids a second `dashboard.admin.audit.read` permission with no other consumer |
| Course ID generation | Same atomic `counters` collection as students/trainers, new `_id: 'course'` sequence, format `DM-CRS-{year}-{6-digit}` | Reuses the proven concurrency-safe primitive a third time instead of inventing a new one |
| Course collection shape | A single self-contained `courses` collection — no `users` join | Unlike students/trainers, a course is not a person/account; it needs no auth-satellite split, so `course.repository.ts#list` is a plain `find().sort().skip().limit()`, not a `$lookup`+`$facet` aggregation |
| Course category | A plain validated string field on `courses`, not a `categories` collection/module | The task explicitly forbade overengineering a full Category Management module for this phase; a dedicated category CRUD module is deferred until a real second consumer (e.g. public catalog browsing) needs it |
| Course "restore" semantics | One action, two behaviors depending on state: un-deletes if soft-deleted, otherwise moves `ARCHIVED` → `DRAFT` (never straight back to `PUBLISHED`) | Soft-delete (`isDeleted`) and lifecycle `status` are orthogonal — a single `restore` verb matches the UI's single "Restore" action, and re-publishing a restored-from-archive course is a distinct, explicit human decision, not an automatic side effect |
| Course publication readiness | One `checkReadiness()` function is the sole source of truth, called by both `POST /courses/:id/readiness-check` and the `publish` action's own validation | Prevents the two surfaces (a live preview panel and the actual publish gate) from silently drifting apart into two different definitions of "ready" |
| Course pricing cross-field validation | Enforced only on the backend (Zod `superRefine` in `course.validator.ts`); removed from the frontend schema | A `.superRefine()` nested in a `zodResolver` schema with many `.default()`-bearing sibling fields interacted badly with RHF's generic type inference (see below); backend validation is the actual trust boundary regardless ("never trust frontend input") |
| Course trainer eligibility | Metadata only — a list of trainer IDs a course is eligible to be taught by, validated to exist/be active/non-deleted | Explicit Phase 9A scope boundary: no batch relationship, no schedule, no real assignment — that belongs to the future Batch Management module |
| Curriculum hierarchy | Course → Modules → Lessons, no SECTION layer | Matches the PRD and the existing Phase 1 `course_modules`/`lessons` scaffold; avoids inventing unnecessary hierarchy per the phase's own explicit guidance |
| Curriculum ordering | Server-controlled contiguous 0-based integers, re-derived from the *relative* ranking a reorder payload submits, never the client's literal values | Simple, robust at the stated scale (10-30 modules, 100-500 lessons); a reorder payload must name every current sibling exactly once, removing partial-reorder ambiguity entirely |
| Curriculum multi-document writes | Real MongoDB transactions (`utils/transaction.ts`), the first in this codebase | Reorder/move/duplicate/cascading-delete all touch multiple documents and need to be all-or-nothing; Atlas is always a replica set in production, so this costs nothing there — a second, dedicated `MongoMemoryReplSet` test helper was added so only curriculum tests pay the slower local startup cost |
| Module deletion cascade | Soft-deletes the module and its then-active lessons together, tombstoning the cascaded lessons (`deletedWithModule: true`) | Restoring the module must restore only the lessons it deleted, never a lesson that was already independently deleted beforehand — a plain boolean flag is simpler than inventing a generalized tombstone/versioning system for one narrow case |
| Curriculum readiness vs. course readiness | Two separate concepts, never merged: Phase 9A's course (metadata) readiness is unchanged; a new curriculum (structural) readiness is added | Publishing curriculum items must not silently change course publication status, and an existing published course with no curriculum yet must remain exactly as valid as it was before this phase shipped |
| Curriculum permissions | Reuses the existing `courses:read`/`courses:manage`/`courses:publish` catalog — no new `curriculum:*` permissions | The task's own guidance preferred fewer permissions absent a real business need for finer granularity; also avoided any `seed-roles.ts`/live-database re-seed for this phase |
| Curriculum drag-and-drop | `@dnd-kit` (first drag-drop dependency in this codebase); cross-module lesson movement is a keyboard-accessible "Move to module…" dialog, not a shared multi-container drop target | Actively maintained, built-in keyboard sensor, tree-shakeable; the task's "drag/drop must not be the only way to reorder" requirement made an explicit always-available action the more defensible primary path for cross-module movement specifically |
| Curriculum optimistic UI | None — every mutation invalidates and refetches on success, never patches the cache speculatively | Reorder/move/duplicate/cascading-delete are too structurally varied to safely optimistic-patch for a first version; the practical benefit is that a failed mutation has nothing to roll back, since nothing was ever speculatively changed |

## 14. Admin User Management Module (Phase 5) — **Implemented**

The first business-facing module built on top of the Phase 2 auth foundation. Manages **system users only** (the `users` collection's auth-identity records) — Student Profile Management and Trainer Academic Management are separate future modules operating on the `students`/`trainers` satellite collections (DATABASE.md §3.1/§3.2), not this one.

**Backend** (`src/{validators,repositories,services,controllers,routes,docs}/user.*`, plus a small `role.*` set):
- `user-management.service.ts` owns every business rule — controllers stay thin, matching CODING-STANDARDS.md §2.
- **Security guards, enforced in the service layer (not just route middleware), on every state-changing action:**
  - *Self-protection:* no actor can deactivate or soft-delete their own account (`assertNotSelf`).
  - *Cross-role protection:* an `ADMIN` cannot act on a `SUPER_ADMIN` account at all — deactivate, delete, or role-change (`assertCanActOnTarget`) — nor grant the `SUPER_ADMIN` role to anyone (`assertRoleGrantAllowed`), closing the privilege-escalation path.
  - *Last-SUPER_ADMIN protection:* deactivating, deleting, or demoting a `SUPER_ADMIN` is blocked if it would leave zero `ACTIVE` `SUPER_ADMIN` accounts, counted fresh per request (not from the token) specifically so a stale-but-still-valid access token (≤15 min window, SECURITY.md §1) can't be used to push the count to zero after the actor's own account was independently deactivated.
  - **Bulk actions run the exact same single-item guarded functions in a loop** — a blocked item is reported in `failed: [{id, reason}]`, never silently skipped or allowed to abort the rest of the batch.
- **Read access is deliberately split into two tiers**, following DATABASE.md §3.1's existing documented design rather than inventing a new one: general list/detail/create/update/status/role/reset-password/resend-verification/bulk/export require `users:manage`/`users:read` (both `ADMIN` and `SUPER_ADMIN` hold these); **viewing or force-revoking another user's sessions, and reading their audit timeline, are gated `requireRole('SUPER_ADMIN')` specifically** — stricter than the general permission, matching "`SUPER_ADMIN` can revoke any session" / "read access is `SUPER_ADMIN`-only" as already written in DATABASE.md before this module existed.
- **"Assign Permissions" is deliberately *not* a per-user mutation.** The existing RBAC design is role-based, not per-user overrides (DATABASE.md §3.1: permissions live on `roles`, referenced by key, not on `users`). Adding a per-user override field would be exactly the kind of unrequested schema expansion CLAUDE.md's "never create unnecessary collections/fields" warns against, and editing a role's shared permission set from a single-user screen risks an admin silently reconfiguring every other user with that role. What's built instead: "Assign Role" (mutates `users.roleId`, fully guarded as above) and a read-only "effective permissions" view in the user detail drawer (derived from the role, via the new `GET /roles` endpoint).
- **`GET /roles`** (`role.controller.ts`/`role.routes.ts`) is a small, deliberate addition beyond the original plan: read-only `{id, name}` list, `users:manage`-gated, that exists solely so the frontend can populate a role picker with valid `roleId`s — no role/permission-set CRUD is exposed.
- **CSV export** (`GET /users/export`) is hand-rolled (`utils/csv.ts`, ~15 lines) rather than a new dependency — small, fixed column set, not worth the supply-chain surface of a CSV library.
- **Audit entries are mapped to an explicit DTO** (`AuditLogEntryDto`) before leaving the service — raw Mongoose documents are never sent to the client, matching every other endpoint's convention (`AdminUserDto`, `PublicUser`, `SessionSummary`, …).

**Frontend** (`src/features/users/`, `src/pages/admin/UsersPage.tsx`): mirrors `features/auth/`'s established shape (`api/`, `hooks/`, `schemas/`, `components/`, `types/`) — one `users.api.ts` is the only file that calls `/users`/`/roles`; every mutation invalidates the `['users','list']` prefix so filtered/paginated views stay consistent without manual cache surgery. `shared/lib/api-client.ts` gained `apiPatch`/`apiGetPaginated` and its response interceptor was corrected to stop discarding the pagination `meta` object (a latent bug from Phase 4, where no endpoint had needed `meta` yet) — see SECURITY.md and this file's git history for the full before/after.

**Pre-existing gap fixed while building this module:** `/admin`, `/trainer`, `/student` had `RequireAuth` but no role gate at all — any authenticated user, including a `STUDENT`, could reach `/admin` in the UI. `app/router.tsx` now wraps each area in `RequireRole` (`admin`: `SUPER_ADMIN`/`ADMIN`, `trainer`: `TRAINER`, `student`: `STUDENT`), consistent with SECURITY.md §3's reminder that this is still only a UX convenience, not the real boundary — the backend's per-route guards above are what actually enforce it.

**Data-hygiene issue found and fixed:** the live `users` collection carried a stale `username_1` unique index from before this module — no field named `username` exists anywhere in the current `IUser` schema, so every document had `username: undefined`, and MongoDB's unique index treated the second such document as a duplicate `null`, blocking all user creation beyond the first. Dropped directly (`db.users.dropIndex('username_1')`) after confirming no schema, code, or historical migration references it.

## 15. Admin Student Management Module (Phase 6) — **Implemented**

Builds on the `students` satellite-collection scaffold from Phase 1 (DATABASE.md §3.2) and reuses the Admin User Management module's auth-identity machinery directly — a student **is** a `users` document (`role: STUDENT`) plus a `students` profile document, not a parallel account system. This phase covers identity/contact/academic profile management only — enrollment, attendance, grading, fees, and certificates remain future modules that will reference `Student._id`, not touch this module's code.

**Reuse over duplication (the module's central design constraint):** activate/deactivate/soft-delete/restore/resend-invitation/sessions/audit for a student call directly into `userRepository`/`userSessionRepository`/`auditLogRepository` — the exact same repositories Admin User Management uses — rather than re-implementing lifecycle logic against the `students` collection. `student-management.service.ts` has no self-protection/last-SUPER_ADMIN/privilege-escalation guards of its own because a student can never hold `SUPER_ADMIN`; those guards are meaningless here and were deliberately not copied over.

**Soft-delete is split across two collections on purpose, matching DATABASE.md §3.2's pre-existing note:** "Delete student" soft-deletes the linked **user** (auth identity, sessions revoked) — the `students` profile document's own `isDeleted` is never touched. This preserves academic-history integrity: a future enrollment/attendance/grade record referencing `Student._id` never dangles or gets silently hidden by a naive `isDeleted` filter on the wrong collection. Consequently, the admin list/export's "excludes deleted by default" filter checks the **joined user's** `isDeleted`, not the student document's — see `student.repository.ts`'s `buildPostLookupMatch`.

**Student ID generation (`DM-STU-{year}-{6-digit sequence}`):** a new `counters` collection (`counter.model.ts`) holds one document per named sequence; `student-id.service.ts#generateStudentId` claims the next number via `findOneAndUpdate({_id:'student'}, {$inc:{seq:1}}, {upsert:true, new:true})` — a single atomic MongoDB operation, safe under concurrent creation (verified by a concurrency test creating 5 students in parallel and asserting unique IDs). The sequence is deliberately **one global counter, never reset per calendar year** — a per-year-reset counter would need a new counter document at every year boundary and a decision about an in-flight request straddling that boundary; a single global counter has no such edge case and stays unique forever, at the minor cost of the numeric suffix not restarting at `000001` each January. `studentId` is generated server-side only and is immutable post-creation (no update endpoint accepts it — enforced by `student.validator.ts`'s schemas never declaring the field, not by a runtime check).

**List/export as a single aggregation, not two queries stitched together in application code:** `firstName`/`admissionDate`/`tags`/etc. live on `students`; `email`/account `status` live on `users`. `student.repository.ts#list` runs one `$lookup`-then-`$facet` aggregation pipeline (student-side `$match` before the join, user-side `$match` — including the free-text `search`, which spans both `studentId`/name/phone on the student side and `email` on the user side — after it, then `$facet` for `data`+`totalCount` in one round trip) rather than issuing a paginated `students` query and a second `users` lookup per row (N+1) or an in-memory join. This is the one place in the codebase using `$lookup`/`$facet` — justified because student-list filtering genuinely spans both collections by design (DATABASE.md's auth/profile split), unlike every other list endpoint in the app so far.

**Profile completion is a deterministic, server-only calculation** (`calculateProfileCompletion` in `student-management.service.ts`) — five equally-weighted 20% groups (basic identity, contact+address, emergency contact, academic background, profile photo), recomputed after every create/update/photo change, never accepted as client input (absent from every Zod schema). `100%` → `COMPLETE`, `0%` → `INCOMPLETE`, anything between → `PARTIAL`.

**Account creation has no multi-document transaction** — `mongodb-memory-server` (the only Mongo target this codebase's automated tests run against, and the only one this module was verified against — see §16 below) runs standalone, not as a replica set, so Mongoose transactions aren't available in the test environment this phase was built and verified in. Instead, `createStudent` creates the `users` document first, then the `students` document; if the latter throws, the just-created user is hard-deleted as compensation (safe, because no client has seen it yet — no session issued, no email sent). A "duplicate email" 409 is checked *before* either write, so this compensating path is only reached by a genuine, otherwise-unreachable failure (verified by an integration test asserting no orphaned user survives a duplicate-email attempt).

**Government-ID storage (Aadhaar) was explicitly NOT implemented.** The Phase 6 task flagged this as a high-risk, business/legal decision (consent, encryption-at-rest, masking, retention, restricted access) that CLAUDE.md/SECURITY.md §7 doesn't yet authorize (SECURITY.md §7's DPDP-Act applicability is itself still `⚠ Pending Confirmation`). The pre-existing `kycDocuments` field (Phase 1 scaffold, generic `{type, url, verifiedAt}`) is left untouched and unpopulated by this module's UI/API — a future phase should not populate it without first resolving that policy question.

**Academic-document upload (transcripts, certificates attached to an `educationRecords` entry) was deferred to a metadata-ready foundation, not a working upload flow** — `documentUrl`/`documentPublicId` exist on `IEducationRecord` and are always written as `null` by this phase's create/update paths. Only the **profile photo** upload is fully wired end-to-end (see below); building the equivalent flow for documents later should reuse `cloudinary-upload.service.ts` as-is (add a `resource_type: 'raw'`/`'auto'` variant for non-image files), not a new pattern.

**Profile-photo upload — the first real Cloudinary signed-upload implementation in the codebase** (§8 above only described the intended pattern until now):
1. `POST /students/{id}/photo/signature` (backend) returns a Cloudinary signature scoped to a server-chosen `folder` (`daisy-minds/students/{id}`) and `publicId`, generated via `cloudinary.utils.api_sign_request` — the API secret never leaves the server.
2. The frontend (`use-student-photo.ts`) uploads the file bytes **directly to Cloudinary** from the browser using that signature — the backend never proxies image bytes.
3. `PATCH /students/{id}/photo` (backend) does **not** trust the client's report that the upload succeeded — `cloudinary-upload.service.ts#verifyUploadedAsset` independently calls the Cloudinary Admin API (`cloudinary.api.resource`) to confirm the asset exists, is an image, and landed in the exact expected folder, before persisting the URL. A previous photo's asset is deleted (`cloudinary.uploader.destroy`) only after the new one is confirmed and saved.
4. Allowed formats (`jpg`/`jpeg`/`png`/`webp`) and a 5MB size cap are enforced both in the signature (Cloudinary rejects a mismatched upload) and client-side (fast feedback before the network round trip).

**Permissions** extend the catalog additively (`students:read`, `students:manage`, `students:export` — a separate grant from `read` per the phase's own spec, mirroring nothing else in the app but justified by an explicit requirement) rather than reusing `users:*` — a `TRAINER` or future non-admin role should be grantable read-only student access later without also exposing user-account management.

**Frontend** (`src/features/students/`, `src/pages/admin/StudentsPage.tsx`): mirrors `features/users/`'s shape exactly. The create flow is a `Stepper`-driven multi-section wizard (`StudentCreateWizard.tsx`) sharing one `useForm` instance across all steps (fields stay populated navigating back and forth — no per-step form remount); edit is a single scrollable form (`StudentEditForm.tsx`) reusing the same section layout without the stepper chrome, since editing doesn't need onboarding-style pacing. Array sections (emergency contacts, education records) use `useFieldArray`; the recurring `emergencyContacts.{index}.field`/`educationRecords.{index}.field` RHF field-path is built via a small typed helper (`emergencyContactField`/`educationRecordField`) rather than an inline template literal, reconciling `@typescript-eslint/restrict-template-expressions` (project-wide, disallows bare `number` in a template) with RHF's `FieldPath<T>` type (which requires exactly that numeric segment) — the interpolation happens once, in one justified, commented `eslint-disable` line per helper, instead of at every call site.

**A frontend/backend form-schema mismatch worth documenting for future forms:** the frontend Zod schemas for `dateOfBirth`/`admissionDate` use plain `z.date()`, and `yearOfCompletion` is kept a validated **string** end-to-end (converted to a number only in the payload-building step right before the API call) — **not** `z.coerce.date()`/`z.coerce.number()`, even though the backend's own validators do coerce. Coercion makes Zod's inferred *input* type (what actually lands in RHF state from an HTML input) diverge from its *output* type, which breaks `useForm<T>()`'s single-generic-parameter `Control<T>` inference that every shared `*Field` component (`TextField`, `SelectField`, …) in this app is typed against. This is the first form in the app complex enough to hit that interaction; any future date/number field in a form should follow the same pattern (native value type in the schema, conversion at submit time) rather than reaching for `z.coerce`.

## 17. Admin Trainer Management Module (Phase 7) — **Implemented**

Structurally the trainer counterpart to §15 — a trainer **is** a `users` document (`role: TRAINER`) plus a `trainers` profile satellite (DATABASE.md §3.2), not a parallel account system. Scope is identity/contact/professional-profile/employment/availability management only: course assignment, batch assignment, live-class scheduling, attendance, assignment evaluation, examinations, payroll, trainer-dashboard analytics, and trainer self-service editing are all explicitly out of scope and untouched.

**Reuse over duplication, same discipline as §15:** activate/deactivate/soft-delete/restore/resend-invitation/sessions/audit/bulk-action all call the same `userRepository`/`userSessionRepository`/`auditLogRepository` the Admin User Management and Admin Student Management modules use — no parallel lifecycle implementation. `trainer-management.service.ts` has no self-protection/last-SUPER_ADMIN guards, for the same reason as students: a trainer can never hold `SUPER_ADMIN`.

**Trainer ID generation (`DM-TRN-{year}-{6-digit sequence}`)** reuses the exact `counters` collection primitive `student-id.service.ts` established (`trainer-id.service.ts#generateTrainerId`, new `_id: 'trainer'` counter document, same atomic `findOneAndUpdate({$inc})`), not a new pattern.

**List/export is the same `$lookup`+`$facet` aggregation shape as students** (`trainer.repository.ts`) — profile fields live on `trainers`, `email`/account `status` live on `users`, and filtering/search spans both, so one aggregation pipeline replaces what would otherwise be an N+1 or in-memory join.

**Profile completion** (`calculateProfileCompletion` in `trainer-management.service.ts`) is a deterministic, server-only calculation across 7 equally-weighted groups (basic identity, contact, professional info, qualifications, employment, teaching/availability, profile photo) — never accepted as client input.

**A real, previously-undetected data-leak bug in the students module was found and fixed as a side effect of this phase's manual verification, and proactively avoided here from the start:** Mongoose embedded-array subdocuments spread with `{...item}` leak internal bookkeeping properties (`$__`, `_doc`, `$isNew`, `__parentArray`, `__index`, `$__parent`) into API responses — `{...subdocument}` does not produce a clean plain object. `student-management.service.ts` was retroactively fixed with explicit field-by-field DTO mapping functions and a regression test; `trainer-management.service.ts`'s equivalent mappers (`toEmergencyContactDto`, `toQualificationDto`, `toCertificationDto`, `toAvailabilitySlotDto`) were written with explicit mapping from day one.

**Weekly availability is a structured recurring-slot editor, deliberately not a calendar UI** (`AvailabilityEditor.tsx`, generic over any form whose values include an `availability` array, shared by both the create wizard and edit form): each row is one `dayOfWeek`+`startTime`+`endTime`+`timeZone`+`type` (`AVAILABLE`/`PREFERRED`/`BLOCKED`) slot. Overlap validation (same day + same type + overlapping time range) runs as a Zod `superRefine` (`rejectOverlappingAvailability`), identically implemented on both backend (`trainer.validator.ts`) and frontend (`trainer.schemas.ts`), attaching its error to the later slot's `startTime` field.

**IANA timezone validation bug found and fixed during this phase:** `Intl.supportedValuesOf('timeZone').includes('Asia/Kolkata')` returns `false` — ICU's canonical list contains the legacy alias `Asia/Calcutta` instead of the modern preferred name, so a perfectly standard timezone identifier used by the majority of the target user base would have been rejected. Fixed by validating via `Intl.DateTimeFormat` construction (wrapped in try/catch) instead, which is alias-tolerant. Applied identically in `trainer.validator.ts` and `trainer.schemas.ts`.

**Profile-photo upload reuses `cloudinary-upload.service.ts` as-is** — same signed-upload-then-Admin-API-reverify-then-safe-replace flow §15 established, just scoped to `daisy-minds/trainers/{id}`. Professional-document upload (qualifications/certifications attachments) was deferred the same way academic-document upload was in §15: `documentUrl`/`documentPublicId` exist on `IQualification`/`ICertification` and are always written `null`; extending to a working upload later should reuse the same Cloudinary service, not a new pattern.

**Permissions** extend the catalog with `trainers:read`/`trainers:manage`/`trainers:export` (mirroring the students module's three-permission shape exactly). The task's own spec floated two additional granular permissions for internal notes (`trainers.internal_notes.read`/`.update`); these were deliberately not added — the existing `trainers:manage` permission already covers the `notes` field, and a separate internal-notes permission has no current consumer that needs the distinction.

**No salary/compensation field exists anywhere in the schema** — explicitly out of scope per the task spec, not merely unexposed in the API.

**Frontend** (`src/features/trainers/`, `src/pages/admin/TrainersPage.tsx`) mirrors `features/students/`'s shape exactly: a `Stepper`-driven 9-step create wizard (`TrainerCreateWizard.tsx`) sharing one `useForm` instance across steps, a flat single-scroll edit form (`TrainerEditForm.tsx`) reusing the same field groups, and a detail drawer (`TrainerDetailDrawer.tsx`) with 7 real tabs (overview/qualifications/employment/availability/sessions/activity, `SUPER_ADMIN`-gated where §15 gated the equivalent) plus 6 placeholder tabs for future modules (courses/batches/live-classes/attendance/assignments/performance), each rendering an `EmptyState` rather than a broken or misleading control. Array/indexed-field RHF paths (`qualifications.{i}.field`, `certifications.{i}.field`, `emergencyContacts.{i}.field`, and `AvailabilityEditor`'s own `availability.{i}.field`) use the same small named-helper-plus-one-justified-`eslint-disable` pattern §15 established for `restrict-template-expressions` vs. `FieldPath<T>`, rather than repeating the disable at every call site.

**One deliberate naming deviation from the task's own suggested endpoint list:** photo endpoints are `/trainers/{id}/photo/*`, not the task's suggested `/trainers/{id}/profile-photo/*` — matching the students module's existing `/students/{id}/photo/*` naming for cross-module consistency, which the task's own instructions explicitly permitted ("keep permissions practical" / reuse-over-duplication intent extended here to naming).

## 18. Admin Dashboard & Operational Analytics (Phase 8) — **Implemented**

Replaces the Phase 3 dashboard shell's hardcoded mock stat cards/chart placeholder (§3 above) with a real, backend-driven operational summary built from data the User/Student/Trainer Management modules (§14/§15/§17) already own. Scope is strictly operational: user/student/trainer counts, status/profile-completion distributions, recent records, a permission-gated audit-activity feed, and operational alerts. No course, batch, enrollment, attendance, assignment, examination, fee, payment, certificate, or placement analytics — those modules don't exist yet, and the task's own spec explicitly forbade fabricating data for them.

**No new collection.** `dashboard.repository.ts` runs direct aggregations against the existing `users`/`students`/`trainers`/`audit_logs` collections — a persisted "dashboard stats" document would just be a second, driftable source of truth for numbers those collections already hold. Student/trainer metrics reuse the same `$lookup`(`users`)+`$facet` shape §15/§17 established for list/export, just producing counts and group-bys instead of paginated rows; one aggregation call per collection covers active-count, new-in-period count, and profile-completion distribution together (`Promise.all`-parallelized across collections, not sequential).

**Timezone-aware period boundaries, not client-side date math.** `utils/date-range.ts#resolveDashboardPeriod` computes named-range boundaries (`TODAY`/`LAST_7_DAYS`/`LAST_30_DAYS`/`THIS_MONTH`/`THIS_YEAR`) using the requesting client's own IANA timezone (`Intl.DateTimeFormat`-based offset calculation, not a fixed UTC day) — "today" means today in the timezone the browser reports, not in UTC. `CUSTOM` ranges use the caller's exact instants, capped at 366 days (enforced identically at the Zod validation layer, so an over-range request fails with a `400`, not a `500` from deep inside the aggregation). The timezone string itself reuses the exact `isValidTimeZone` check §17 introduced for trainer availability (extracted to `utils/timezone.ts` so both modules share one implementation, not two).

**Permission-aware response shaping, not a second endpoint.** `dashboard:read` (held by both `ADMIN` and `SUPER_ADMIN`) gates the whole `GET /dashboard/admin` endpoint; within that single response, `recentActivity` is `null` for `ADMIN` and a populated, safely-serialized array for `SUPER_ADMIN` — mirroring the exact `requireRole('SUPER_ADMIN')` carve-out §15/§17 use for sessions/audit access, rather than inventing a `dashboard.admin.audit.read` permission with no other consumer. The activity feed itself is allowlisted to a fixed, reviewable set of lifecycle actions (`DASHBOARD_ACTIVITY_ACTIONS` in `dashboard.repository.ts`) — session/auth/photo/export/bulk events are deliberately excluded as noise for a high-level operational feed, and only `action`/`entityType`/a resolved human-readable `entityLabel`/`actorLabel`/`createdAt` ever leave the service layer — never raw `metadata`, `ipAddress`, or `userAgent` (SECURITY.md §8).

**Caching is a thin, best-effort addition, not a new general-purpose cache layer.** No cache-service abstraction existed before this phase — `config/redis.ts`'s client was used only by the health-readiness check. `dashboard-cache.service.ts` wraps `redisClient` with a `dashboard:admin:` key prefix and swallows every error (`isRedisConnected()` check plus try/catch around get/set), so a Redis outage degrades the dashboard to always-fresh-from-DB rather than failing it — and no Redis mock is needed in tests, since `mongodb-memory-server` test runs never call `connectRedis()`, so every cache read/write in the test suite is a real, harmless no-op verified by dedicated unit tests. Cache key includes the permission scope (`super_admin`/`admin`), range, resolved start/end instants, and timezone — so a `SUPER_ADMIN`'s cached response (with `recentActivity` populated) can never be served to an `ADMIN` requesting the same period. TTL is 60 seconds, simple expiry-based invalidation — no event-driven cache busting, per the phase's own explicit "don't overengineer" guidance.

**Alerts use an allowlisted internal route map, never a client- or request-derived route.** `ALERT_ROUTES` in `dashboard.service.ts` is a fixed `Record<AlertType, string>` — an alert's `actionRoute` can never be an open redirect, because it's never built from any part of the request. On the frontend, `AlertsPanel`'s `<Link to={alert.actionRoute}>` trusts this the same way any other server-supplied internal route is trusted.

**No charting library was added.** The frontend had none installed, and the phase spec required evaluating that tradeoff before adding one "solely for decorative charts." The 2–5-bucket distributions (user status, student/trainer profile completion) render as a custom `DistributionCard` — a small, accessible bar-list where every bar's label/count/percentage is always visible as text (never color- or length-only), with an `aria-label` summarizing the same information for assistive tech. The pre-existing `ChartPlaceholder` component (§3, whose own code comment named "Phase 18 — Reports & Analytics" as its intended real-chart replacement) is left untouched — this phase's distributions are simple enough not to need it, and a real multi-series time-chart is still correctly deferred to that later reporting phase.

**Deep-linkable alerts required a small, deliberate addition to three existing pages.** For an alert like "`X` incomplete student profiles" to be more than a dead link, `StudentsPage`/`TrainersPage`/`UsersPage` now read `status`/`profileCompletionStatus`/`action` query-string values once at mount (`shared/lib/query-params.ts#readInitialQueryParam`, a one-shot lazy `useState` initializer, not a `useSearchParams` effect/re-render cycle) to seed their filter state or auto-open the create wizard. This is the only cross-module change this phase made outside `features/dashboard/`.

**Frontend** (`src/features/dashboard/`, `src/pages/admin/AdminDashboardPage.tsx`) follows the same reuse-over-duplication discipline as §15/§17: `useAdminDashboard` is a single `useQuery` with `keepPreviousData` (switching the period selector never blanks the dashboard mid-fetch) and an `enabled` flag (a `CUSTOM` range with incomplete start/end dates never fires a doomed request). `AbortSignal` support in `dashboard.api.ts` means TanStack Query cancels a stale in-flight request when the period changes mid-fetch. Loading/error/empty states are explicit per section (`StatCardSkeleton`/`ListSkeleton`/`ErrorState`/`EmptyState`, all pre-existing shared components) so one failing section (e.g. the audit feed) never blanks the whole page — the base summary/distributions/recent-lists stay usable even if the activity feed alone errors.

A follow-on, minimal change from Phase 9A (below) added one honest secondary metric, `publishedCourses`, to `DashboardSecondaryStats` — a direct `CourseModel.countDocuments({status:'PUBLISHED', isDeleted:false})` in `dashboard.repository.ts`, parallelized into the same `Promise.all` this section describes. No enrolment, completion, revenue, attendance, or popularity metric was added — those all require modules that don't exist yet.

## 19. Admin Course Management Module (Phase 9A) — **Implemented**

Course-level metadata and lifecycle only. A course is a single self-contained `courses` document — no curriculum, modules, lessons, videos, PDFs, quizzes, assignments, live classes, attendance, progress tracking, batch assignment, enrolment, certificates, or payments exist yet. Those are all separate future modules; this phase deliberately stops at "what a course *is*," not "what happens inside it."

**No `users` join, unlike students/trainers.** A course is not a person/account, so `course.repository.ts` has no `$lookup`+`$facet` aggregation — `list()`/`listAllForExport()` are a plain `CourseModel.find(query).sort().skip().limit()`. This is the one structural place this module differs from §15/§17's shape, not an inconsistency.

**Course ID generation (`DM-CRS-{year}-{6-digit sequence}`)** reuses the same atomic `counters` collection primitive as student/trainer ID generation (`course-id.service.ts#generateCourseCode`, a new `_id: 'course'` counter document, the same concurrency-safe `findOneAndUpdate({$inc})`) — a third proven pattern, not a new one.

**Lifecycle is an explicit state machine**, not a free-form status field: `create` → `DRAFT`; `publish` (readiness-gated) → `PUBLISHED` (sets `publishedAt`); `unpublish` (`PUBLISHED`-only) → `DRAFT`; `archive` (`DRAFT`|`PUBLISHED`, not already `ARCHIVED`) → `ARCHIVED` (sets `archivedAt`); `restore` is dual-purpose — if the course is soft-deleted, un-deletes it (status untouched); otherwise, if `ARCHIVED`, moves it to `DRAFT` (never straight back to `PUBLISHED` — a re-publish is a separate, explicit action). Soft-delete (`isDeleted`/`deletedAt`) is orthogonal to `status`, matching the ADR above.

**Publication readiness is a single source of truth.** `checkReadiness()` in `course-management.service.ts` returns a structured `{ready, blockers: {field, message}[]}` and backs both the dedicated `POST /courses/:id/readiness-check` endpoint and the `publish` action's own gate (a `422` with the same blocker shape via `ApiError.unprocessable`). A course can never be published while structurally invalid, and the readiness preview a course editor sees can never disagree with what the publish button actually enforces.

**Pricing metadata only — no payment gateway, no checkout, no invoices.** `pricingType` is `FREE`|`PAID`; a `PAID` course requires a positive `basePrice`; an optional `discountPrice` must be below the base price; an optional sale window (`saleStartsAt`/`saleEndsAt`) requires the end to be after the start; switching a course back to `FREE` clears any stale paid-only fields rather than leaving them present-but-ignored. All of this is enforced backend-only via a Zod `superRefine` on `pricingSchema` (see the ADR row above for why the frontend mirror was removed) — violations surface as an API-error toast on submit, not an inline field error.

**Course media reuses the existing signed-upload pattern exactly.** Thumbnail and banner images go through the same Cloudinary signature → client-direct-upload → Admin-API-`resource`-reverify → safe-replace/delete flow §15/§17 established for profile photos, scoped to `daisy-minds/courses/{id}/thumbnail` and `daisy-minds/courses/{id}/banner`. No video upload exists — that belongs to the future Learning Content module.

**Trainer eligibility is metadata, not assignment.** `eligibleTrainerIds` is a validated (must exist, must be active, must not be soft-deleted) list of trainer IDs a course *could* be taught by — there is no batch relationship, no schedule, and no real teaching assignment. The frontend's `EligibleTrainersField` is a legitimate, explicitly-sanctioned read-only cross-feature reuse: it queries `features/trainers/api/trainers.api.ts#listTrainers` directly rather than duplicating trainer-lookup logic.

**Course category is a plain validated string, not a new module** (see ADR above) — deliberately not overengineered into a full Category Management CRUD surface this phase.

**CSV export excludes internal-only fields** (`internalNotes`, raw audit metadata, Cloudinary credentials) and escapes every field against CSV-formula injection (a leading `=`/`+`/`-`/`@` is neutralized), matching the export-safety pattern already established for students/trainers. `MAX_EXPORT_ROWS = 5000` caps a single export request.

**Bulk actions** (`publish`/`archive`/`restore`/`delete`) validate and authorize each course independently and report partial failures (`{succeeded: string[], failed: {id, reason}[]}`) rather than aborting the whole batch on the first bad item — the same shape students/trainers/users bulk endpoints already use.

**Route ordering matters, on both backend and the frontend test mocks.** `/courses/export` and `/courses/bulk/*` must be registered before the `/courses/:id` param route, or a request to `/courses/bulk/archive` gets incorrectly matched as `id="bulk"` against `/courses/:id/archive`. `course.routes.ts` documents this explicitly; the MSW mock handlers (`frontend/src/test/msw/handlers/courses.handlers.ts`) initially missed this and had to be corrected to match.

**A frontend Zod/RHF interaction was found and fixed, worth documenting for future modules with many `.default()`-bearing schema fields.** A Zod object schema field with `.default(value)` has an *output* type where the field is required (the default fills it in post-parse) but an *input* type where it stays optional (pre-parse — what the caller/form actually provides). The course schema has ~13 such fields. `zodResolver`'s generic overload resolution silently failed when given a form-values type derived via `z.infer`/`z.output` (which treats those fields as required), falling back to an unconstrained generic and breaking every shared `Control<T>`-typed field component with cryptic, unrelated-looking type errors. Typing `CreateCourseFormValues`/`UpdateCourseFormValues` as `z.input<typeof schema>` — the textbook-correct type for what an RHF form actually holds — fixed it completely. The trainer/student modules never hit this because they have fewer `.default()`-bearing fields, below whatever internal threshold triggers the failure. `toPayload()` functions now use `?? fallback` for the resulting optional defaulted fields when building the final API payload.

**Frontend** (`src/features/courses/`, `src/pages/admin/CoursesPage.tsx`) follows the same structure as students/trainers: a list page with stat cards/search/filters/sort/bulk actions/export, a `Stepper`-driven 9-step create wizard, a flat edit form, and a detail drawer. Unlike the trainer detail drawer's placeholder tabs (§17), the course detail drawer's future-module tabs (batches, enrolment, learning analytics) explicitly show an honest "available in a later phase" empty state — never fabricated or fake data, per the phase's own hard requirement. The drawer's **Curriculum** tab is no longer one of these placeholders as of Phase 9B — see §20.

**Permissions** extend the catalog with `courses:read`/`courses:manage`/`courses:publish`/`courses:export`, matching the existing dot/colon naming convention and kept to what the module actually needs (a separate `publish` permission exists because publishing a course to the public catalog is a materially higher-stakes action than editing draft metadata).

**Dashboard integration is intentionally minimal** — see §18's addendum above: one honest `publishedCourses` count, nothing analytical.

## 20. Curriculum Builder Module (Phase 9B) — **Implemented**

Structure and ordering only: `Course → Modules → Lessons`. No SECTION layer was introduced — the PRD's own hierarchy and the existing Phase 1 `course_modules`/`lessons` scaffold both already matched the simpler two-level shape, and the task's own guidance was explicit not to invent unnecessary hierarchy. This phase deliberately does **not** implement video/PDF upload, rich lesson body content, the learning player, student progress/completion tracking, quizzes, assignments, batches, or enrolment — `lessonType`/`prerequisiteLessonIds` describe *intended future content and sequencing*, they don't deliver or enforce any of it yet.

**Extends the Phase 1 scaffold additively, same discipline §19 established for `courses` itself.** `course-module.model.ts`/`lesson.model.ts` already existed but had zero consumers anywhere in the codebase (verified before touching them) — `status` (the same shared `ApprovalStatus` enum `courses` uses) and `estimatedDurationMinutes` are new on both; on `lesson.model.ts`, the old `isPublished` boolean and `durationSeconds` fields are *replaced* (not left as dead duplicates) by `status`/`estimatedDurationMinutes`, matching the exact `durationHours`→`durationValue`+`durationUnit` replacement precedent §19 set. `contentType`/`contentUrl` are left in place, now optional, reserved for the future Learning Content phase to actually populate — `lessonType` (new) is the structural classification available today, a distinct concept from the content-file-type enum those two dormant fields describe.

**Ordering strategy: server-controlled contiguous 0-based integers, never client-trusted.** `order` is never settable through the plain create/update endpoints — creating always appends (`nextModuleOrder`/`nextLessonOrder`, one extra query reading the current max), and repositioning only ever happens through the dedicated reorder/move endpoints. A reorder request must name **every** current active sibling exactly once (`findSetMismatch` in `curriculum-order.util.ts`) — a partial list is rejected outright rather than guessing where unlisted siblings should land; the server then re-derives a contiguous sequence from the *relative* ranking submitted (`normalizeOrders`), so a client-side drag-drop library's own numbering scheme never has to match the backend's literal values.

**The first real database transaction in this codebase.** Every prior module's writes were single-document; curriculum's reorder/move/duplicate/cascading-delete operations touch multiple documents at once and need to be all-or-nothing. `utils/transaction.ts#withTransaction` wraps `mongoose.startSession()`/`session.withTransaction()` — this requires a replica set (MongoDB Atlas in production always is one). Local tests use a **second, dedicated** `MongoMemoryReplSet` helper (`tests/setup-db.ts#setupTransactionalTestDatabase`) alongside the existing standalone `MongoMemoryServer` helper every other module's tests use — only curriculum test files pay the slower replica-set startup cost, and no other test file was touched.

**Module deletion cascades to its active lessons, with an explicit tombstone for correct restore.** Deleting a module soft-deletes it and every one of its then-active lessons in one transaction, marking only the cascaded lessons with `Lesson.deletedWithModule: true`. Restoring the module restores only lessons carrying that flag (then clears it) — a lesson that was independently soft-deleted *before* the module delete is never resurrected by the module's own restore. The alternative (blocking module deletion until lessons are moved out) was considered and rejected as worse UX for the common case of retiring an entire module at once.

**Move vs. reorder are two different endpoints, not one overloaded one.** Reordering (`POST /lessons/reorder`) repositions lessons *within* one module; moving (`POST /lessons/:lessonId/move`) relocates a lesson to a *different* module (or a different position in the same one) in a single transaction that closes the gap in the source module and makes room in the target — cross-course moves are structurally impossible since the target module is looked up scoped to the same `courseId` the URL already trusts (a mismatched target simply 404s, no explicit cross-course check needed).

**Duplication remaps only the prerequisites that survive together.** Duplicating a module copies it and every active lesson within it in one transaction, building an old-lesson-id→new-lesson-id map as it goes; a duplicated lesson's prerequisite is remapped to its duplicated counterpart only if *that* prerequisite was also duplicated in the same operation — a prerequisite pointing outside the module being duplicated is dropped, never left pointing at the original, undupped lesson. Duplicating a single lesson inserts the copy immediately after the source (shifting later siblings by one) and copies its prerequisites as-is (still valid, since the duplicate lives in the same course).

**Prerequisites are structure metadata only — no unlock/progress logic exists yet.** Every write path (create has nothing to violate yet since a brand-new lesson can't already be a dependency; update is the real gate) rejects: self-reference, a prerequisite outside the course, a prerequisite that doesn't exist or is deleted, and any edge that would close a cycle. Cycle detection (`utils/curriculum-prerequisite.util.ts`) is a plain iterative graph walk — `wouldCreateCycle`/`findCyclicPrerequisite` for the incremental "would adding this one edge close a loop" check every write performs, and a separate full-graph 3-color-DFS `hasCycle` used only by the curriculum readiness check as a defense-in-depth safety net (writes should make a stored cycle structurally impossible, but readiness re-verifies it cheaply anyway rather than just trusting that invariant forever).

**Two distinct readiness concepts, deliberately not merged.** Phase 9A's course readiness (`course-management.service.ts#checkReadiness`) is metadata readiness — title, description, thumbnail, pricing — and is completely unchanged by this phase; an existing published course with no curriculum at all is still exactly as valid as it was before Phase 9B shipped. Curriculum readiness (`curriculum.service.ts#checkCurriculumReadiness`) is a separate, new concept: at least one active module and lesson, no orphan lessons, no published lesson under an archived module, and no prerequisite cycle. **Publishing curriculum items never auto-publishes the course, and publishing the course never requires curriculum to exist** — staged editing is explicitly supported (a `PUBLISHED` course may still have `DRAFT` modules/lessons being prepared for a future update). A later phase (learning-content completeness) is expected to combine both into a genuine "launch readiness" concept; this phase's UI copy is deliberately "curriculum **structure** ready," never "course ready to launch," to avoid overclaiming.

**Archived course = curriculum read-only; soft-deleted course = curriculum inaccessible.** Every curriculum write path calls `assertEditableCourse`, which 409s if `course.status === 'ARCHIVED'` (reads still work, so an admin can review an archived course's structure) — the alternative of a more granular "which fields" read-only model was rejected as unnecessary complexity for a state that's supposed to mean "not active." A soft-deleted course 404s on both reads and writes (via the existing `courseRepository.findById`'s `isDeleted: false` scoping), matching every other module's soft-delete convention.

**Curriculum audit events are recorded against the parent *course*, not a `course_module`/`lesson` entity of their own.** `entityType: 'course'`, `entityId: courseId` — a deliberate reuse of the existing `GET /courses/:id/audit` endpoint and `CourseAuditTimeline` UI (§19) instead of standing up a second audit-read surface; the specific module/lesson affected always travels in the event's `metadata`. This means every curriculum mutation shows up in a course's existing "Activity" tab for free.

**Permissions reuse the existing `courses:read`/`courses:manage`/`courses:publish` catalog — no new `curriculum:*` permissions were added.** The task's own guidance preferred fewer permissions absent a real business need for finer granularity, and curriculum management is conceptually part of managing a course. This also meant no `seed-roles.ts` change, and therefore no live-database re-seed was needed for this phase.

**Frontend** (`src/features/courses/curriculum/`, nested under the existing courses feature rather than a new top-level one — curriculum only ever exists in the context of one specific course) is a dedicated full page (`src/pages/admin/CourseCurriculumPage.tsx`, route `/admin/courses/:courseId/curriculum`), not a tab's worth of content crammed into the course detail drawer — the drawer's Curriculum tab instead shows a compact readiness summary and an "Open Curriculum Builder" link. This mirrors the same reasoning that moved course/student/trainer *creation* out of side drawers into dedicated pages during Phase 9A's follow-on UI work: a builder with drag handles, per-module lesson lists, and multiple action menus needs real page width, not a `sm:max-w-2xl` panel.

**Drag-and-drop uses `@dnd-kit` (`core`+`sortable`+`utilities`)** — the first drag-drop dependency in this codebase, evaluated first per the task's own "confirm maintenance/accessibility/bundle impact" requirement: it's the actively-maintained modern standard (the older `react-beautiful-dnd` is archived/unmaintained), ships a built-in keyboard sensor, and is tree-shakeable. Two separate `DndContext`s exist — one at the page level for module reordering, one *per module card* for reordering that module's own lessons — deliberately **not** one shared multi-container context spanning module boundaries. Moving a lesson to a *different* module is a keyboard-accessible menu action ("Move to module…", a small dialog picking target module + position) rather than a cross-container drop target: the task's own "drag/drop must not be the only way to reorder" requirement made an explicit, always-available action the more defensible primary path for that specific operation, not just a fallback. Every reorderable item also gets explicit **Move up**/**Move down** menu actions (not just dnd-kit's own keyboard sensor) as the guaranteed-accessible alternative to physical drag for same-container reordering.

**No optimistic UI updates — every mutation invalidates and refetches the curriculum tree on success.** Reorder/move/duplicate/cascading-delete all touch multiple documents, and building correct optimistic cache patches for all of them would be substantial complexity for a first version (task's own "do not overengineer real-time collaborative editing" guidance). The practical consequence: on a failed reorder, nothing in the UI has changed yet (there was nothing to roll back), and the error surfaces as a toast — verified by an explicit regression test. Toast success/error messages double as the "announce successful/failed reorder" accessibility requirement, since the app's `<Toaster />` (sonner) already renders every toast inside an `aria-live` region.

## 21. Learning Content Management Module (Phase 9C) — **Implemented**

Lesson-content authoring and secure media delivery for the four lesson types that actually have content today: `VIDEO`, `TEXT`, `DOCUMENT`, `EXTERNAL_LINK`. `QUIZ`/`ASSIGNMENT`/`LIVE_CLASS` remain honest structural placeholders — a `contentStatus` of `NOT_CONFIGURED` and an explicit "coming in a future phase" notice in the editor, never a fake/disabled form. This phase deliberately does **not** implement the student learning player, lesson progress/completion tracking, quizzes, assignments, live-class scheduling, attendance, certificates, batches, enrolment, or payments.

**Replaces the Phase 1 scaffold's dormant `contentType`/`contentUrl` with a `lessonType`-discriminated content structure — same "replace, don't duplicate" discipline §19/§20 established.** Both fields had zero consumers anywhere (verified before touching them; `shared/enums.ts`'s `CONTENT_TYPES` enum was deleted outright alongside them, same zero-consumer check). `lesson.model.ts` now carries `textContent`/`videoAsset`/`documentAsset`/`externalLink` — exactly one populated per lesson, selected by `lessonType` — plus a server-computed `contentStatus: EMPTY | INCOMPLETE | READY | PROCESSING | ERROR | NOT_CONFIGURED` (`utils/lesson-content-status.util.ts#computeContentStatus`), never client-settable. Changing a lesson's `lessonType` away from one with existing content is rejected with `409` unless the request also sets `confirmContentReset: true`, in which case all four content fields are cleared and `contentStatus` is recomputed in the same write (`curriculum.service.ts#updateLesson`) — silent content loss on a type change is structurally impossible.

**`lesson_resources` stays its own collection, now with real Cloudinary-backed fields instead of the Phase 1 scaffold's unused `resourceUrl`/`fileType`.** A lesson has exactly one primary content item but zero-to-many downloadable resources with their own independent add/reorder/remove lifecycle and a max-count cap (`MAX_RESOURCES_PER_LESSON`, default 20) — embedding them as an array on `lessons` would also risk the 16MB document limit on a heavily-resourced lesson. `courseId` is denormalized onto each resource for the same read-pattern reason `lessons.courseId` is (§19).

**Three distinct readiness concepts now exist, never collapsed into one.** Course metadata readiness (Phase 9A, `course-management.service.ts#checkReadiness`) and curriculum structural readiness (Phase 9B, `curriculum.service.ts#checkCurriculumReadiness`) are both completely unchanged by this phase. **Course launch readiness** (`course-launch-readiness.service.ts`, new) is the third, additive layer: it composes the first two plus a content-readiness pass over published lessons (at least one published module; every published lesson's `contentStatus === 'READY'`) and reports which of the three layers is blocking. UI copy says "Learning content ready" / "Launch readiness" — never that the course can accept students, since no enrolment/batch/payment module exists yet to make that claim true.

**Deliberately does not add a hard `contentStatus === 'READY'` gate inside the existing Phase 9B `publishLesson` endpoint.** Doing so would be a behavior change to an already-shipped endpoint, retroactively affecting lessons Phase 9B already published with no content. Instead, launch readiness alone surfaces "published lesson lacks ready content" as a blocker — the safer of the two options the task itself offered, chosen explicitly.

**Signed direct-to-Cloudinary uploads for video/document/resource, generalized from the existing photo-upload pattern rather than duplicated.** `cloudinary-upload.service.ts`'s `generateSignedUploadParams`/`verifyUploadedAsset`/`deleteAsset` (previously hardcoded to `resource_type: 'image'` for course thumbnail/banner and student/trainer photos) now accept optional `resourceType`/`type`/`allowedFormats`/`maxFileSize` parameters that default to the original image behavior — every Phase 9A/earlier caller is unaffected and untouched. New callers pass explicit constraints: video → `resource_type: 'video'`, formats `mp4`/`webm`/`mov`, `MAX_VIDEO_UPLOAD_MB`; document/resource → `resource_type: 'raw'` (Cloudinary's non-image/video bucket), document formats `pdf` only, resource formats `pdf`/`doc(x)`/`ppt(x)`/`xls(x)`/`zip`/`jpg`/`jpeg`/`png`/`webp` (`ALLOWED_RESOURCE_FORMATS`) — executable/installer formats are never in any allowlist. Folder scope is always server-chosen and verified (`daisy-minds/courses/{courseId}/lessons/{lessonId}/{video|document|resources}`), never accepted from the client; the signature endpoint also never accepts a client-supplied public ID.

**Every upload is independently re-verified against Cloudinary's Admin API before being trusted — a client-reported `secureUrl` is never authoritative.** `verifyUploadedAsset` confirms the asset exists, is the expected `resource_type`, landed in the exact expected folder, and (where a limit applies) doesn't exceed the configured size/duration — a signature only constrains what a client is *permitted* to upload, never proof of what actually happened. `originalFilename` (document) and `filename`/`title`/`description`/`isDownloadable` (resource) are the only client-reported fields ever trusted as-is, since they're purely cosmetic display metadata never used for storage paths, security decisions, or the Cloudinary API calls themselves — `resourceType`/`format`/`mimeType`/`bytes` for a resource are always derived server-side from the verified asset (`utils/lesson-resource-format.util.ts`), never accepted from the client.

**`type: 'authenticated'` Cloudinary uploads for all Phase 9C media — never `type: 'upload'` (public) like the existing photo/thumbnail/banner flow.** No lesson video/document/resource asset is ever reachable at a permanent public URL. The one place a playable/downloadable URL is minted is `media-delivery.service.ts#generateSignedDeliveryUrl` — a short-lived (5-minute default), HMAC-signed Cloudinary delivery URL computed locally (no network call, so it never fails due to Cloudinary being unreachable), deliberately generic (not lesson-specific) so the future Learning Player reuses it unchanged instead of standing up a parallel implementation. Every DTO returned to the frontend (`VideoAssetDto`/`DocumentAssetDto`/`LessonResourceDto`) omits `provider`/`publicId`/`assetId`/`version` entirely — preview/delete/replace operations are always lesson- or resource-ID-scoped server-side, so the client never needs (and is never given) the raw Cloudinary identifier.

**TEXT lesson content is sanitized server-side on every write, via a maintained library (`sanitize-html`) — frontend sanitization is never trusted.** `utils/html-sanitize.ts#sanitizeLessonHtml` enforces an explicit tag/attribute/scheme allowlist (headings, paragraphs, bold/italic/strike, lists, links — `rel="noopener noreferrer nofollow"` forced on every link, code blocks, blockquotes, tables) — `script`/`style`/`iframe`/`object`/`embed`/`form`, all event-handler attributes, and `javascript:`/`data:` URLs are never in the allowlist and are always stripped, regardless of what the client sends. The stored value is always the *sanitized* output, never the raw input.

**External-link content is validated server-side (`javascript:`/`data:`/`file:`/`ftp:` schemes rejected, `http(s)` only) and never fetched by the backend** — no SSRF surface exists for this feature, by construction, not by a network-egress rule. The frontend validates the same schemes client-side (`content.schemas.ts`) purely for immediate UX feedback; the backend re-validates independently and is the actual security boundary.

**Malware scanning is an explicit, documented production-readiness gap, not a fabricated capability.** No malware-scanning provider is wired into this phase — Cloudinary itself does not perform malware/virus scanning on uploaded files, and no code or documentation claims otherwise. The mitigations actually in place: a strict per-content-type format allowlist (never "any file"), independent server-side re-verification of format/size/resource-type against Cloudinary's own response, environment-driven size caps, `type: 'authenticated'` private storage (no public hotlinking), and audit logging of every upload/replace/delete. See SECURITY.md's Resource Upload section for the explicit "before allowing untrusted third parties to upload" requirement this gap implies.

**Permissions reuse the existing `courses:read`/`courses:manage`/`courses:publish` catalog — same discipline §20 established, `courses:media:manage` was considered and rejected as permission bloat** absent a genuine need to let some `courses:manage` holders touch content but not structure (no such role split exists in this product today). No `seed-roles.ts` change, no live-database re-seed.

**Audit events reuse the exact same `recordCurriculumAudit` helper/pattern as §20** — `entityType: 'course'`, `entityId: courseId`, specifics in `metadata` — so every content mutation lands in the same course "Activity" timeline curriculum events already use, with no new audit-read surface. **Frontend** (`src/features/courses/curriculum/content/`, nested under the existing curriculum feature the same way curriculum itself nests under courses — §20's reasoning) is a dedicated page (`src/pages/admin/LessonContentEditorPage.tsx`, route `/admin/courses/:courseId/curriculum/modules/:moduleId/lessons/:lessonId/content`), lazy-loaded the same way every other admin page is (`routes/admin.routes.tsx`'s `lazy: () => import(...)`) — this is also what keeps Tiptap and the video-preview code out of every route that isn't the content editor. ## 22. Admin Batch Management Module (Phase 10A) — **Implemented**

A batch is a **scheduled delivery instance** of a course — "when and how," as distinct from a course's own "what" (§19). One course can have many batches (e.g. "Full Stack Web Development" → "August 2026 Morning" / "August 2026 Evening" / "Corporate Batch — ABC Pvt Ltd"). This phase deliberately does **not** implement student enrolment, a waiting list, batch transfer, a student roster, attendance, live-class sessions, the learning player, progress tracking, assignments, quizzes, examinations, fees, payments, certificates, or notifications — capacity (`maxStudents`/`minimumStudents`/`waitlistEnabled`) is **configuration only** this phase; there is no `enrolledCount` or any derived seat-occupancy field anywhere in the schema, DTO, or UI, and none is fabricated. A future Phase 10B is expected to add real enrolment/seat tracking without needing to touch this phase's shape.

**Replaces the Phase 1 `batch.model.ts` scaffold entirely — same "verify zero consumers, then replace" discipline §19/§20/§21 all established.** The scaffold's single `trainerId` field, fake `enrolledCount` counter, and numeric `dayOfWeek` didn't match this phase's actual requirements (multiple trainers, a real lifecycle state machine, a recurring weekly timetable, calendar exceptions) and had zero real consumers (only a documentation comment in `trainer.model.ts` referenced it).

**Batch ID generation (`DM-BAT-{year}-{6-digit sequence}`)** reuses the same atomic `counters` collection primitive §19's course-ID generation established — a fourth proven instance of the same pattern, not a new one (`batch-id.service.ts#generateBatchCode`).

**`startDate`/`endDate` are nullable, unlike a course's required fields** — a deliberate design choice, not an oversight: a `DRAFT` batch is fully editable-but-not-yet-operational (mirroring `DRAFT` course/module/lesson semantics throughout this codebase), and the readiness check's own blocker list (`START_DATE_MISSING`/`END_DATE_MISSING`) only makes sense if the dates can be legitimately absent at that stage. `timezone`/`deliveryMode`/`maxStudents` stay required at creation, since the 8-step creation wizard collects all three before the `POST` call ever fires.

**Lifecycle is an explicit state machine, looked up from one table rather than hand-rolled per-action conditionals.** `utils/batch-lifecycle.util.ts#ALLOWED_TRANSITIONS` is the single source of truth every lifecycle service method consults via `canTransition`: `DRAFT → {SCHEDULED, CANCELLED}`, `SCHEDULED → {DRAFT, ACTIVE, CANCELLED}`, `ACTIVE → {COMPLETED, CANCELLED}`, `COMPLETED → {ARCHIVED}`, `CANCELLED → {ARCHIVED}`, `ARCHIVED → {DRAFT}`. `COMPLETED→ACTIVE`, `CANCELLED→ACTIVE`, and `ARCHIVED→ACTIVE` are all structurally impossible, not just discouraged. No system-date check ever silently flips a status — a batch whose `startDate` has passed while still `DRAFT` stays `DRAFT` forever until an admin explicitly schedules/activates it; dates only ever inform the readiness check, never drive a transition themselves. `restore` is dual-purpose, mirroring §19's course `restore` exactly: if the batch is soft-deleted, un-deletes it (status untouched); otherwise moves `ARCHIVED` back to `DRAFT` (a fresh restart, never straight back to an operational status).

**Readiness, status, and trainer conflicts are three deliberately distinct concepts, never merged.** `status` is the explicit, admin-driven lifecycle state above. `batch-readiness.service.ts#checkReadiness` is a computed, backend-authoritative `{ready, blockers: {field, code, message}[]}` — the single source of truth behind both the standalone `POST /:id/readiness-check` endpoint and the `schedule` lifecycle action's own gate (rejected with the same blocker shape via a `422`, mirroring §19's course-publish gate exactly). It deliberately omits checks the write-time Zod validator already makes structurally unreachable (end-before-start once both dates are present, overlapping weekly slots, invalid capacity/timezone) — the same "don't check the unreachable" discipline §21's launch-readiness service established. `batch-conflict.service.ts` is a third, independently-queryable concept (`GET /:id/conflicts`) folded into readiness as additional blockers rather than duplicated: trainer availability conflicts (a weekly slot outside a trainer's declared `AVAILABLE`/`PREFERRED` windows, or intersecting a `BLOCKED` one — compared only when both sides share the exact same IANA timezone string; a different-timezone slot is silently skipped rather than falsely flagged, since full cross-timezone wall-clock conversion was explicitly out of scope) and cross-batch double-booking (the same trainer already primary/assistant on another `SCHEDULED`/`ACTIVE` batch with an overlapping date range **and** an overlapping weekly slot). Conflict detection is validation feedback, not a scheduling lock — two admins racing to assign the same trainer to overlapping batches is a rare, low-stakes collision the trainer sorts out afterward, not data corruption, so no distributed lock was introduced for it.

**Trainer assignment reuses a course's `eligibleTrainerIds` semantics rather than inventing a parallel concept.** A batch's `primaryTrainerId` must belong to its course's `eligibleTrainerIds` list **only when that list is non-empty** — an empty list means "no restriction configured," never "no trainer allowed." Readiness additionally requires the primary trainer to exist, not be soft-deleted, have an employment status that permits teaching (`ACTIVE`, not `TERMINATED`/`INACTIVE`), and have a linked user account that is itself `ACTIVE` — checks kept separate from the cheaper write-time existence check (`trainerRepository.countExisting`, existence-only, added additively) so a batch can still be saved as `DRAFT` with a trainer who isn't yet fully eligible to teach, and only blocked from `SCHEDULED` once genuinely ready.

**The weekly schedule is a bounded, embedded array of recurring-timetable *template* metadata — it never generates an actual live-class/session record.** Each slot stores `dayOfWeek` + a plain `"HH:mm"` wall-clock string pair + the batch's own `timezone`, deliberately never converted to UTC at write time — converting a *recurring* weekly slot to UTC would silently break across DST transitions and defeat the entire point of storing "every Monday at 6 PM local time" (`trainer.model.ts#IAvailabilitySlot` established this same local-time-plus-timezone pattern first; batches reuse it rather than inventing a second convention). Calendar exceptions (`{date, type, title, note}` — `HOLIDAY`/`NO_CLASS`/`INSTITUTE_CLOSED`/`TRAINER_UNAVAILABLE`/`OTHER`) are simple date exclusions, embedded on the batch document rather than a separate `batch_calendar_exceptions` collection — the task's own guidance was explicit that per-batch exception counts are small enough that embedding is the practical V1 choice; both arrays use this app's established "whole-array replace, never partial" contract (`POST /:id/weekly-schedule`, `POST /:id/calendar-exceptions` — API-STANDARDS.md §4), the same pattern §20 set for curriculum's own reorder endpoints.

**Location is mode-aware but not mode-exclusive at the schema level.** `ONLINE` batches only ever populate `meetingProvider` (an enum placeholder — `GOOGLE_MEET`/`ZOOM`/`TEAMS`/`OTHER`) and `virtualClassNotes`; real meeting credentials/URLs are never stored anywhere in this phase (no live-class integration exists yet). `OFFLINE` batches populate the full venue address; `HYBRID` batches may populate both. Which fields are *required* for which `deliveryMode` is validator/readiness logic (`LOCATION_INCOMPLETE` for an offline/hybrid batch missing a complete address), not a schema-level branch — an admin building a `HYBRID` batch genuinely needs both halves available on the same document.

**A real PATCH data-loss bug was found by the test suite and fixed before this phase shipped, worth documenting for future modules reusing this "base schema, `.omit()` + `.partial()` for update" pattern.** `updateBatchSchema` was originally `batchBaseSchema.omit({courseId:true}).partial()`. Several base fields (`weeklySchedule`, `calendarExceptions`, `assistantTrainerIds`, `tags`, `waitlistEnabled`) carried a Zod `.default(...)`. `.partial()` does **not** suppress a field's own `.default()` — Zod substitutes the default the instant a key is `undefined`, regardless of the field's optionality, so a bare `{name: "..."}` PATCH silently parsed with `weeklySchedule: []`/`assistantTrainerIds: []`/`tags: []`/`waitlistEnabled: false` baked in, and since `batch-management.service.ts#updateBatch` spreads the parsed input into its `$set`, every partial update that didn't explicitly re-send those fields wiped them (and fired their field-specific audit events on every PATCH, not only when genuinely changed). Fixed by keeping `batchBaseSchema` itself entirely bare (`.optional()`, no `.default()` on any field) so `.partial()`'s "omitted key ⇒ leave unchanged" semantics actually hold, and re-adding `.default([]/false)` only on `createBatchSchema` via `.extend()`, where "omitted at creation" genuinely should mean "start empty." §19's own course module and any future module built on the same `omit().partial()` update-schema shape should double-check this interaction before shipping.

**CSV export, bulk actions, and audit logging all reuse the exact establishing patterns from §19/§20/§21 — no new primitive was invented.** Export columns (Batch Code, Name, Course Code, Course Title, Start/End Date, Timezone, Delivery Mode, Primary Trainer, Maximum Capacity, Waitlist Enabled, Status, Created At) exclude `internalNotes` and the full venue address; every field is passed through the same `utils/csv.ts#toCsv`/formula-injection guard §19 established; `MAX_EXPORT_ROWS = 5000`. Bulk actions (`archive`/`cancel`/`delete`) validate and act on each batch independently, reporting `{succeeded, failed: {id, reason}[]}` rather than aborting on the first failure. The minimum audit-event set is `batch.{created,updated,scheduled,unscheduled,activated,completed,cancelled,archived,restored,soft_deleted,duplicated,trainers_changed,timetable_changed,calendar_exceptions_changed,capacity_changed,location_changed,bulk_action,exported}` — a noisy `batch.readiness_checked` event was deliberately not added, mirroring §19's own restraint around read-only checks.

**Route naming resolves an ambiguity the task itself flagged: lifecycle "schedule" vs. timetable "schedule."** A naive `/schedule` route would collide between "mark this batch `SCHEDULED`" and "set the weekly timetable." Lifecycle transitions live under `POST /:id/lifecycle/{schedule,unschedule,activate,complete,cancel,archive,restore}`; the recurring timetable is `POST /:id/weekly-schedule` — unambiguous, and matching the "compact, whole-set, never partial" replace contract the calendar-exceptions endpoint (`POST /:id/calendar-exceptions`) also uses. Deliberately POST, not PUT — this project never uses PUT (API-STANDARDS.md §2).

**Permissions: `batches:read`/`batches:manage`/`batches:export` — three, not four.** `batches:manage` covers every lifecycle action (schedule/unschedule/activate/complete/cancel/archive/restore/delete) rather than a separate `batches:lifecycle` permission, chosen for the same "consistency over artificial granularity" reasoning that gave courses `publish` its own permission but batches did not need an equivalent split (no distinct "batch approval" workflow exists the way course publication has one). ADMIN and SUPER_ADMIN get all three; TRAINER and STUDENT get none — a trainer manages their own teaching content, not the batch scheduling surface. `scripts/seed-roles.ts` was extended additively; this has **not** been run against the shared Atlas database (local-only per the phase's safety constraints) — see the final report's live-infrastructure note.

**Database indexes are query-driven only, mirroring every prior module's restraint.** Unique `batchCode` (partial, `isDeleted: false`), `{courseId, status}`, `{primaryTrainerId, status}`, `{startDate, endDate}`, `{status, startDate}`, `{isDeleted, status}`, `{tags}`, and a text index on `{name, batchCode}` for search — no speculative indexes beyond what the list/filter/conflict-detection query patterns actually need.

**Frontend** (`src/features/batches/`, mirroring the `courses`/`trainers` feature-folder shape exactly: `api/`, `components/`, `hooks/`, `schemas/`, `types/`) gets a dedicated detail page (`src/pages/admin/BatchDetailPage.tsx`, route `/admin/batches/:batchId`) rather than a drawer, the same reasoning §20 gave curriculum: a weekly-timetable editor, calendar-exception list, trainer selectors, readiness/conflict panels, and five tabs (Overview/Schedule/Trainers/Settings/Audit) need real page width. The 8-step `BatchCreateWizard` (Course & Identity → Dates & Timezone → Trainers → Weekly Timetable → Delivery & Location → Capacity → Calendar Exceptions → Review) always creates a `DRAFT` batch — it never auto-schedules, matching every other module's "wizard creates, a separate explicit action activates/publishes" pattern. The `WeeklyScheduleEditor` deliberately does **not** use `@dnd-kit` despite it being available in this codebase (§20/§21) — the task's own spec only asked for add/remove/optional copy-to-another-day on a template editor with no meaningful ordering concept, so adding a drag-drop dependency here would be over-engineering a UI that has nothing to reorder. List-table capacity always renders "Max {N}" — never a fraction or an "X/Y enrolled" figure, enforced by an explicit regression test asserting no `enrolledCount`/`availableSeats` field exists on any rendered row, since no such field exists in the DTO at all (see the "capacity is configuration only" note above).

## 23. Student Enrollment Engine — Backend Foundation (Phase 10B Part 1) — **Implemented**

An enrollment is a student's membership in one batch — the authorization bridge between student identity and learning access. This part ships the full backend domain (schema, capacity/waitlist engine, lifecycle, transfer, entitlement) and no frontend UI (Part 2). Out of scope for Part 1: the admin enrollment UI, self-service student enrollment, payment/fee gating, and any actual Learning Player/lesson-access wiring — `enrollment-access.service.ts#assertStudentCourseAccess` is built and exported but not called from any route yet, ready for Phase 11+ to import unchanged.

**Replaces the Phase 1 `enrollment.model.ts` scaffold entirely (zero real consumers verified first) — same discipline §19–§22 all established.** The old 4-state `PENDING_PAYMENT`/`ACTIVE`/`COMPLETED`/`WITHDRAWN` shape has no seat/capacity concept, no waitlist, no transfer lineage, and no access-window entitlement — bolting any of that onto the existing enum would still have required the same breaking status-enum change this replacement makes explicitly.

**Enrollment ID (`DM-ENR-{year}-{6-digit sequence}`)** reuses the same atomic `counters` collection primitive §19/§22 established — a fifth instance of the identical pattern.

**Explicit 8-status lifecycle, chosen deliberately over the task's alternative "PENDING reserves a seat" model.** `PENDING → CONFIRMED|WAITLISTED|CANCELLED`, `WAITLISTED → CONFIRMED|CANCELLED`, `CONFIRMED → ACTIVE|CANCELLED`, `ACTIVE → SUSPENDED|COMPLETED|DROPPED|CANCELLED`, `SUSPENDED → ACTIVE|DROPPED|CANCELLED`; `COMPLETED`/`CANCELLED`/`DROPPED` are terminal (`utils/enrollment-lifecycle.util.ts`, the single source of truth every lifecycle service method consults, mirroring `batch-lifecycle.util.ts`'s exact shape). Seat-consuming statuses are `CONFIRMED`/`ACTIVE`/`SUSPENDED` only — `PENDING` and `WAITLISTED` never hold a seat. **The standard creation path (`POST /enrollments`, and `bulk/enroll`) goes directly to `CONFIRMED` (seat reserved) or `WAITLISTED` (no seat, if the batch allows one) — it never produces a `PENDING` record.** `PENDING` stays in the schema and state machine (reachable via `POST /:id/confirm`) as a deliberately-unused-today hook for a possible future bulk-import-staging/approval-queue workflow, rather than removed — this was the more defensible reading of the task's own two partially-conflicting descriptions (a "PENDING doesn't consume a seat" status definition vs. a creation-transaction walkthrough that reserves a seat immediately), resolved in favor of the walkthrough since it's the more procedurally explicit of the two.

**Capacity is now real, transactional, server-managed derived state on `batches` — the correct phase to introduce it, per §22's own explicit deferral.** `batches.occupiedSeats`/`waitlistSequence` (additive fields, Phase 10A shipped with neither) are never client-writable and never generically PATCH-able — the only writers are `batchRepository.reserveSeat`/`releaseSeat`/`nextWaitlistPosition` (`enrollment-capacity.service.ts`'s exclusive callers). **The oversubscription race is closed at the database level, not the application level:** `reserveSeat` is a single atomic `findOneAndUpdate` using `$expr: {$lt: ['$occupiedSeats', '$maxStudents']}` to compare two fields of the *same* document — MongoDB serializes concurrent writes to one document, so of two simultaneous last-seat requests, only one can ever match the filter and apply the `$inc`; the loser gets `null` back and falls through to the waitlist path (or a `409`). This was verified, not just designed: an integration test fires two concurrent `POST /enrollments` at a `maxStudents: 1` batch and asserts exactly one `CONFIRMED` + one `WAITLISTED` result, never two `CONFIRMED`s. Every seat-affecting write happens inside `withTransaction` (§20's transaction helper, reused unchanged) alongside the enrollment document write, so a downstream failure rolls the reservation back too — verified by a transfer-atomicity test where a full, non-waitlisted target batch causes the whole transfer (including the source batch's seat release) to roll back, leaving the source enrollment untouched.

**A real aggregation-casting bug was found by the test suite and fixed before this phase shipped, worth documenting for every future module joining collections by ObjectId.** `EnrollmentModel.aggregate()`'s `$match` stages do **not** auto-cast query values against the schema the way `find()`/`findOne()` do — comparing a plain JS string against an ObjectId-typed field in a `$match` silently matches zero documents rather than erroring. `enrollment.repository.ts#buildPreLookupMatch` (and `findWaitlistForBatch`'s pipeline) now explicitly wrap every `studentId`/`batchId`/`courseId` filter in `new Types.ObjectId(...)` before use — caught by a regression test asserting `GET /enrollments?studentId=...`/`?batchId=...`/`?courseId=...` actually filter, not just that an unfiltered list call returns joined data. Any future aggregation-based repository method filtering by an ObjectId-typed field must do the same explicit cast.

**Waitlist ordering uses a monotonic per-batch sequence counter (`batches.waitlistSequence`), never a live position count.** `batchRepository.nextWaitlistPosition` atomically increments it inside the same transaction as the waitlisted enrollment's creation — the returned value is stored as that enrollment's permanent `waitlistPosition`, never renumbered as earlier entries are promoted or cancelled. The queue is displayed sorted by `waitlistedAt` (ARCHITECTURE.md's usual "server truth over derived math" preference); `waitlistPosition` is historical record-keeping, not a live rank.

**Same-course-different-batch is blocked at the service layer, not a compound unique index** — a plain `{studentId, courseId}` unique index can't express "unless terminal," so `enrollment.repository.ts#findNonTerminalByStudentAndCourse` is the actual duplicate-prevention mechanism; the schema's own `{studentId, batchId}` unique partial index (non-deleted only) is a hard integrity backstop underneath it, not the primary check. A student moving between batches of the same course must go through `POST /:id/transfer` — there is no path to two simultaneous non-terminal enrollments in one course.

**Transfer is one atomic transaction: release source seat (if it held one) → reserve/waitlist the target → create the new enrollment (`source: 'TRANSFER'`) → mark the source `DROPPED` with `transferredToEnrollmentId` set.** Restricted to same-course targets only (cross-course transfer is a `400`, not a business rule to be "smart" about) and to `CONFIRMED`/`ACTIVE`/`SUSPENDED` source statuses. The target status is `ACTIVE` only if both the source enrollment and the target batch were already `ACTIVE`; otherwise `CONFIRMED` (or `WAITLISTED` if the target is full). Course-progress migration across a transfer is an explicitly deferred future requirement (no schema change made for it yet — progress tracking doesn't exist as a module at all today).

**Access entitlement is one pure, reusable function — `enrollment-access.service.ts#hasLearningAccess`.** `ACTIVE` grants access; `SUSPENDED` denies it regardless of any date field (a temporary revocation, not a window edit); `COMPLETED` retains access only while `accessEndsAt` is `null` (lifetime) or still in the future; every other status denies. **`accessStartsAt`/`accessEndsAt` is a deliberate consolidation of the task's own separately-proposed `accessGrantedAt`/`accessRevokedAt` pair into one window** — the PRD never resolves whether course access ends when a batch does or persists afterward (a common coaching-center "lifetime recording access" offer), so a nullable end date (never client-settable, `null` = open) is the future-safe choice the task's own "Recommended Access Policy" section pointed toward. `completeEnrollment` deliberately never sets `accessEndsAt` — this is the concrete implementation of "lifetime access by default unless explicitly revoked."

**Delete-protection guards were added to three *existing* modules, not just the new one — exactly the hook Phase 10A's own doc comment anticipated.** `batch-management.service.ts#softDeleteBatch`, `course-management.service.ts#softDeleteCourse`, and `student-management.service.ts#softDeleteStudent` each gained a targeted, minimal guard (`enrollmentRepository.existsNonTerminalForBatch`/`existsNonTerminalForCourse`/`existsNonTerminalForStudent`, plus `batchRepository.existsNonArchivedForCourse` for the course case) rejecting the delete with `409` rather than orphaning or cascading through enrollment history. None of the three modules were otherwise rewritten.

**Permissions: `enrollments:read`/`enrollments:manage`/`enrollments:export` — a new three-permission catalog entry, not reused from `batches:*`.** `enrollments:manage` covers every lifecycle action including transfer (no separate `enrollments:transfer` — same "consistency over artificial granularity" reasoning §22 gave batches). `ADMIN`/`SUPER_ADMIN` only; `TRAINER`/`STUDENT` get none this phase (a future "My Enrollments" self-service surface is an explicitly separate, self-scoped API, not a grant of this admin permission set). The capacity-reconcile maintenance endpoint (`POST /batches/:id/capacity/reconcile`) is deliberately gated `requireRole('SUPER_ADMIN')` rather than `batches:manage`/`enrollments:manage` — the same stricter-than-module-permission carve-out SECURITY.md §3 already uses for sessions/audit access, appropriate here since a counter correction implies something bypassed the service layer.

**Database indexes are query-driven only.** `enrollments`: unique `enrollmentCode` (partial, non-deleted), unique `{studentId, batchId}` (partial, non-deleted — see above), `{batchId, status}`, `{studentId, status}`, `{studentId, courseId, status}`, `{courseId, status}`, `{createdAt}`, `{batchId, waitlistedAt, waitlistPosition}`. No index was added for `occupiedSeats`/`waitlistSequence` on `batches` — both are point-read/atomic-write fields on an already-indexed document, never filtered or sorted on independently.

## 24. Admin Enrolment Operations & Frontend (Phase 10B Part 2) — **Implemented**

The admin-facing surface over §23's backend: an enrolment list, a capacity-aware create wizard, lifecycle actions, waitlist promotion, batch-to-batch transfer, bulk enrolment, CSV export, and lightweight integration points on Batch Detail and Student Detail. §23's contracts and lifecycle rules were treated as authoritative and not redesigned — every change below is additive. Out of scope, unchanged from §23's own boundary: the Student Learning Portal, self-service enrolment, the Learning Player, progress/attendance/assignments/quizzes, fees/payments, and certificates.

**Three small, additive backend refinements — no concurrency/lifecycle redesign.** (1) `computeEnrollmentAccessState()` (`enrollment-access.service.ts`) derives a single `accessState` enum (`ACTIVE|LIFETIME|NOT_YET_ACTIVE|SUSPENDED|ENDED|NONE`) from status + access window, now exposed on both `AdminEnrollmentDto` and `AdminEnrollmentListItemDto` — the frontend renders this directly and never re-derives entitlement rules from raw status/date fields itself, per the task's own explicit instruction. (2) `AdminBatchListItemDto` (and detail DTO) now exposes real `occupiedSeats`/`availableSeats` (`Math.max(0, maxStudents - occupiedSeats)`), replacing Phase 10A's "configuration only, no derived seat field" boundary now that §23 makes `occupiedSeats` real — no new query, since both fields already lived on the batch document. (3) `updateBatch` gained a guard rejecting `maxStudents < batch.occupiedSeats` with `409` — capacity can never be configured below what's already allocated. No new endpoints were added: the Batch Detail Students tab and Student Detail Enrolment History tab both compose existing endpoints (`GET /enrollments?batchId=`/`?studentId=`, `GET /batches/:id/capacity`, `GET /batches/:id/waitlist`) rather than getting bespoke aggregation endpoints of their own.

**Error handling deliberately does not introduce a business-error-code taxonomy.** The task's spec listed example codes (`CAPACITY_FULL`, `DUPLICATE_ENROLLMENT`, `CROSS_COURSE_TRANSFER`, etc.) but was equally explicit that the frontend must "use actual error codes from Part 1 — do not invent codes that backend doesn't return." §23's services only ever throw `ApiError.conflict(message)`/`ApiError.badRequest(message)`/`ApiError.notFound(message)` with a human-readable `message` and a generic code (`CONFLICT`/`BAD_REQUEST`/`NOT_FOUND`) — there is no granular taxonomy to map. The frontend therefore reuses the existing `getSafeErrorMessage(error)` utility everywhere (already the established pattern across every other feature), which falls through to the backend's own message for any code without a special override. This is a deliberate scope resolution, not an oversight: adding a fake code table mapping non-existent codes to copy would violate the task's own instruction more than it would help.

**Feature structure mirrors every prior admin feature** — `frontend/src/features/enrollments/{types,api,schemas,hooks,components}` plus three pages (`EnrollmentsPage`, `EnrollmentCreatePage`, `EnrollmentDetailPage`, the last two dedicated routes rather than drawers, given the lifecycle/timeline/transfer surface area). No server data is held in Zustand; TanStack Query owns all of it, with query keys `enrollmentsKeys.{list,detail,auditLog}` and `batchesKeys.{capacity,waitlist}` (new on the batches side). Mutations invalidate only the relevant keys — e.g. creating an enrolment invalidates the enrolment list plus the target batch's capacity/waitlist/detail, never the whole cache.

**A new cross-feature invalidation precedent: `features/enrollments` hooks import `batchesKeys` directly.** Every enrolment mutation that can change seat occupancy (create, every lifecycle transition, transfer, bulk enrol/lifecycle) invalidates the affected batch's `capacity`/`waitlist`/`detail`/`all` keys alongside the enrolment's own — a superset invalidation (e.g. `activate`/`suspend`/`resume` don't actually change seat count, but are invalidated the same way) chosen over tracking exactly which action changes seats, since the correctness cost of under-invalidating stale capacity is worse than one extra cache refetch. This mirrors how selector components already read cross-feature (`StudentSelectorField` reading `features/students`), now extended to cross-feature *invalidation*.

**Lifecycle actions are status-gated, never a generic dropdown** — `EnrollmentDetailPage` and the enrolments table's row menu each compute the valid action set from the enrolment's current status (`PENDING`→Confirm/Cancel, `WAITLISTED`→Promote/Cancel, `CONFIRMED`→Activate/Cancel/Transfer, `ACTIVE`→Suspend/Complete/Drop/Transfer, `SUSPENDED`→Resume/Drop/Transfer, `COMPLETED`/`CANCELLED`/`DROPPED`→none), matching §23's `ALLOWED_TRANSITIONS` table without duplicating it — the backend remains the sole authority and re-validates every transition regardless of what the UI offers.

**Transfer UX restricts the target-batch selector client-side to the same course** (`BatchSelectorField courseId={enrollment.courseId}`) purely as a UX guardrail — §23's transfer service re-verifies the same-course rule server-side regardless, so a stale or bypassed client never produces a cross-course transfer. The batches list/search endpoint gained a `courseId` query filter to support this (previously unfiltered by course), used by both the transfer dialog and the create wizard.

**Bulk enrolment surfaces an estimate, never a guaranteed outcome.** The review step shows "approximately N may be confirmed, M may be waitlisted" computed from the currently-displayed `availableSeats` — explicitly labeled as an estimate because §23's capacity engine decides the real, transaction-safe result per student at submit time; the result screen shows actual succeeded/waitlisted/failed counts with per-student failure reasons, and a partial result (some failed) is rendered as a normal, expected outcome, never a top-level error.

**Concurrent-capacity UX treats a stale capacity number as expected, not a bug** — capacity shown during the create/bulk-enrol flow can be seconds stale by submit time (another admin enrolling concurrently); rather than an error state, the UI's copy for a waitlist/capacity outcome is written to read as normal information ("Batch full — student will be waitlisted"), matching how the batch-level capacity race is already handled server-side (§23's atomic `findOneAndUpdate` reservation).

**Testing:** 8 new focused backend tests (`enrollment.part2-refinements.test.ts`) cover only the three refinements above — no re-test of §23's lifecycle/capacity/transfer coverage. ~30 new frontend tests span the create wizard (confirmed vs. waitlisted outcomes, duplicate-enrolment error), the enrolments list (search, promote, cancel, bulk-suspend partial-failure), the detail page (every lifecycle transition, transfer, cross-course-target exclusion, lazy-loaded audit tab), the Batch Detail Students tab, and the Student Detail Enrolment History tab — plus a route-config test for the three new routes (registered in the shared `/admin` role gate, no additional per-route check, matching every other admin feature). Two pre-existing Phase 10A tests (`BatchesPage`'s "Max N, never a fraction" assertion and `useBatchesList`'s "never includes a seat-count field" assertion) were updated in place — both encoded Phase 10A's deliberate "capacity is configuration only" boundary, which this phase intentionally and explicitly supersedes now that `occupiedSeats` is real.

## 25. Student Portal Foundation (Phase 11A) — **Implemented**

The first authenticated, self-scoped **STUDENT**-facing surface — every prior module (§14–§24) is admin-operated. This introduces a genuinely new architectural pattern this codebase hadn't needed before: a role-scoped API namespace with no permission-catalog entries behind it at all.

**A new `requireRole`-only gating pattern, not `requirePermission`.** `STUDENT` carries an empty permission array by design (`scripts/seed-roles.ts`) — there is nothing in the permission catalog for a self-scoped route to check, since "read your own data" isn't a grantable/revocable admin permission. `src/routes/student-portal.routes.ts` gates its entire router on `requireAuth, requireRole('STUDENT')` alone, the same shape `GET /auth/me` already used for exactly one endpoint — this is the first time the pattern is used for a whole module. Every handler resolves the acting student via a single `resolveStudent(userId)` helper (`studentRepository.findByUserId(req.user.id)`) — self-scoped routes never accept `studentId` from `params`/`query`/`body`, so there is no `studentId` to spoof.

**Student-safe DTOs are a deliberate second, narrower mapping layer — never the admin DTOs reused as-is.** `student-portal-dto.ts` defines its own `StudentEnrollmentDto`/`StudentCourseDetailDto`/`StudentModuleDto`/`StudentLessonDto`/`StudentResourceDto`, each hand-picking fields rather than importing `curriculum-dto.ts`'s admin-facing `ModuleDto`/`LessonDto`. Concretely: the student curriculum view omits `status` entirely (student-visible items are always already filtered to `PUBLISHED`, so the field would only ever leak the DRAFT/ARCHIVED *concept*, never a useful value), and lesson-resource responses never carry a raw Cloudinary `publicId` — only `generateSignedDeliveryUrl()` (reused unchanged from §21's media-delivery service) does, behind a dedicated `GET /student/resources/:resourceId/delivery-url` endpoint that re-verifies entitlement on every call rather than embedding a long-lived URL in the list response.

**Course-overview access is two separate checks, not one — this is the one place this phase's design deliberately diverges from a blanket "entitled or 403."** `hasLearningAccess()` (§23's rule, reused unchanged) gates only *what content is returned* (published curriculum, resources) — it never gates *whether the course page itself loads*. A student with a `SUSPENDED` enrollment still gets `200` with the course header and an honest "access is currently paused" state; only a student with **no enrollment at all** for that course gets `404`. This lets the frontend render a graceful paused/ended state instead of an opaque permission error, without weakening the actual entitlement boundary (curriculum/resources still check `hasLearningAccess()` independently, every time, server-side).

**A new pure derivation, not a new persisted concept: `schedule-occurrence.util.ts`.** The Schedule tab needs concrete upcoming class dates, but `batches.weeklySchedule` is a recurring day+time template, not a calendar. `generateUpcomingOccurrences()` projects template → concrete dates at read time (`Intl.DateTimeFormat` for timezone-correct day-of-week/date-key resolution, no new date library), respecting `calendarExceptions` and `startDate`/`endDate`. Nothing is written — this is intentionally the same category of decision as §10B's "derived `accessState`," a computed view over existing data, not a new collection.

**Backend additions were kept additive to existing repositories, not a new data-access layer.** `batchRepository.findByIds`, `courseRepository.findByIds`, `enrollmentRepository.findAllByStudent`/`findLatestByStudentAndCourse`, and `lessonResourceRepository.findActiveByCourse`/`findByIdAcrossLessons` were added alongside each repository's existing methods — chosen specifically to avoid the N+1 pattern a naive "one query per enrollment" implementation would produce; the dashboard/enrollments/courses/schedule views all share one `loadEnrollmentContext(studentId)` loader (1 enrollments query + 1 batched course fetch + 1 batched batch fetch, regardless of enrollment count). `calculateProfileCompletion` (student-management.service.ts) and `phoneSchema`/`addressSchema`/`emergencyContactSchema` (student.validator.ts) were changed from module-private to `export`ed — additive, zero behavior change — so the self-service profile update reuses the exact same completion formula and field validation the admin flow already uses, rather than a parallel copy.

**Frontend: a distinct `StudentShell`, not `DashboardLayout` reused with different nav data.** Admin/Trainer/Student had shared one generic `AppShell` (sidebar + header + mobile drawer) differentiated only by which `NavSection[]` was passed in. The task's design spec explicitly called for a more spacious, learner-focused feel and a mobile bottom nav with no admin/trainer equivalent — `shared/components/layout/student-shell.tsx` composes the same underlying `Sidebar`/`Header`/`MobileNavDrawer`/`Footer` primitives (those were already generic, not admin-styled) plus a new `StudentBottomNav` (four primary actions — Home/Courses/Schedule/Profile — fixed, mobile-only, `lg:hidden`), rather than forking a second full design system. `student-dashboard-layout.tsx` now points at `StudentShell` instead of `DashboardLayout`; Admin's and Trainer's layouts are untouched.

**Testing:** 8 new focused backend tests (`student-portal.security.test.ts`) — self-scoping/IDOR (own-vs-other-student enrollment access), role rejection (`ADMIN` on a `STUDENT`-only router), entitlement-gated curriculum (`ACTIVE` sees it, `SUSPENDED` doesn't but still gets `200`), published-only filtering (a `DRAFT` module/lesson never appears even with `ACTIVE` access), never-enrolled → `404`, and resource-delivery-url entitlement denial. 10 new frontend tests (`StudentPortal.test.tsx`) cover the dashboard (populated + honest empty state), My Courses, course overview (entitled + not-found), schedule, resources (list + signed-URL fetch on click), student nav (student-only routes, never admin/trainer), the new bottom nav, and the profile page. Both suites run standalone (`mongodb-memory-server` / MSW) — no change to either existing test suite was needed.

**Explicitly out of scope, unchanged:** the Learning Player itself (video/document lesson consumption — §8/Phase 8's original objective), lesson progress/watch-position tracking, attendance, live classes, assignments, quizzes, examinations, payments, and certificates. `StudentCourseOverviewPage`'s lesson rows are display-only — clicking one goes nowhere yet; that's the Learning Player phase's own starting point, deliberately not half-built here.

## 26. Learning Player + Progress Tracking (Phase 11B) — **Implemented**

Course → module → lesson consumption, lesson/course progress, prerequisite enforcement, and resume-learning — built directly on §25's foundation (self-scoped `STUDENT` namespace, `hasLearningAccess`, published-only curriculum filtering), not a redesign of it.

**One central access gate, not one per controller.** `student-lesson-access.service.ts` exports `resolveStudentLessonAccess()` (never throws for a suspended/locked lesson — returns a resolved context with `hasAccess`/`locked`/`lockReason` flags, so the lesson-detail view can render a graceful state) and `assertStudentLessonAccess()` (the hard gate — throws `403` for either condition, used before any protected content — media URL, progress write — is ever issued). Both resolve, in order: student exists → course exists → *some* enrollment exists for this course (else `404`, matching §25's no-existence-disclosure rule) → lesson exists/`PUBLISHED`/belongs to this course (else `404`) → its module is also `PUBLISHED` (else `404` — a published lesson under a draft/archived module stays hidden, same rule §25's course-overview curriculum filter already established) → prerequisite lock state, computed from this student's `COMPLETED` progress rows in the same course. This is the single place that chain is implemented; no other file re-derives it.

**A new shared identity-resolution util, extracted on its second consumer.** `resolveStudent(userId)` existed only inside `student-portal.service.ts` in §25; this phase needed the identical three lines in `student-lesson-access.service.ts`, so it moved out to `student-identity.util.ts#resolveStudentForUser` — both services now import it, zero behavior change, no duplicated logic (CLAUDE.md's own standing rule).

**Course-completion percentage is computed fresh every time, from `{lessons, progressRows}` — never stored.** `utils/course-progress.util.ts#computeCourseProgress()` is a pure function: `completedMandatoryLessons ÷ mandatoryLessons` (falling back to *all* published lessons if none are marked mandatory, the task's own documented fallback), draft/archived/deleted lessons excluded before the function ever sees them. The same function backs three different views without three different implementations: the dedicated `GET .../courses/:courseId/progress` endpoint, the enriched course-overview curriculum (each lesson gets a `progressStatus`/`locked`/`lockReason`), and the My Courses/Dashboard progress bars (`computeCourseProgressForStudent`, exported from `student-learning.service.ts` and imported by `student-portal.service.ts` — a deliberate, bounded parallel `Promise.all` across a student's own small enrollment count, documented in code as a conscious choice, not a missed N+1).

**Video completion never trusts the client for duration — only for position, and even that is clamped.** `lessons.videoAsset.durationSeconds` (Cloudinary-verified at upload time, §21) is the sole source of truth for "has this student watched 90%"; the client only ever reports `positionSeconds`, itself Zod-bounded (`0`–`86400`) and further clamped server-side to `duration + 5s` tolerance before any threshold comparison. No `videoDurationSeconds` field exists on `lesson_progress` at all — storing a second copy of a value that already lives on `lessons` would just be a value that can drift from the source of truth, for no benefit (see the model's own doc comment).

**Progress writes are one atomic upsert, keyed on the same unique index that prevents duplicates.** `lesson-progress.repository.ts#upsertProgress` is the sole write path — a `findOneAndUpdate` upsert on `{studentId, lessonId}` (already unique from §25... rather, from this phase's evolution of the Phase 1 scaffold, see DATABASE.md), using `$max` for `videoPositionSeconds` (a late/out-of-order heartbeat can never regress a further-along position) and `$setOnInsert` for `startedAt` (set once, on first-ever write, never overwritten). "Mark complete" called twice is genuinely idempotent: the second call reads the existing `COMPLETED` row and returns it unchanged, never re-touching `completedAt`.

**Frontend: a deliberately separate full-page route, not nested inside `StudentShell`.** `/student/courses/:courseId/learn(/:lessonId)` is mounted as a sibling to (not a child of) the `student-dashboard-layout` route tree in `app/router.tsx` — the Learning Player renders its own header/curriculum-sidebar/mobile-drawer and needs to stay distraction-free (task's own instruction), not wrapped in the portal's sidebar/header/bottom-nav chrome on top of its own. `/learn` (no lesson id) is a dedicated `StudentLearningRedirectPage` that resolves real resume-learning server-side (`lastAccessedLessonId` ?? `firstLessonId`, both backend-computed) and issues a client-side `<Navigate>` — never a guessed lesson id.

**Frontend: native `<video>`, not a player library.** Play/pause/seek/volume/fullscreen/rate all come from the browser's own controls (task's own instruction: no DRM, no heavy dependency unless genuinely required). Position reporting is throttled client-side to ~12s while playing, plus explicit sends on pause/seeked/unmount — never a write per `timeupdate` tick, never relying solely on `beforeunload`.

**Cross-feature query invalidation, same precedent §24 set for `enrollments`→`batches`.** `useMarkLessonComplete`/`useUpdateLessonProgress` (only on a `COMPLETED` transition) invalidate `learningPlayerKeys` *and* `studentPortalKeys.course/dashboard/enrollments` — completing a lesson can change curriculum lock state, course progress, and every progress bar showing that course, so every affected view is invalidated together rather than tracking exactly which one changed.

**Testing:** 12 new focused backend tests (`student-learning.security.test.ts`) — entitled-student access, never-enrolled `404`, suspended-student media `403`, draft-lesson `404`, prerequisite-locked (no content revealed) and prerequisite-completed-unlocks, idempotent manual complete, course-percentage calculation, out-of-range position rejection, 90%-threshold video auto-completion, cross-student progress isolation, and media-URL entitlement denial — plus the two `createLoggedInStudent()`-calling-twice-per-test fixture safety fix shared back into §25's own test file. 12 new frontend tests (`StudentLearningPlayer.test.tsx`) cover the player header/progress, curriculum active-lesson state, locked-lesson rendering, text-lesson mark-complete, video-lesson signed-URL wiring, Previous/Next links, the mobile curriculum drawer, an unresolvable-lesson error state, and the document/external-link lesson views in isolation — plus 2 tests confirming My Courses and the Dashboard route "Continue/Start Learning" into the real resume endpoint. One pre-existing §25 test (`StudentPortal.test.tsx`'s dashboard CTA-label assertion) was updated in place to accept "Start course" (a fresh enrollment has no `lastAccessedLessonId` yet) as well as "Continue course" — the same "update a stale assertion, don't re-test the earlier phase's own coverage" precedent §24 set.

**Explicitly out of scope, unchanged:** quizzes, assignments, live classes, attendance, payments, certificates, gamification (points/streaks). Enrollment lifecycle status is never auto-mutated on course completion — `courseProgress.isComplete` is a read-only derived signal this phase, deliberately not wired into any enrollment-status transition, avoiding a hidden side effect the task's own instruction explicitly warned against.

## 27. Live Classes + Attendance (Phase 12) — **Implemented**

Evolves `batches.weeklySchedule` (a recurring *template*, §22) into real, individually-manageable class-session records, adds a roster-based attendance workflow on top of each session, and wires both into the admin/trainer/student surfaces built in §22–§26 — without duplicating any of that prior work's business logic.

**Domain boundary, stated once and held throughout.** Weekly timetable (template) → generated/scheduled `live_classes` session (concrete occurrence) → `attendance` records (per-session, per-student outcome). A `live_classes` document is never itself a template, and a timetable slot never has attendance directly — attendance always hangs off a real session.

**Session identity, mirroring every other module's ID convention.** `live-class-id.service.ts#generateLiveClassSessionCode()` — the same atomic `counters`-collection `findOneAndUpdate` pattern as `batchCode`/`courseCode`/`enrollmentCode` — produces `DM-CLS-{year}-{6-digit sequence}`, unique, immutable, server-generated only.

**Two ways to create a session, one underlying create path.** Manual (`POST /live-classes`, one session, admin picks every field) and generate-from-timetable (`POST /live-classes/generate/preview` then `/generate`, many sessions at once, projected from `weeklySchedule`) both funnel through `live-class.service.ts`'s validation (batch-range, trainer-conflict) before persisting. Generation reuses `generateUpcomingOccurrences()` **unchanged** — the exact same function Phase 11A built for the student Schedule tab's derived-occurrence preview — treating an admin-supplied `[startDate, endDate]` range as `{from: startDate, daysAhead}`. Duplicate-generation prevention is a partial unique index (`{batchId, scheduledDate, startDateTime}`, scoped to `source: TIMETABLE_GENERATED`) rather than an application-level check, so it holds even under concurrent requests; a manually-created session can still intentionally coexist on the same slot since the index doesn't apply to `source: MANUAL`.

**Timezone-safe UTC construction, no library dependency.** `zoned-datetime.util.ts#zonedWallTimeToUtc()` uses the same `Intl.DateTimeFormat` "round-trip" technique as `batches`' own `isValidTimeZone()` precedent: treat the wall-clock digits as a UTC guess, format that guess back out *in the target timezone*, and the difference between guess and re-read value is the zone's real UTC offset at that instant — correct across DST transitions, no `date-fns-tz`/`luxon` added. The identical technique is duplicated (deliberately, not extracted — it's 15 lines and the two call sites, backend session-generation and the frontend's manual-create datetime-local input, don't share a runtime) into the frontend as `features/live-classes/utils/zoned-datetime.ts`, so an admin's manually-picked date/time is interpreted in the *session's* timezone, never the admin's browser timezone.

**Named-transition lifecycle, never a generic status PATCH.** `live-class-lifecycle.util.ts#ALLOWED_TRANSITIONS`: `DRAFT → {SCHEDULED, CANCELLED}`, `SCHEDULED → {LIVE, COMPLETED, CANCELLED}`, `LIVE → {COMPLETED, CANCELLED}`; `COMPLETED`/`CANCELLED` are terminal. Each transition is its own endpoint (`/schedule`, `/start`, `/complete`, `/cancel`) with its own audit action string — mirrors the `batches` lifecycle pattern (§22) exactly, one lookup table as the single source of truth for what's legal, checked before every mutation.

**Trainer conflicts, checked the same way batches already check them.** `findOverlappingForTrainers()` is an indexed interval-overlap query (`existing.start < new.end AND existing.end > new.start`) against other `SCHEDULED`/`LIVE` sessions for the same trainer(s) — never a JS-side scan across all sessions. Both this and the batch-date-range check share one rule: blocked by default, bypassable only with an explicit `overrideReason` (required, audited) — no silent override, no silent block.

**Student join security is a dedicated, time-windowed endpoint — never a field on a list DTO.** `StudentLiveClassDto` (the `GET /student/live-classes` list shape) carries no `joinUrl`/`hostUrl` at all. `GET /student/live-classes/:id/join` is the only place a join URL is ever returned, and only after: student authenticated → an access-granting enrollment exists for *this exact* course+batch pair (not just any batch of the course) → session status is student-visible (`SCHEDULED`/`LIVE`) → join window open (15 minutes before `startDateTime` through `endDateTime` + 15-minute grace, both constants in `student-live-class.service.ts`). `hostUrl` is never present anywhere in the student-facing DTO or join-details response — only the admin/trainer `AdminLiveClassDto` carries it, since a trainer, like an admin, is an "operator" of the session.

**Attendance defaults to nothing, not everyone-absent.** `attendance` documents are created only when explicitly marked (`PATCH .../attendance`, bulk upsert) or on finalize (`POST .../attendance/finalize`, which back-fills `ABSENT`/`source: SYSTEM` for every still-unmarked *eligible* student). A roster row with no matching document renders as the derived `UNMARKED` state — never a fabricated stored `ABSENT`. Eligibility is enrollment status `ACTIVE`/`CONFIRMED` for the session's batch only (documented rule, `attendance.service.ts`): `SUSPENDED` is deliberately excluded (a paused student shouldn't be expected to attend), `WAITLISTED`/`CANCELLED`/`DROPPED`/`PENDING`/`COMPLETED` never eligible.

**Attendance lifecycle lives on the session, not a separate model.** `attendanceStatus: OPEN | FINALIZED` plus `attendanceFinalizedAt`/`attendanceFinalizedBy` are fields on `live_classes` (§DATABASE.md 3.5) — a session's attendance state is inherently 1:1 with the session, so a standalone `attendance_sessions` collection would be a join for no benefit. Once `FINALIZED`, `bulkMarkAttendance` rejects further writes (`409`) until an `ADMIN`/`SUPER_ADMIN` explicitly reopens it (reason required, audited) — a `TRAINER` can mark attendance for a session they own but can never finalize or reopen (matches the routes: `/trainer/live-classes/:id/attendance` only exposes `GET`/`PATCH`, never `/finalize`/`/reopen`).

**Attendance percentage, one formula, computed fresh, never stored.** `getStudentAttendanceSummary()`: `(present + late) ÷ (finalizedSessions − excused)`, rounded; `excused` is excluded from the denominator (doesn't count for or against); future/unfinalized sessions never enter the calculation at all (`findFinalizedForCourse` only returns `attendanceStatus: FINALIZED` sessions). The exact same function backs three views without three implementations: the student's own `/student/attendance`, the admin cross-session report, and (indirectly, same shared data) the per-course summary — no parallel percentage logic anywhere.

**Bulk operations, not N+1, for both the write and read side.** `attendanceRepository.bulkUpsert()` is one `AttendanceModel.bulkWrite()` call for an entire roster's worth of marks, each op an atomic upsert keyed on the `{sessionId, studentId}` unique index — never one HTTP/DB round trip per student. Roster/report building batches distinct student/session/course/batch IDs into single `findByIds()` calls and joins in memory (the same `loadEnrollmentContext`-style pattern §25/§26 established), never a query per row.

**Schedule precedence: a real session always wins over the derived timetable occurrence for the same slot.** `student-portal.service.ts#buildUpcomingSchedule()` (§25's dashboard/schedule widget) now fetches real sessions for the student's accessible batches first, builds a `{batchId}|{dateKeyInBatchTimezone}` suppression set from every real session in the window (including `CANCELLED` — a cancelled date must never fall back to a phantom derived slot that won't happen), then only adds `generateUpcomingOccurrences()`'s derived rows for dates *not* in that set. `CANCELLED` sessions suppress but are never themselves re-added to this lightweight widget (it has no status field to show "cancelled" — the dedicated `/student/live-classes` page is where that full detail lives, including the cancelled state itself, per its own `StudentLiveClassDto.status` field).

**Frontend: batch-scoped creation, not a floating create form.** `CreateLiveClassDialog`/`GenerateLiveClassesDialog` both require a known `batchId` and are only ever opened from the Batch Detail page's new "Live Classes" tab (`BatchLiveClassesTab`, replacing the former placeholder in `FutureModuleCards`) — a live class is never created "unattached" to a batch, so there's no standalone batch-picker combobox to build/maintain. The standalone `/admin/live-classes` list page is read/filter/manage only (search, status filter, per-row "Manage" link into `LiveClassDetailPage`), matching the same "list page is a flat cross-batch view, mutation happens in context" shape enrollments (§24) already established.

**Frontend: one shared attendance panel, not two parallel implementations.** `AttendanceRosterPanel` (roster + mark + finalize + reopen) is rendered by both the admin session-detail page (`canFinalize`) and the trainer self-scoped attendance page (`canFinalize={false}`, `basePath="/trainer/live-classes"`) — same component, same mutation hooks, the only difference is a boolean prop and which base path the underlying API calls hit. No client-side permission-hiding was added for the admin lifecycle/create/generate actions (`Can`/`usePermission` exist in the codebase but are unused everywhere else too) — matching the established precedent that frontend role/permission checks are a UX convenience only (SECURITY.md §3), never the enforcement boundary; the backend's `requirePermission`/ownership checks are authoritative.

**Testing:** 23 new focused backend tests across four files — `live-class.lifecycle.test.ts` (create/sessionCode format, batch-range override, trainer-conflict override, generate-and-skip-duplicate, calendar-exception exclusion, full DRAFT→SCHEDULED→LIVE→COMPLETED walk with an out-of-order-jump rejection, cancel-then-cancel-again rejection, manage-permission gate), `attendance.marking.test.ts` (eligible-only UNMARKED roster, bulk-mark with ineligible-student rejection, finalize-auto-absents-then-blocks-edits-then-reopen-restores as one flow, percentage-formula calculation, CSV export header, manage-permission gate), `student-live-class.security.test.ts` (join-window-closed 403, join-window-open 200 with no `hostUrl` leak, cross-batch-access 404, cancelled-session-visible-with-status, and the schedule-precedence suppression test itself), `trainer-live-class.ownership.test.ts` (view/start-complete/mark-attendance all correctly 404 for a non-owning trainer). 12 new focused frontend tests across seven files (status-badge WCAG-label checks ×2, `zonedWallTimeToUtc` DST-correctness ×3, admin list + search + Manage-link wiring, lifecycle transition + attendance mark/save/finalize on the detail page, student join-CTA/cancelled-state/DRAFT-hidden, student attendance-percentage display, trainer self-scoped list + complete action, trainer attendance mark with no Finalize button present, and one addition to the existing `BatchDetailPage.test.tsx` for the new tab) plus the full 352-test pre-existing suite re-run clean.

**Explicitly out of scope, unchanged:** assignments, quizzes, examinations, payments, certificates, placement, advanced analytics, real managed-video-conferencing provider credentials (§9), provider-webhook auto-attendance, a full Notifications module (hooks/event points only — session scheduled/cancelled/starting-soon, attendance finalized — no actual email/WhatsApp dispatch).

## 28. Assignments + Student Submissions + Trainer Grading (Phase 13) — **Implemented**

Builds the full academic assignment workflow — admin/trainer authoring, batch/course targeting, publish, student submission (text/file/link), trainer grading with feedback, and return-for-resubmission — on top of the auth/courses/batches/enrolments/Cloudinary infrastructure built in prior phases, without duplicating any of it.

**One document per attempt, not one document per student-per-assignment.** `assignment_submissions` (`assignment-submission.model.ts`) creates a brand-new document — incremented `attemptNumber` — every time a student submits or resubmits; grading history and feedback are never overwritten by a later attempt. `{assignmentId, studentId, attemptNumber}` is a unique index; the "current" attempt for a student is simply the highest `attemptNumber`.

**Four submission statuses, not five — "late" is a boolean, not a status.** `ASSIGNMENT_SUBMISSION_STATUSES = ['DRAFT', 'SUBMITTED', 'RETURNED', 'GRADED']`. The spec's own two candidate status lists disagreed on whether "late" belonged in the enum; treating `submittedLate` as an orthogonal boolean (set once at submit time by comparing against `dueDateTime`/`lateUntil`) avoids a combinatorial status explosion (`SUBMITTED_LATE`, `GRADED_LATE`, …) — the same kind of resolution Phase 12 applied to attendance eligibility statuses.

**Named-transition lifecycle, mirroring `live-class-lifecycle.util.ts` exactly.** `assignment-lifecycle.util.ts#ALLOWED_TRANSITIONS`: `DRAFT → {PUBLISHED, CANCELLED}`, `PUBLISHED → {CLOSED, CANCELLED}`, `CLOSED → {ARCHIVED}`; `CANCELLED`/`ARCHIVED` are terminal. `CANCELLED` is only reachable from `DRAFT`/`PUBLISHED`, never from `CLOSED`/`ARCHIVED`. Each transition is its own endpoint (`/publish`, `/close`, `/cancel`, `/archive`) with its own audit action, never a generic status `PATCH`.

**Targeting: one course, one-or-more batches of that same course — never cross-course.** An assignment's `courseId` is fixed at creation; every id in `batchIds` must belong to that exact course (`assignment.service.ts#assertReadyToPublish()` validates this, plus non-empty batches, before allowing `DRAFT → PUBLISHED`), the same "structured blockers, not a single opaque error" pattern batches/live-classes use for their own readiness gates.

**Late submission is a window, not a hard cutoff.** `dueDateTime` plus an optional `allowLateSubmission` + `lateUntil` pair: before `dueDateTime` is on-time, between `dueDateTime` and `lateUntil` (only reachable if `allowLateSubmission`) is late-but-accepted (`submittedLate: true`), and past `lateUntil` (or past `dueDateTime` with late submission disabled) the submission window is closed — `assertWithinSubmissionWindow()` is the single function every submit/save-draft path checks, never duplicated per submission type.

**Attachments and submission files addressed by Mongo `_id`, never by raw Cloudinary `publicId`.** Cloudinary `publicId`s contain `/` characters that can't round-trip through an Express path param, so the shared `assignmentAttachmentSchema` (`models/shared/assignment-attachment.schema.ts`) keeps its own subdocument `_id` — routes/DTOs address one specific file as `.../attachments/:attachmentId` or `.../files/:fileId`, and the DTO layer never exposes the raw `publicId` to any client. Upload reuses the existing two-step signed-upload flow unchanged: `cloudinary-upload.service.ts` mints a signature, the browser (`uploadDirectToCloudinary`, reused unmodified from the Phase 9C/12 course-content uploader) pushes the file straight to Cloudinary, then the server verifies and confirms via `cloudinary-upload.service.ts#verifyUpload()` before the attachment/file record is persisted. Delivery URLs mint through the same `media-delivery.service.ts` signed-URL minting Phase 9C/12 built.

**Resubmission never destroys grading history.** `maxAttempts` bounds how many attempts a student may create; each new attempt is its own `assignment_submissions` document, so a trainer's marks/feedback on attempt 1 remain queryable even after attempt 2 is graded. "Return for Resubmission" (`RETURNED` status) lets a trainer send a graded-or-submitted attempt back for another try without editing the original attempt's own record — `returnSubmission()` creates the space for a new attempt rather than mutating the old one.

**Grade computed fresh, never stored.** `assignment-grade.util.ts#computeGrade(marksAwarded, maxMarks, passingMarks)` returns `{percentage, passStatus}` computed at DTO-mapping time — the same "never store what's computable" rule Phase 12 applied to attendance percentage. `marksAwarded` is bounds-checked server-side against the assignment's own `maxMarks` on every grade call (`0 ≤ marksAwarded ≤ maxMarks`), regardless of what the client sends.

**One grading service, shared by two routers after two separate authorization checks — never a parallel grading code path.** `assignment-submission.service.ts` (and its controller) backs both the admin `/assignments/:id/submissions/:submissionId/...` routes and the trainer `/trainer/assignments/:id/submissions/:submissionId/...` routes. `canOverrideResubmission(actor)` — true for `ADMIN`/`SUPER_ADMIN`, false for `TRAINER` — is the one behavioral fork inside the shared function (only an admin can return a submission on an assignment where `allowResubmission: false`); everything else is identical logic reached by two different authorization gates.

**Trainer ownership is derived from batch assignment, not stored on the assignment itself.** Assignments target batches, not trainers directly, so `trainer-assignment.service.ts#requireOwnedAssignment()` intersects the assignment's `batchIds` against `batchRepository.findIdsForTrainer()` (a new, deliberately un-status-filtered read — unlike `findOperationalBatchesForTrainer`, since grading legitimately continues after a batch's schedule completes) to decide whether the acting trainer is `primaryTrainerId`/`assistantTrainerIds` on any targeted batch. `requireSubmissionUnderAssignment()` additionally cross-checks that a `:submissionId` genuinely belongs to its `:id` (assignment) URL segment — both ownership and route-nesting failures 404, never 403, matching the codebase's IDOR-hardening convention (SECURITY.md).

**Aggregation, not N+1, for "latest attempt per student" and per-assignment submission counts.** `assignment-submission.repository.ts` uses one `$match → $sort → $group → $replaceRoot` pipeline for the admin/trainer grading-list view (one document per student, their latest attempt) rather than fetching every attempt and reducing in JS.

**Two intentionally different attempt-history functions for two different audiences.** The admin/trainer `getAttemptHistory()` excludes `DRAFT` attempts (a trainer shouldn't see an in-progress unsent draft as "history"). The student's own `getMyAttemptHistory()` deliberately includes their current `DRAFT` (sorting first, being the highest `attemptNumber`) — without it, a student's own in-progress draft content would be unfetchable after any page reload. This is a real, documented divergence, not a bug: the two functions are never shared.

**Permissions: four, not two — grading is a distinct, separately-grantable action from editing.** `assignments:read` / `assignments:manage` / `assignments:grade` / `assignments:export`, chosen for precedent-consistency with `courses:publish` (a distinct significant action gets its own permission) rather than a simpler 2-permission scheme that would conflate "edit an assignment" with "grade a student's work" — two very different blast radii. `ADMIN`/`SUPER_ADMIN` are granted all four in `seed-roles.ts`; `TRAINER` reaches grading endpoints via ownership (§ above), not a granted permission.

**CSV export never leaks private file URLs.** `exportSubmissionsCsv()` columns are Student ID / Name / Batch / Assignment / Attempt / Submitted At / Late / Marks / Percentage / Grade Status only — no signed Cloudinary URLs, matching the same CSV-security posture as every prior phase's export endpoints.

**Frontend: presentational grading UI shared, not duplicated, across admin and trainer.** `SubmissionsPanel` and `GradingModal` (`features/assignments/components/`) accept data and callback props rather than owning their own data-fetching — the admin and trainer detail pages each wire their own role-appropriate hooks/endpoints around the identical UI, the same "one shared component, two host pages" shape §27 established for `AttendanceRosterPanel`.

**Frontend: numeric form fields stay strings until the API call, never `z.coerce.number()`.** `AssignmentForm.tsx`'s numeric fields (`maxFiles`, `maxFileSizeMb`, `maxMarks`, `passingMarks`, `maxAttempts`) are plain regex-validated strings in the Zod schema, converted with `Number(...)` only when building the mutation payload — `z.coerce.number()` breaks `useForm<T>()`'s `Control<T>` inference because Zod's input type (pre-coercion) diverges from its output type, per the documented convention in `features/students/schemas/student.schemas.ts`. Relatedly, `FormValues` is declared via `z.input<typeof formSchema>` (not `z.infer`/`z.output`), matching `features/batches/schemas/batch.schemas.ts`'s established pattern — required because the schema's `.default()`-valued checkbox fields otherwise produce a `Resolver<>` type mismatch against `useForm`.

**Quality gates:** backend `tsc --noEmit` / `eslint` / `prettier --check` / build all clean; frontend `tsc -b` / `eslint --max-warnings=0` / `prettier --check` / `vite build` all clean (frontend build requires Node ≥20.19 per `package.json#engines` — Vite's rolldown dependency imports `node:util#styleText`, unavailable on Node 18). **No large automated test suite was built this phase** (explicit phase instruction) — see the Testing Backlog below for what dedicated coverage should land in a later phase.

**Explicitly out of scope, unchanged:** quizzes, examinations, certificates, payments, placement, advanced analytics, a full Notifications module (hooks/event points only — `assignment.published` / `due_soon` / `submitted` / `returned` / `graded` — no actual email/WhatsApp dispatch).

## 29. Question Bank + Quizzes/Examinations Assessment Engine (Phase 14) — **Implemented**

One unified assessment engine for both quizzes and examinations, plus an independent, reusable question bank — replacing the Phase 1 `quizzes`/`quiz_attempts`/`examinations`/`examination_results` scaffold entirely (zero real consumers verified before touching it, same precedent every prior phase established).

**One engine, not two — `assessmentType` is configuration, never a service-layer fork.** `assessments` (`assessmentType: QUIZ | EXAM`) is a single collection/model/service/route-set; a quiz and an exam are the same document shape, differing only in the *values* an admin sets (e.g. a quiz typically `maxAttempts: 3`, an exam `maxAttempts: 1`). There is no `quiz.service.ts` vs `examination.service.ts` split anywhere in the stack.

**Questions are bank-owned, never assessment-owned.** `questions` is its own collection, referenced by `assessments.sections[].questionIds` — never embedded, never duplicated per assessment. Archiving or editing a question never cascades into an assessment that already references it, because every attempt keeps its own immutable snapshot (below) independent of the bank question's current state — this is precisely what makes it safe to let a question be edited even after it's been used in a live attempt, unlike `assignments`, which locks editing to `DRAFT` only.

**Six explicit assessment statuses, not seven — no stored `OPEN`.** `DRAFT → PUBLISHED → CLOSED → RESULT_PUBLISHED → ARCHIVED`, plus a `CANCELLED` branch from `DRAFT`/`PUBLISHED` only. The task's own spec floated a seventh `OPEN` status but also supplied its own resolution ("lifecycle remains explicit for major states + availability computed from openAt/closeAt") — `isAssessmentAcceptingAttempts()` is a pure function of `status === 'PUBLISHED'` plus the current time against `openAt`/`closeAt`, never a second stored source of truth. Mirrors how `assignment_submissions` resolved an identical spec self-contradiction (§28) by making "late" a boolean instead of a status value.

**Four attempt statuses, not six — `SUBMITTED`/`AUTO_SUBMITTED` are never resting states.** `IN_PROGRESS → {PENDING_MANUAL_GRADING, GRADED}`, plus a reserved `INVALIDATED` (schema-forward-compatible only, no write path this phase — same "reserved enum value" discipline `live_classes.provider`'s unused values established). Objective scoring is always synchronous (a cheap reduction over an already-loaded snapshot, never a background job), so the moment a student submits — manually or via server-detected expiry — the attempt transitions directly to whichever of the two grading states actually applies. *How* it was submitted is captured by the orthogonal `submissionMethod: 'MANUAL' | 'AUTO_EXPIRY'` field instead. Same resolution shape as `assignment_submissions`' own 4-vs-5-state ADR.

**Every attempt snapshots its own questions at start time — the single mechanism that makes "edit a question after it's in use" safe.** `assessment-attempt.model.ts`'s `questionSnapshot[]` is a frozen, per-attempt copy (text, type, marks, options with `isCorrect`, `correctBoolean`, `acceptedAnswers`, `correctNumericAnswer`) taken once when the attempt starts and never recomputed — a later edit or archive of the source `Question` document can never change how an in-progress or already-graded attempt is displayed or scored. Question/option order is decided once at snapshot time too (`shuffleQuestions`/`shuffleOptions`, Fisher-Yates via `shuffle.util.ts`), then persisted — never reshuffled on a later read.

**One assessment code prefix, not two.** `DM-ASM-{year}-{6digit}` for both QUIZ and EXAM — a deliberate, documented choice (not an oversight): every other `*-id.service.ts` in this codebase mints one prefix per *collection*, never branching on a document's own type field, and `assessmentType` already discriminates the two everywhere a query/filter/display needs it. Questions get `DM-QST-`, attempts get `DM-ATT-` — same atomic-counter mechanism as every prior ID service.

**A flat quiz is just an assessment with one section — never a second code path.** `sections[]` (embedded, own `_id`) is the sole question-organization container; the authoring UI, readiness check, and attempt-question-selection logic have exactly one implementation regardless of whether the admin thinks of it as "sectioned." A section's `randomQuestionCount`, when set, turns `questionIds` into a *pool* the server draws from once at attempt start (never recomputed) — and every question in that pool must carry equal `marks` (enforced both at `replaceSections` write time and again at publish-readiness as defense-in-depth), a deliberate simplification that keeps `assessment.totalMarks` deterministic regardless of which questions a given student draws, avoiding an intractable per-student-varying-total-marks problem.

**Whole-array-replace for sections, matching the batches precedent.** `POST /assessments/:id/sections` replaces the entire `sections` array in one call (API-STANDARDS.md §4's "compact, whole-set, never partial" contract, same shape as batches' weekly-schedule/calendar-exceptions endpoints) — never five granular section/question CRUD endpoints. `assessment.totalMarks` is recomputed and persisted on every call.

**Server-authoritative timer, computed once, never re-derived from the client.** `computeAttemptExpiry(startedAt, durationMinutes, closeAt)` — the earlier of the attempt's own duration and the assessment's hard `closeAt` — is calculated exactly once, at attempt creation, and stored as `expiresAt`. Every subsequent read/write of an `IN_PROGRESS` attempt (`getMyAttempt`, `saveAnswers`, `submitAttempt`, and defensively every grader-side read too) runs `materializeAttemptExpiry()` first, which lazily finalizes the attempt (scores it and transitions its status) if `now > expiresAt` — satisfying "never trust the frontend timer for final acceptance" without a background sweep job. **Documented tradeoff:** this is lazy, on-access expiry, not a proactive cron/BullMQ job — a truly abandoned attempt nobody ever opens again simply stays `IN_PROGRESS` in storage (harmless, since no further writes are possible once expired, and every read path re-checks first). A future hardening phase could add a scheduled sweep; not built here to avoid introducing a new background-job pattern for a single phase's edge case.

**Duplicate-start race defended at the database level, not just application logic.** A partial unique index on `{assessmentId, studentId}` (filtered to `status: 'IN_PROGRESS'`) means MongoDB's own write serialization — not a check-then-create race — guarantees at most one in-progress attempt per student per assessment. `startOrResumeAttempt()` catches the resulting `11000` duplicate-key error and gracefully resumes whatever the winning request created, rather than surfacing a raw conflict to a student who opened two tabs.

**`attemptNumber` is consumed at creation, not at successful completion.** Starting a second attempt always uses one unit of `assessment.maxAttempts` immediately, regardless of what happens to it afterward — matching how real exam software counts attempts, and keeping the attempt-limit check (`countAttemptsByAssessmentAndStudent`) a simple, race-safe count rather than a "did they ever actually finish" heuristic.

**One scoring engine, one negative-marking floor, applied at exactly one point.** `assessment-scoring.util.ts` — the phase's one "critical algorithm," covered by a small dedicated unit test (see Testing Backlog) — scores every objectively-gradable question type (`SINGLE_CHOICE`/`MULTIPLE_CHOICE`/`TRUE_FALSE`/`NUMERIC`/auto-mode `FILL_IN_THE_BLANK`) server-side; `MULTIPLE_CHOICE` is all-or-nothing (no partial credit, the task's own V1 recommendation). Unanswered is always `0` penalty, distinct from answered-and-wrong (the only case negative marking applies to). The floor — "assessment total cannot go below 0" — is applied exactly once, to the raw objective subtotal (`Math.max(0, objectiveMarksRaw)`); manual marks are separately bounded `0..question.marks` at grading-save time, so their sum is already non-negative and the two combine without a second, redundant floor.

**Subjective grading batch-saves, and auto-finalizes only once every manual question is graded.** `PATCH .../grade` accepts an array of `{questionId, marksAwarded, feedback}` entries in one call (never one request per question) and can be called multiple times while grading is in progress; the attempt transitions from `PENDING_MANUAL_GRADING` to `GRADED` automatically the moment `computeManualGradingProgress()` reports every manual question has a saved mark — never a separate explicit "finalize" action. Re-grading an already-`GRADED` attempt (a correction) is permitted; grading an `IN_PROGRESS` or `INVALIDATED` one is not.

**Result visibility is a pure function, re-evaluated on every read, never cached as a stored flag.** `isAttemptResultVisible(assessment, attempt)`: `attempt.status === 'GRADED'` AND (`assessment.status === 'RESULT_PUBLISHED'` OR `assessment.showResultImmediately`). `isCorrectAnswerReviewVisible()` layers `showCorrectAnswersAfterResult` on top. `attempt.resultVisibleAt` is purely informational (set once, for display, at whichever of grading-completion-with-immediate-result or assessment-level results-publish happens first) — never itself checked as an authorization gate, so it can never drift out of sync with the real rule.

**One shared grading service, two authorization gates — never a parallel grading code path.** `assessment-grading.service.ts` backs both the admin `/assessments/:id/attempts/:attemptId/grade` route (`assessments:grade` permission) and the trainer `/trainer/assessment-attempts/:attemptId/grade` route (ownership of a target batch, resolved via the same `batchRepository.findIdsForTrainer()` §28 introduced) — identical to `assignment-submission.service.ts`'s own precedent. `requireAttemptUnderAssessment()` cross-checks a `:attemptId` genuinely belongs to its `:id` (assessment) URL segment; the trainer's own flat `/trainer/assessment-attempts/:attemptId` shape instead resolves ownership from the attempt's own `assessmentId` directly — both paths 404, never 403, on mismatch.

**Grader view vs. student view are the same underlying mapper, different flags — never two parallel DTO builders.** `assessment-attempt-dto.ts#mapAttemptQuestions()` takes `{revealCorrectness, includeGrading}` booleans; a grader (admin/trainer) always gets both `true`, a student gets them computed from the same `isAttemptResultVisible`/`isCorrectAnswerReviewVisible` functions the rest of the engine uses. This is the one place correctness data (`options[].isCorrect`, `correctBoolean`, `acceptedAnswers`, `correctNumericAnswer`) is ever included in a response — every other DTO path omits it structurally, not by convention.

**Permissions: six, matching the assignments module's own precedent.** `questions:read`/`questions:manage`, `assessments:read`/`:manage`/`:grade`/`:export` — grading kept separate from managing for the identical reason `assignments:grade` was split out in §28. `ADMIN`/`SUPER_ADMIN` hold all six; `TRAINER` reaches grading via ownership only, no new permission-catalog grants (matching `assignments`' own `TRAINER` row). **Action required:** run `npm run seed:roles` in `backend/` against your target environment to provision these — never run automatically against live/shared Atlas.

**Frontend: one exam player, no dashboard chrome.** `ExamPlayer` (`features/student-assessments/components/`) renders a `fixed inset-0` distraction-free shell — no sidebar/topbar — matching the task's own explicit instruction. Autosave is debounced (2s after the last change) and additionally flushed synchronously on question navigation and `beforeunload`; the server-authoritative `expiresAt` drives a countdown whose screen-reader announcement is throttled to once a minute (once per 15s in the final minute) so it never spams assistive tech, while the visible digits still tick every second. A page refresh naturally resumes: `GET .../attempts/:attemptId` returns the attempt's current DB state (already-autosaved answers, `expiresAt`), and `ExamPlayer` is remounted fresh via `key={attempt.id}` at the call site — never a `useEffect`-based re-sync, the same pattern §13's own lint-driven fix established for `GradingModal`.

**Frontend: one player/result endpoint, not two.** `GET /student/assessments/attempts/:attemptId` serves both the in-progress player state and the post-grading result view — `StudentAssessmentAttemptPage` branches purely on `attempt.status`/`resultVisible`, avoiding a redundant second `/result` endpoint that would return the identical DTO shape under a different URL.

**No fabricated anti-cheating claims.** Focus-loss (tab/window blur) events are counted (`attempt.focusLossCount`) as an audit signal only — never surfaced to the student as a warning, never labeled "cheating detected," and never advertised as proctoring. This phase provides controlled attempts, randomized questions/options, a server-authoritative timer, and secure server-side scoring — it does not, and does not claim to, provide proctoring (task's own explicit "no fake anti-cheating claims" instruction).

**Quality gates:** backend `tsc --noEmit` / `eslint` / `prettier --check` / build all clean; frontend `tsc -b` / `eslint --max-warnings=0` / `prettier --check` / `vite build` all clean (same Node ≥20.19 requirement §28 documented). **No large automated test suite was built this phase** (explicit phase instruction) beyond one small, focused unit test for the scoring engine (`assessment-scoring.util.test.ts` — see the Testing Backlog for what a dedicated hardening phase should still add).

**Found during this phase, not fixed (out of this phase's declared scope):** `assignment.validator.ts`'s `updateAssignmentSchema` (§28) shares its base field object with `createAssignmentSchema`, and several of those fields carry a `.default(...)` (`allowedFileTypes`, `maxFiles`, `maxFileSizeBytes`, `allowLateSubmission`, `allowResubmission`). Verified empirically against this repo's own Zod version: `.partial()` does **not** suppress `.default()` — a PATCH that omits one of those fields has Zod silently inject its default value into the parsed input, which `assignment.service.ts#updateAssignment`'s own `if (input.field !== undefined)` guards then treat as "the client sent this," silently overwriting real data on any partial update that doesn't resend all five fields. This is the exact bug class SECURITY.md §4 documents (and fixed) for `updateBatchSchema` — it was not re-introduced in this phase's own validators (`question.validator.ts`/`assessment.validator.ts` both keep their shared base fields default-free, applying defaults only via `.extend()` on the create schema). Flagging prominently rather than silently fixing, since "do not refactor unrelated completed modules" was this phase's own explicit instruction — recommend a fast-follow fix.

**Explicitly out of scope, unchanged:** certificates, payments, placement, advanced analytics, a full Notifications module (hooks/event points only — question/assessment lifecycle audit events exist, no actual email/WhatsApp dispatch), bulk CSV question import (deferred per the task's own "if this significantly increases scope, defer and document" allowance — not built this phase), proctoring/webcam/tab-lock enforcement (never fabricated).
