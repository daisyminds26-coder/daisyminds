# Daisy Minds LMS — API Standards

**Base path:** `/api/v1` · **Format:** JSON only · **Docs:** Swagger/OpenAPI served at `/api/docs` (non-production environments only, or protected behind auth in production).

---

## 1. Resource Naming

- Plural nouns for collections: `/students`, `/courses`, `/batches`.
- Nested resources only where the child cannot exist independently of the parent: `/courses/:courseId/modules`, `/batches/:batchId/attendance`. Otherwise, top-level with a filter query param: `/Enrollllments?studentId=...` rather than `/students/:id/Enrollllments`, to keep the resource independently queryable/filterable.
- Actions that aren't pure CRUD are modeled as sub-resources/verbs on the resource, not as new top-level routes: `POST /Enrollllments/:id/withdraw`, `POST /payments/:id/refund`, `POST /certificates/:id/revoke`.
- No verbs in collection URLs (`/getStudents` is not acceptable).

## 2. HTTP Methods & Status Codes

| Method | Use | Success Code |
|---|---|---|
| GET | Read (single or list) | 200 |
| POST | Create, or a non-idempotent action | 201 (create) / 200 (action) |
| PATCH | Partial update | 200 |
| PUT | Not used — PATCH only, to avoid full-document-replace footguns on partially-modeled resources | — |
| DELETE | Hard delete (only where DATABASE.md permits it) or soft-delete/status-transition otherwise | 204 |

Error codes follow standard semantics: `400` validation, `401` unauthenticated, `403` unauthorized (authenticated but lacking permission), `404` not found, `409` conflict (e.g., duplicate Enrollllment), `422` semantically invalid but well-formed (e.g., withdrawing an already-withdrawn Enrollllment), `429` rate-limited, `500` unhandled server error (never exposes internals — see SECURITY.md).

## 3. Response Envelope

Every response — success or error — uses one consistent shape so frontend handling never branches per-endpoint. Built via `utils/api-response.ts` helpers — controllers never hand-construct either shape.

**Success:**
```
{
  "success": true,
  "message": "Request completed successfully",
  "data": { ... } | [ ... ],
  "meta": { "page": 1, "limit": 20, "total": 134 },   // present only on paginated list endpoints
  "requestId": "..."
}
```

**Error:**
```
{
  "success": false,
  "message": "Human-readable summary",
  "code": "VALIDATION_ERROR",
  "errors": [ { "field": "email", "message": "must be a valid email" } ],  // present for 400/422
  "details": { "lockedUntil": "2026-08-06T12:30:00.000Z" },               // present only for errors that carry structured data (e.g. ACCOUNT_LOCKED)
  "requestId": "..."
}
```

`code` is a **stable machine-readable string** (`VALIDATION_ERROR`, `NOT_FOUND`, `FORBIDDEN`, `ACCOUNT_LOCKED`, `EMAIL_NOT_VERIFIED`, `DUPLICATE_EnrolllLMENT`, `PAYMENT_GATEWAY_ERROR`, etc.) — the frontend and any future API consumer branch on `code`, never on parsing `message`. `details` is an optional, error-specific structured payload (distinct from `errors`, which is specifically field-level validation errors) — e.g. `POST /auth/login` against a `LOCKED` account returns `code: "ACCOUNT_LOCKED"` with `details.lockedUntil` so the frontend can show a real retry-after time instead of parsing the message text. `requestId` is generated by `middlewares/request-id.middleware.ts` (from the inbound `X-Request-Id` header if present, otherwise a new UUID), echoed on the response header and in every log line for that request, and included in the envelope so a user-reported error can be traced directly to its log lines. This is implemented once, globally, via the final Express error-handling middleware (`middlewares/error-handler.middleware.ts`) — individual controllers never hand-construct this shape, they just `throw` a typed `ApiError` subclass (CODING-STANDARDS.md §4) and let it propagate.

**Deliberate exception — file downloads:** `GET /users/export` (Phase 5) returns `Content-Type: text/csv` with the raw CSV body, not the JSON envelope — an envelope has no meaningful shape for a file download, and the frontend requests it with `responseType: 'blob'` specifically to bypass the JSON-unwrapping path. `GET /students/export` (Phase 6), `GET /trainers/export` (Phase 7), `GET /courses/export` (Phase 9A), and `GET /batches/export` (Phase 10A) all follow the identical pattern — no new exception invented.

## 4. Pagination, Filtering, Sorting

Query parameters, consistent across every list endpoint:

- `page` (default `1`), `limit` (default `20`, max `100` — enforced server-side regardless of what's requested).
- `sort` — e.g. `sort=createdAt:desc`. Only fields explicitly whitelisted per endpoint are sortable (never arbitrary field passthrough into a Mongo sort — injection/perf risk).
- Filters are explicit query params per resource (`status=ACTIVE&batchId=...`), not a generic free-form filter DSL — keeps validation and indexing predictable (ties to DATABASE.md's indexing strategy: a filter param should map to an indexed field).
- `meta` on list responses always includes `page`, `limit`, `total`, and `totalPages`.

**Reference implementation:** `GET /users` (Phase 5) is the first endpoint to exercise this pattern end-to-end — `sort=email:asc`, `status=ACTIVE`, `roleId=...`, `search=` (email prefix), `page`/`limit`, all validated by a single Zod schema (`listUsersQuerySchema`) whose `sort` field transforms the `field:direction` string into `{field, direction}` before it reaches the repository, so only whitelisted `field` values ever survive parsing. `GET /students` (Phase 6) follows the same contract from the client's perspective (same `page`/`limit`/`sort`/`meta` shape) while being the first list endpoint whose filters/search span two collections under the hood via a `$lookup` aggregation — see DATABASE.md §3.2 and ARCHITECTURE.md §15 for why that was necessary here specifically. `GET /trainers` (Phase 7) is a third instance of the identical `$lookup`+`$facet` pattern (ARCHITECTURE.md §17) — no new list-query shape was invented for it. `GET /courses` (Phase 9A) uses the same client-facing contract but, unlike students/trainers, needs no `users` join — its query is a plain `find().sort().skip().limit()`, since a course is a fully self-contained document (ARCHITECTURE.md §19).

**Permission-aware response shaping (Phase 8 reference implementation):** `GET /dashboard/admin` (ARCHITECTURE.md §18) is the first endpoint whose response *body* varies by the caller's role while still being one endpoint, one permission (`dashboard:read`), and one `200` — not a second endpoint or an extra `403`. `recentActivity` is `null` for `ADMIN` and a populated array for `SUPER_ADMIN`; every other field is identical for both. This is a deliberate, minimal alternative to the app's other pattern for role-varying access (a stricter `requireRole('SUPER_ADMIN')` gate on a *separate* sessions/audit sub-route, used by `/users`, `/students`, `/trainers`) — appropriate here because the varying data is one field of an otherwise-shared payload, not an entire independent resource.

**Reorder/move contract (Phase 9B reference implementation):** `POST /courses/{courseId}/modules/reorder`, `POST /courses/{courseId}/lessons/reorder`, and `POST /courses/{courseId}/lessons/{lessonId}/move` (ARCHITECTURE.md §20) establish this app's first "reposition a sibling set" contract. The request body is always compact `{id, order}` pairs (or a single `{targetModuleId, targetOrder}` for move) — **never** a full document round-trip. A reorder payload must name every current active sibling exactly once; a partial list, an unknown id, or a duplicate id/order value is rejected with `400` before any write happens, and the server re-derives a contiguous 0-based sequence from the *relative* ranking submitted rather than trusting the client's literal `order` values. The response is the full updated sibling list (same shape a `GET` of that list would return), so the frontend never needs a follow-up fetch after a successful reorder. `POST /courses/{courseId}/modules/{moduleId}/lessons/{lessonId}/resources/reorder` (Phase 9C) reuses this exact contract unchanged for the resource-manager's drag/keyboard reorder.

**Whole-array-replace contract, POST rather than PUT (Phase 10A reference implementation):** `POST /batches/{id}/weekly-schedule` and `POST /batches/{id}/calendar-exceptions` (ARCHITECTURE.md §22) extend the same "compact, whole-set, never partial" reorder discipline above to a full-array *replace* (not a reposition) — the request body **is** the complete new array, and the response is the updated batch. Since this project's method table (§2) does not use `PUT` anywhere, a whole-resource/whole-array replace is modeled as `POST` on a named sub-resource path instead, exactly like the reorder endpoints above — never introduced as this app's first `PUT` usage. `POST /batches/{id}/trainers` (full replace of `primaryTrainerId`+`assistantTrainerIds` together, since the pair has cross-field validation — a primary cannot also be an assistant) follows the identical pattern.

**Signed-upload contract (Phase 9C reference implementation, generalizing the Phase 9A course-thumbnail/banner pattern):** every media upload (lesson video/document, lesson resource) is a three-call sequence, never a file upload through this API directly — `POST .../signature` (no body; returns `{timestamp, signature, apiKey, cloudName, folder, publicId, resourceType, type, allowedFormats, maxFileSize}`, all server-chosen) → the client uploads the file **directly to Cloudinary** using those exact params → `POST .../verify` (body: `{publicId}` plus any purely-cosmetic client-reported metadata like `originalFilename`/`title`, never anything security-relevant) re-verifies the asset against Cloudinary's own Admin API before trusting it, and is what actually updates the lesson/resource record. `GET .../preview-url` and `GET .../{resourceId}/delivery-url` return a short-lived (5-minute) signed Cloudinary URL, computed fresh on every call — never cached or returned as part of any other response, since it must never become a permanent public reference. `DELETE` on a video/document/resource always resolves the Cloudinary asset from the server's own stored record, never from a client-supplied identifier.

## 5. Validation

- Every request body/query/param is validated via a **Zod schema** for that route, applied through a shared `validate(schema)` middleware (`middlewares/validate.middleware.ts`) mounted before the controller. Zod objects strip unknown keys by default — every request-validation schema in this codebase uses `.strict()` (or `z.strictObject()`) instead, so an unexpected field fails the request with a `VALIDATION_ERROR` rather than being silently dropped (per CLAUDE.md: "never trust frontend input"). Response/documentation schemas (`src/docs/`) are unaffected — strictness only applies to inbound validation.
- The Zod schema is the single source of truth for what an endpoint accepts; the controller's request type is inferred from it (`z.infer<typeof schema>`), and the same schema feeds the generated OpenAPI spec (§10) so documentation cannot drift from validation.
- Business-rule validation (e.g., "cannot Enrollll in a full batch") lives in the service layer and returns `422`, not `400` — `400` is reserved for structurally invalid input.

## 6. Authentication & Authorization

- `Authorization: Bearer <accessToken>` header on every authenticated request. Access tokens are short-lived (see SECURITY.md); refresh handled via a dedicated `/auth/refresh` endpoint.
- **Default-deny by router mounting order, not per-route opt-in:** public routers (auth, health, certificate verification) are mounted in `app.ts` *before* the shared `requireAuth` middleware; every other feature router is mounted *after* it, so a newly added module is protected automatically simply by where it's registered — forgetting to add a route to an allowlist can never accidentally expose it.
- Role/permission checks via a `requireRole(...roles)` / `requirePermission(...)` middleware factory, composed into the route's middleware array after `requireAuth` — controllers never manually check `req.user.role`.

## 7. Rate Limiting

Global default via `express-rate-limit` (e.g., 100 req/min per IP for authenticated routes), with **tighter, explicit limits** on sensitive endpoints:
- `/auth/login`, `/auth/refresh` — brute-force protection (see SECURITY.md).
- `/certificates/verify/:certificateNumber` — public, unauthenticated, and directly named as an enumeration risk in the understanding report; rate-limited per-IP and should degrade to a CAPTCHA challenge if abuse patterns are detected (⚠ CAPTCHA provider pending).

## 8. Idempotency

State-changing endpoints that may be retried by a client or a payment gateway webhook (`POST /payments/webhook`, `POST /payments/:id/refund`) require an idempotency key (gateway transaction ID for webhooks; client-generated `Idempotency-Key` header for client-initiated retries) — processing the same key twice must not double-charge or double-create records. This is enforced at the database layer via the unique index on `payments.gatewayTransactionId` (DATABASE.md §2.5), not just application logic.

## 9. Versioning

`/api/v1` is the only version at launch. A breaking change to a resource shape is introduced as a new `/api/v2` router mounted alongside `/api/v1` (URI-based versioning), not by silently changing `v1`'s contract. No deprecation timeline exists yet for v1 since nothing has shipped — this section will be expanded once v2 planning begins.

## 10. Swagger

Every module's Zod schemas are registered with `zod-to-openapi`, which generates the OpenAPI document from the same schema objects that drive runtime validation (§5) — there is no separate hand-written spec to drift out of sync. `swagger-ui-express` serves the generated spec at `/api/docs`. The generated spec is the API contract used by the frontend team and is reviewed as part of PR review for any endpoint change.
