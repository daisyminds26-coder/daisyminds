# Daisy Minds LMS — Database Standards

**Engine:** MongoDB Atlas · **ODM:** Mongoose · **Status:** V1 production schema — 32 collections, implemented at `backend/src/models/*.model.ts`. Single-tenant (see [ARCHITECTURE.md](./ARCHITECTURE.md) §1) — no `organizationId` field is included pending confirmation of PROJECT-UNDERSTANDING-REPORT.md Q1.

This document is the design record; the Mongoose schemas are the source of truth for exact field shapes. Where they'd ever disagree, the code wins and this doc is stale and needs an update (CLAUDE.md: "never leave undocumented architecture changes").

---

## 1. Conventions

- **Collection names:** plural, **snake_case** (`user_sessions`, `course_modules`, `assignment_submissions`) — changed from the earlier camelCase convention (`courseBatches`) to match this schema generation's explicit collection list. Set explicitly via each schema's third `model()` argument, not left to Mongoose's auto-pluralization (which wouldn't produce `user_sessions` from a model named `UserSession`).
- **Field names:** camelCase.
- **Primary keys:** MongoDB default `_id` (ObjectId). Never exposed as a guessable public identifier for anything user-facing and enumerable — see `certificates` §2.6.
- **References:** stored as `ObjectId` with a `ref` to the target model; populated only where the read pattern requires it, never by default on list endpoints (performance).
- **Audit fields — mandatory on every collection:** `createdBy: ObjectId | null (ref: users)`, `updatedBy: ObjectId | null (ref: users)`, `createdAt: Date`, `updatedAt: Date` (both via Mongoose `timestamps: true`), `isDeleted: boolean` (default `false`), `deletedAt: Date | null`. Applied uniformly via `src/models/plugins/audit-fields.plugin.ts` (`auditFieldsDefinition` spread into every schema + `applyAuditPlugin()` for `timestamps`) so they can never drift in shape between collections. `createdBy`/`updatedBy` are nullable to accommodate system/seed-created documents (the first `SUPER_ADMIN`, seeded roles) where no authenticated actor exists yet.
- **Soft delete — fields always present, usage varies:** every collection has `isDeleted`/`deletedAt` per the mandate above, but per DATABASE.md's original philosophy ("soft delete only when needed"), several collections' business logic must **never** actually set `isDeleted: true` — see each collection's "Soft Delete" line. Where that's the case, the fields are structurally present (schema consistency, future-proofing) but dormant by policy, enforced at the service layer (or, for `audit_logs`, at the schema level via update-blocking hooks — §2.1).
- **No unnecessary collections:** lookup/enum-like data lives as application-level `as const` arrays (`src/models/shared/enums.ts`) or in `application_settings`, not as a collection per enum.

## 2. Cross-Cutting Design Decisions

These extend or supersede the V1 baseline design from earlier in this document's history — each is a deliberate change made when generating the full 32-collection schema, not an oversight:

1. **RBAC is now data-driven**, not a hardcoded enum. `roles` holds a denormalized `permissions: string[]` array (the hot-path read on every authorization check); `permissions` is the admin-facing catalog of what keys *exist* (read when building/editing a role, not per-request). `users.roleId` references `roles`. The four original roles (`SUPER_ADMIN`/`ADMIN`/`TRAINER`/`STUDENT`) become seeded system roles (`isSystem: true`), not a closed enum — a custom role can be added later without a schema migration, directly answering PROJECT-UNDERSTANDING-REPORT.md Q10.
2. **`user_sessions` replaces `users.refreshTokenHash`.** One document per active session (device/IP tracked, independently revocable) instead of a single token per user — proper multi-device support and the ability to "log out of all other devices."
3. **`questions` is a standalone bank**, referenced (not embedded) by both `quizzes` and `examinations`. This reverses the earlier "start embedded" recommendation because the explicit collection list demands a `questions` collection and — now that quizzes *and* exams both need to draw from it — reuse across two parent collections is exactly the scenario where referencing is correct over embedding.
4. **The placement domain splits into three collections**: `placement_profiles` (1:1 student profile), `companies` (employer catalog), `interviews` (per-application pipeline with embedded rounds) — replacing a single flat `placements` collection with a model of the actual workflow.
5. **`reports` persists async export jobs** (status, requester, result file, expiry) generated by the `reports` BullMQ queue (ARCHITECTURE.md §6) — never live dashboard data, which stays as ad-hoc aggregation and is never written to a collection.
6. **No `markedBy`/similar redundant actor fields.** Anywhere an earlier design might have added a bespoke "who did this" field, the audit plugin's `createdBy`/`updatedBy` already covers it — see `attendance` §2.16 for the clearest example. The one deliberate exception is `assignment_submissions.gradedBy`/`gradedAt` (§2.18), kept explicit because grading is a distinct lifecycle event a later unrelated update must not be able to obscure.

## 3. Collections

Legend for **Soft Delete**: **Active** = service layer sets `isDeleted`/`deletedAt` as part of normal deletion flows. **Dormant** = fields present per §1's mandate, but business logic must never set them true (status transitions or hard-delete/immutability are the real lifecycle). **N/A (immutable)** = the collection is append-only; no delete path exists at all.

### 3.1 Identity & Access

#### `permissions` — **Implemented (Phase 2)**, seeded via `scripts/seed-roles.ts`
**Purpose:** Admin-facing catalog of atomic permission keys (`resource:action`, e.g. `students:create`), used to build `roles.permissions`.
**Fields:** `key` (string, required, unique, pattern `^[a-z0-9-]+:[a-z0-9-]+$`) · `description` (string, required, ≤300) · `category` (string, required, ≤60 — groups keys for an admin UI) · `isSystem` (boolean, default `false`).
**Indexes:** unique `{ key: 1 }` (partial: `isDeleted: false`) · `{ category: 1 }`.
**Relationships:** referenced by `roles.permissions` **by key string, not ObjectId** — deliberate: authorization checks read `roles.permissions` directly without a join, so the catalog and the grant are decoupled by design.
**Soft Delete:** Active — a permission key can be deprecated without breaking historical role definitions that no longer reference it.
**Business/Ownership/Security:** SUPER_ADMIN-only CRUD; `isSystem` keys cannot be deleted via the admin UI (service-layer check, not schema-enforced).
**Query/Pagination/Search:** list by `category`, offset-paginated (small collection, tens of rows); no full-text search needed.
**Future Scalability:** stays small (hundreds of rows at most) — no scaling concern.

#### `roles` — **Implemented (Phase 2)**; read exposed via `GET /roles` (Phase 5)
**Purpose:** Named permission sets assigned to users — seeded system roles plus room for custom roles.
**Fields:** `name` (string, required, unique, uppercased, ≤60) · `description` (string, default `''`, ≤300) · `permissions` (string[], default `[]` — permission keys, not refs) · `isSystem` (boolean, default `false`).
**Indexes:** unique `{ name: 1 }` (partial: `isDeleted: false`) · `{ permissions: 1 }` (multikey — "which roles grant X").
**Relationships:** `users.roleId → roles._id` (many users : one role).
**Soft Delete:** Active, but service layer must block deleting a role still referenced by any `users.roleId`.
**Business/Ownership/Security:** SUPER_ADMIN-only CRUD; `isSystem` roles' `name`/`isSystem` are immutable (permissions array may still be edited); permission-key values written here should be validated against the `permissions` catalog at the service layer (not schema-level — an async cross-collection validator is business logic, out of scope for this task).
**Query/Pagination/Search:** small collection, list all (no pagination needed in practice); no search.
**Future Scalability:** if custom-role count grows meaningfully, add a `{ isSystem: 1 }` index — not needed at V1 scale.
**Phase 5 note:** `GET /roles` (`users:manage`-gated) returns `{id, name}` for every role, purely so the admin UI can populate a role picker with valid `roleId`s. No role/permission-set CRUD is exposed yet — creating/editing roles or their `permissions` array remains SUPER_ADMIN-only and has no admin UI in this phase.

#### `users` — **Implemented (Phase 2)**; admin CRUD/lifecycle/role-assignment via `/users` (Phase 5)
**Purpose:** Base identity/auth record for every human in the system — auth-relevant fields only; profile data lives in `students`/`trainers`.
**Fields:** `email` (string, required, unique, lowercased, trimmed, regex-validated, ≤254) · `passwordHash` (string, required, `select: false` — Argon2id, SECURITY.md §2) · `roleId` (ObjectId ref `Role`, required) · `status` (enum, default `PENDING_VERIFICATION`) · `mfaEnabled` (boolean, default `false`) · `mfaSecret` (string \| null, `select: false` — reserved, MFA not yet implemented) · `lastLoginAt` (Date \| null) · `lastLoginIp` (string \| null) · `passwordChangedAt` (Date \| null) · `failedLoginAttempts` (number, default `0`) · `lockedUntil` (Date \| null — account lockout, SECURITY.md §2) · `emailVerifiedAt` (Date \| null) · `emailVerificationTokenHash` (string \| null, `select: false`) · `emailVerificationTokenExpiresAt` (Date \| null) · `passwordResetTokenHash` (string \| null, `select: false`) · `passwordResetTokenExpiresAt` (Date \| null).
**Enum — `status`:** `PENDING_VERIFICATION` \| `ACTIVE` \| `SUSPENDED` \| `LOCKED` \| `DEACTIVATED` — revised from the original `ACTIVE`/`INVITED`/`SUSPENDED`/`DEACTIVATED` set when Phase 2 (auth) was implemented: `INVITED` (admin-provisioned, no password yet) was replaced by `PENDING_VERIFICATION` (self-registration flow, needs email verification) since there is no admin-invitation flow in this codebase yet, and `LOCKED` was added for the account-lockout feature (SECURITY.md §2) as a distinct, admin-visible state from `SUSPENDED` (an explicit admin action).
**Verification/reset token fields** are single-active-token-at-a-time (unlike `user_sessions`, which is inherently multi-valued) — that's why they're plain nullable fields here rather than their own collection. Tokens themselves are opaque high-entropy random values; only their SHA-256 hash is stored (`token.service.ts` — see SECURITY.md §1 for why SHA-256, not Argon2, is correct here).
**Indexes:** unique `{ email: 1 }` (partial: `isDeleted: false` — lets a deactivated account's email be reused by a new signup) · `{ roleId: 1, status: 1 }` (admin user-list filtering).
**Relationships:** `roleId → roles`; `students.userId`/`trainers.userId` reference back 1:1; `user_sessions.userId` references forward.
**Soft Delete:** Active (`DEACTIVATED` status is the operational signal; `isDeleted` is reserved for a harder "account removed" case — e.g. right-to-erasure requests once DPDP applies, SECURITY.md §7).
**Business/Ownership/Security:** `passwordHash`/`mfaSecret`/`emailVerificationTokenHash`/`passwordResetTokenHash` never selected by default (`select: false`) — a query must explicitly opt in (`user.repository.ts`'s `WithPassword`/token-hash lookup methods). Self-service profile edits are limited to non-auth fields (handled entirely outside this schema, in `students`/`trainers`).
**Query/Pagination/Search:** admin user list filtered by `roleId`/`status`, offset-paginated; search by email via a prefix query on the unique index (no text index needed for an exact-ish field); reset/verification-token lookups hit their respective hash fields directly (not indexed — low read volume, one-at-a-time by nature).
**Future Scalability:** at 10k+ students this collection stays lean (auth fields only) by design — the split from profile data is exactly what keeps it fast at scale.
**Phase 5 note:** the admin `GET /users` list additionally supports free-text `search` (case-insensitive regex prefix on `email`, escaped — DATABASE.md §6 still applies: no text index yet, acceptable at current scale) and `sort` on `email`/`status`/`createdAt`/`lastLoginAt`. All state-changing admin actions (activate/deactivate/soft-delete/restore/role-assign/reset-password/resend-verification, including bulk variants) are guarded in `user-management.service.ts` per SECURITY.md's privilege-escalation rules and write an `audit_logs` entry. A stale, orphaned `username_1` unique index (predating the current schema — no `username` field exists) was found blocking user creation on the live Atlas cluster and was dropped; see this file's git history and ARCHITECTURE.md §14 for details.

#### `user_sessions` — **Implemented (Phase 2)**
**Purpose:** One document per active refresh-token session — multi-device login with independent per-session revocation (SECURITY.md §1).
**Fields:** `userId` (ObjectId ref `User`, required) · `refreshTokenHash` (string, required, `select: false`) · `userAgent` (string \| null, ≤500) · `ipAddress` (string \| null, ≤45) · `expiresAt` (Date, required) · `revokedAt` (Date \| null) · `lastUsedAt` (Date \| null).
**Indexes:** `{ userId: 1, revokedAt: 1 }` (list a user's active sessions) · TTL `{ expiresAt: 1 }` (`expireAfterSeconds: 0` — Mongo hard-deletes once past expiry).
**Relationships:** `userId → users`.
**Soft Delete:** **Dormant for `isDeleted`** — `revokedAt` is the real "soft delete" signal (explicit logout/revoke); the TTL index hard-deletes naturally-expired sessions, since an expired session has no audit value worth keeping.
**Business/Ownership/Security:** a user can list/revoke only their own sessions; `SUPER_ADMIN` can revoke any session (e.g. responding to a compromised-account report, SECURITY.md §10). `refreshTokenHash` never selected by default. **Phase 5:** `GET /users/:id/sessions` and `POST /users/:id/sessions/:sessionId/revoke` (admin "view sessions" / "force logout") are `requireRole('SUPER_ADMIN')`-gated specifically — stricter than the general `users:manage` permission `ADMIN` also holds — since forcing another user's logout is a higher-blast-radius action than the rest of the module.
**Query/Pagination/Search:** "my active sessions" = `{ userId, revokedAt: null }`, small result set, no pagination needed; no search.
**Future Scalability:** naturally self-limiting via TTL — this collection never grows unbounded regardless of login volume.

#### `audit_logs` — **Implemented (Phase 2)**
**Purpose:** Append-only trail of every state-changing action (SECURITY.md §8). Every auth event (`auth.login.success`/`.failed`, `auth.refresh.reuse_detected`, `auth.logout`, `auth.logout_all`, `auth.password.*`, `auth.email.*`, `auth.session.revoked`) is written here by `auth.service.ts` — the first real producer of this collection.
**Fields:** `actorId` (ObjectId ref `User` \| `null` — null for system-initiated entries) · `actorRole` (string \| null — captured **at write time**, since a user's role can change later and the historical record must reflect what they were *when they acted*) · `action` (string, required, ≤120, e.g. `student.updated`) · `entityType` (string, required, ≤60) · `entityId` (ObjectId, required) · `metadata` (object, default `{}` — before/after diff or context, never secrets) · `ipAddress` (string \| null) · `userAgent` (string \| null).
**Indexes:** `{ entityType: 1, entityId: 1 }` · `{ actorId: 1, createdAt: -1 }` · `{ action: 1, createdAt: -1 }`.
**Relationships:** `actorId → users`; `entityId` is polymorphic (points into whichever collection `entityType` names — intentionally not a typed `ref`, since it can target any collection).
**Soft Delete: N/A (immutable).** `updateOne`/`updateMany`/`findOneAndUpdate` are blocked with a `pre` hook that throws — enforced at the schema level, not just by convention, because "an audit trail that can be edited is not an audit trail." No delete path exists either (retention/purge policy is pending — DATABASE.md §6).
**Business/Ownership/Security:** written only by internal service code (never a direct client-facing write endpoint); read access is `SUPER_ADMIN`-only (and the specific actor viewing their own action history, if that UI is ever built). **Phase 5** is the first read consumer: `GET /users/:id/audit` (SUPER_ADMIN-only) powers the admin user-detail "Audit Timeline," mapped to an explicit `AuditLogEntryDto` (raw documents never leave the service layer).
**Query/Pagination/Search:** "history for entity X" (`entityType`+`entityId`) and "actions by actor Y" (`actorId`+`createdAt` desc) are both cursor-paginated by `createdAt`, not offset — this is the collection DATABASE.md §4 names as the most likely candidate to need cursor pagination first, given append-only high volume. **Phase 5's** `findByEntity('user', userId, page, limit)` currently uses offset pagination (small per-user result sets in practice); revisit if a single user accumulates enough history for it to matter.
**Future Scalability:** highest-volume collection in the system by write count; once a retention period is confirmed, a TTL index becomes the primary scaling lever (not sharding at this scale).

### 3.2 People

#### `students` — **Admin management implemented (Phase 6)**; student self-service editing still pending
**Purpose:** 1:1 academic/personal profile satellite to `users` (role = STUDENT) — split out so auth-hot-path reads never load this larger payload.
**Fields:** `userId` (ObjectId ref `User`, required, unique) · `studentId` (string, required, unique, uppercased — server-generated, format `DM-STU-{year}-{6-digit sequence}`, see below) · `firstName`/`lastName` (string, required, ≤100) · `middleName`/`displayName` (string \| null) · `dateOfBirth` (Date \| null) · `gender` (enum \| null) · `preferredLanguage` (string \| null) · `phone`/`alternatePhone` (string \| null, ≤20) · `address` (embedded: `line1`, `line2?`, `city`, `state`, `postalCode`, `country`) · `emergencyContacts` (embedded array, ≥1 required at creation, Zod-enforced not schema-enforced: `name`, `phone`, `relationship`, `alternatePhone?`, `email?`) · `guardianName`/`guardianPhone`/`guardianEmail`/`guardianRelationship`/`guardianOccupation` (nullable — reserved for the pending minors/DPDP decision, SECURITY.md §7) · `guardianAddressSameAsStudent` (boolean) · `guardianAddress` (embedded, same shape as `address`, nullable) · `educationRecords` (embedded array: `degree`, `institution`, `yearOfCompletion`, plus Phase 6 additions `boardOrUniversity`/`fieldOfStudy`/`gradeValue`/`gradeType`/`documentUrl`/`documentPublicId`, all nullable) · `profilePhotoUrl`/`profilePhotoPublicId` (string \| null) · `kycDocuments` (embedded array: `type`, `url`, `verifiedAt` — **unpopulated**, reserved for a future government-ID decision, not built this phase) · `admissionDate` (Date \| null) · `source` (enum \| null) · `counsellorId` (ObjectId ref `User` \| null — distinct from the audit plugin's `createdBy`; the counsellor who owns the relationship may not be whoever operated the admin UI) · `notes` (string \| null, ≤2000) · `tags` (string[]) · `profileCompletionPercentage` (number, 0–100) · `profileCompletionStatus` (enum).
**Enum — `gender`:** `MALE` \| `FEMALE` \| `OTHER` \| `PREFER_NOT_TO_SAY`. **`source`:** `WEBSITE` \| `REFERRAL` \| `WALK_IN` \| `SOCIAL_MEDIA` \| `ADVERTISEMENT` \| `OTHER`. **`profileCompletionStatus`:** `INCOMPLETE` \| `PARTIAL` \| `COMPLETE` (server-calculated, never client-writable — ARCHITECTURE.md §15).
**Indexes:** unique `{ userId: 1 }` (partial: `isDeleted: false`) · unique `{ studentId: 1 }` (partial: `isDeleted: false`) · `{ phone: 1 }` (sparse) · text `{ firstName, lastName }` · `{ admissionDate: 1 }` · `{ tags: 1 }` · `{ 'address.state': 1, 'address.city': 1 }`.
**`studentId` generation:** a new `counters` collection (one doc per named sequence, `{_id, seq}`) backs `student-id.service.ts#generateStudentId`, which claims the next number via a single atomic `findOneAndUpdate({_id:'student'}, {$inc:{seq:1}}, {upsert:true})` — concurrency-safe by construction, unlike counting existing documents. One global sequence, deliberately never reset per calendar year (ARCHITECTURE.md §15 explains why).
**Relationships:** `userId → users` (1:1) · `counsellorId → users` (nullable). `address`/`emergencyContacts`/`guardianAddress`/`educationRecords`/`kycDocuments` are **embedded**, not referenced — small, bounded, always read/written with the parent document, never queried independently.
**Soft Delete:** Active in schema, but **deliberately never toggled by the admin "delete student" action** — that action soft-deletes the linked `users` document instead (auth identity + sessions), preserving academic history integrity so a future enrollment/attendance/grade record referencing `Student._id` never dangles (ARCHITECTURE.md §15). `isDeleted` here is reserved for a genuine future "erase this profile" case, not the everyday admin delete/restore flow.
**Business/Ownership/Security:** `ADMIN`/`SUPER_ADMIN` manage any record via `students:read`/`students:manage`/`students:export`; viewing/revoking a student's sessions and reading their audit timeline are `SUPER_ADMIN`-only (mirrors the `users` collection's stricter carve-out, DATABASE.md §3.1). Student self-service editing of their own profile is **not yet built** (out of scope for Phase 6, which is admin-only management). `kycDocuments`/guardian fields are PII — never logged (SECURITY.md §7); the CSV export deliberately excludes both, plus free-text `notes`, to limit PII sprawl in a downloadable file.
**Query/Pagination/Search:** the admin list/export is the first query in this codebase to `$lookup` `students`→`users` and `$facet` for `data`+`total` in one aggregation — filters/search span both collections (`status`/`email` on `users`; everything else on `students`), so a single combined pipeline avoids N+1 or an in-memory join (ARCHITECTURE.md §15). `search` matches `studentId`/`firstName`/`lastName`/`phone`/`alternatePhone` (student side, case-insensitive contains) and `email` (user side, case-insensitive prefix) via escaped `$regex`, not the Mongo text index (kept for potential future standalone use). CSV export is capped at 5,000 rows.
**Future Scalability:** at 10k+ students this collection scales linearly and predictably — no denormalization needed here since it's the leaf of the profile graph. The `$lookup`-based list query is the one thing worth revisiting first if student count grows much past that, since a join-per-page-request doesn't scale as cleanly as a single-collection query.

`counters`-collection mechanism as `students.studentId`) · `firstName`/`lastName` (string, required, ≤100) · `middleName`/`displayName` (string \| null) · `dateOfBirth` (Date \| null) · `gender` (enum \| null) · `preferredLanguage` (string \| null) · `bio` (string, ≤2000) · `phone`/`alternatePhone` (string \| null) · `address` (embedded, same shape as `students.address`) · `emergencyContacts` (embedded array, ≤5) · `designation`/`department` (string \| null) · `totalYearsExperience`/`teachingYearsExperience`/`industryYearsExperience` (number \| null) · `expertiseAreas`/`secondaryExpertise`/`skills`/`technologies`/`specializations` (string[]) · `linkedinUrl`/`portfolioUrl`/`githubUrl`/`websiteUrl` (string \| null) · `qualifications` (embedded array: `degree`, `institution`, `boardOrUniversity?`, `fieldOfStudy?`, `yearOfCompletion`, `gradeValue?`, `gradeType?`, `documentUrl?`, `documentPublicId?`) · `certifications` (embedded array: `name`, `issuingOrganization`, `credentialId?`, `issueDate`, `expiryDate?`, `verificationUrl?`, `documentUrl?`, `documentPublicId?`) · `joiningDate` (Date \| null) · `employmentType`/`employmentStatus` (enum) · `employeeCode`/`workLocation` (string \| null) · `reportingManagerId` (ObjectId ref `User` \| null) · `probationEndDate` (Date \| null) · `noticePeriodDays` (number \| null) · `preferredTeachingModes` (enum[], ≤3) · `preferredTimeSlots` (enum[], ≤4) · `maxConcurrentBatches`/`maxWeeklyTeachingHours` (number \| null) · `availabilityStatus` (enum) · `availabilityNotes` (string **Enum — `employmentType`:** `FULL_TIME` \| `PART_TIME` \| `CONTRACT` \| `VISITING` \| `FREELANCE`. **`employmentStatus`:** `ACTIVE` \| `ON_LEAVE` \| `INACTIVE` \| `TERMINATED`. **`availabilityStatus`:** `AVAILABLE` \| `LIMITED` \| `UNAVAILABLE`. **`preferredTeachingModes`:** `ONLINE` \| `OFFLINE` \| `HYBRID` (defined locally in `trainer.model.ts`, not imported from `batch.model.ts`, to avoid a premature cross-module dependency). **`availability[].type`:** `AVAILABLE` \| `PREFERRED` \| `BLOCKED`. **`profileCompletionStatus`:** `INCOMPLETE` \| `PARTIAL` \| `COMPLETE` (server-calculated, never client-writable — ARCHITECTURE.md §17).
**Indexes:** unique `{ userId: 1 }` (partial: `isDeleted: false`) · unique `{ trainerId: 1 }` (partial: `isDeleted: false`) · `{ department: 1 }` · `{ employmentStatus: 1 }` · `{ tags: 1 }` · `{ expertiseAreas: 1 }` · text `{ firstName, lastName }`.
**Relationships:** `userId → users` (1:1) · `reportingManagerId → users` (nullable). `address`/`emergencyContacts`/`qualifications`/`certifications`/`availability`/`documents` are **embedded**, not referenced — same rationale as `students`: small, bounded, always read/written with the parent document. `assignedCourseIds` remains a placeholder denormalized read cache for a future batches module, exactly as before this phase — its sync contract (owned by the batches service, not this module) is unchanged.
**Soft Delete:** Active in schema, but — matching `students`' precedent exactly — never toggled by the admin "delete trainer" action, which soft-deletes the linked **user** instead, preserving referential integrity for any future course/batch assignment referencing `Trainer._id`.
**Business/Ownership/Security:** `ADMIN`/`SUPER_ADMIN` manage any record via `trainers:read`/`trainers:manage`/`trainers:export`; sessions/audit-timeline access is `SUPER_ADMIN`-only. Trainer self-service editing of their own profile is **not yet built** (out of scope for Phase 7). No salary/compensation field exists in this schema at all — explicit scope exclusion, not just an unexposed field. CSV export excludes `notes` and any document/photo URLs.
**Query/Pagination/Search:** admin list/export uses the same `$lookup`+`$facet` aggregation pattern as `students` (ARCHITECTURE.md §17) — `search` matches `trainerId`/`firstName`/`lastName`/`phone`/`expertiseAreas` (trainer side) and `email` (user side). CSV export capped at 5,000 rows, same as students.
**Future Scalability:** same profile as `students` — stays small relative to student volume (PRD targets 500+ trainers), no scaling concern at current or projected scale.

### 3.3 Academic Structure

#### `courses` — **Admin management implemented (Phase 9A)**; curriculum/lessons/batches/enrolment still pending
**Purpose:** Top of the academic hierarchy — `Course → course_modules → lessons` (the latter two are not built yet). Phase 9A scope is course-level metadata and lifecycle only — no curriculum, no video, no batch/enrolment/certificate/payment relationship exists.
**Fields:** `courseCode` (string, required, unique, uppercased, immutable — server-generated, format `DM-CRS-{year}-{6-digit sequence}`, same `counters`-collection mechanism as `students.studentId`/`trainers.trainerId`) · `title` (string, required, ≤200) · `shortTitle` (string \| null, ≤80) · `slug` (string, required, unique, lowercased, ≤220, auto-normalized/deduped from `title` if not explicitly provided) · `shortDescription` (string, ≤300) · `description` (string, ≤10,000) · `category` (string, required, ≤100 — plain validated string, not a foreign-key relationship, see ARCHITECTURE.md §19 ADR) · `subcategory` (string \| null, ≤100) · `level` (enum, required) · `language` (string, default `'en'`) · `secondaryLanguages` (string[]) · `tags` (string[]) · `durationValue` (number \| null) · `durationUnit` (enum \| null) · `deliveryMode` (enum, required) · `learningOutcomes`/`skills`/`prerequisites` (string[]) · `targetAudience`/`eligibilityCriteria` (string \| null, ≤500) · `certificateEnabled` (boolean) · `maxStudentCapacity` (number \| null, min 1) · `pricing` (embedded, see below) · `visibility` (enum, default `PRIVATE`) · `status` (enum, default `DRAFT` — the shared `ApprovalStatus` enum also used by assignments/quizzes/examinations) · `isFeatured` (boolean) · `featuredOrder` (number \| null) · `metaTitle` (string \| null, ≤70) · `metaDescription` (string \| null, ≤160) · `canonicalUrl` (string \| null, ≤500) · `thumbnailUrl`/`thumbnailPublicId`/`bannerUrl`/`bannerPublicId` (string \| null — Cloudinary signed-upload refs) · `promoVideoUrl` (string \| null — **dormant**, no course-video upload flow built this phase) · `eligibleTrainerIds` (ObjectId[] ref `Trainer`, default `[]` — metadata only, not a real assignment, see below) · `internalNotes` (string \| null, ≤2000) · `publishedAt`/`archivedAt` (Date \| null).
**`pricing` (embedded, no `_id`):** `pricingType` (enum, default `FREE`) · `currency` (enum, default `INR`) · `basePrice` (number, required, default `0`, min 0) · `discountPrice` (number \| null, min 0) · `taxInclusive` (boolean) · `saleStartsAt`/`saleEndsAt` (Date \| null). No payment-gateway/checkout/invoice fields exist — this is pricing *metadata* only.
**Enum — `level`:** `BEGINNER` \| `INTERMEDIATE` \| `ADVANCED` \| `ALL_LEVELS`. **`deliveryMode`:** `ONLINE` \| `OFFLINE` \| `HYBRID` \| `SELF_PACED`. **`durationUnit`:** `HOURS` \| `DAYS` \| `WEEKS` \| `MONTHS`. **`pricing.pricingType`:** `FREE` \| `PAID`. **`visibility`:** `PRIVATE` \| `INTERNAL` \| `PUBLIC`. **`status`:** `DRAFT` \| `PUBLISHED` \| `ARCHIVED` (shared `ApprovalStatus`).
**Indexes:** unique `{ courseCode: 1 }` (partial: `isDeleted: false`) · unique `{ slug: 1 }` (partial: `isDeleted: false`) · `{ status: 1, category: 1 }` · `{ level: 1 }` · `{ visibility: 1 }` · `{ isFeatured: 1, featuredOrder: 1 }` · `{ tags: 1 }` · text `{ title, description, tags, skills }`.
**Relationships:** parent of `course_modules`, `lessons` (denormalized `courseId`), and — as of Phase 10A — `batches` (`courseId`, required, immutable). Still-intended parent of `assignments`, `quizzes`, `examinations`, none of which are built yet. `eligibleTrainerIds → trainers` is a separate, batch-independent reference: a validated (must exist, active, non-deleted) list of trainers a course *could* be taught by — metadata only; a batch's own `primaryTrainerId` is validated against this list only when it is non-empty (ARCHITECTURE.md §19, §22).
**Soft Delete:** Active — published courses may eventually have historical `enrollments`/`certificates` referencing them; hard-delete would orphan those once those collections exist. `isDeleted`/`deletedAt`/`restore` are orthogonal to lifecycle `status` — see the "restore" ADR in ARCHITECTURE.md §19.
**Business/Ownership/Security:** `DRAFT` courses never appear in any future student-facing catalog query (service-layer filter on `status: 'PUBLISHED'`, not yet built); `ADMIN`/`SUPER_ADMIN` manage courses via `courses:read`/`courses:manage`/`courses:publish`/`courses:export`. Publication is gated by `checkReadiness()` — a course cannot move to `PUBLISHED` while structurally incomplete (missing description/duration/learning outcomes/thumbnail). CSV export excludes `internalNotes` and any Cloudinary credentials, and escapes every field against CSV-formula injection; capped at 5,000 rows.
**Query/Pagination/Search:** admin list/export is a **plain `find().sort().skip().limit()`** — unlike `students`/`trainers`, a course needs no `users` join, so no `$lookup`+`$facet` aggregation is needed (ARCHITECTURE.md §19). `search` matches `title`/`courseCode`/`category`/`tags` via escaped `$regex`, not the Mongo text index (kept for potential future standalone catalog-search use). Filters/sorts are allowlisted, not arbitrary client-supplied fields.
**Future Scalability:** at 1,000+ courses, the text index remains adequate; a dedicated search service (e.g. Atlas Search) is a future upgrade if relevance quality becomes a problem, not a schema change.

#### `course_modules` — **Structure implemented (Phase 9B)**; no learning-content delivery yet
**Purpose:** Named grouping of lessons within a course's curriculum tree.
**Fields:** `courseId` (ObjectId ref `Course`, required) · `title` (string, required, ≤200) · `description` (string, default `''`, ≤2000) · `order` (number, required — server-controlled, see below) · `status` (enum, default `DRAFT` — the same shared `ApprovalStatus` `courses` uses, independent of the parent course's own `status`) · `estimatedDurationMinutes` (number \| null).
**Enum — `status`:** `DRAFT` \| `PUBLISHED` \| `ARCHIVED` (shared `ApprovalStatus`).
**Indexes:** `{ courseId: 1, order: 1 }` · `{ courseId: 1, status: 1 }` · `{ courseId: 1, isDeleted: 1 }`.
**Relationships:** `courseId → courses`; parent of `lessons`.
**Soft Delete:** Active — deleting a module cascades a soft-delete to its then-active lessons in one transaction, tombstoning them (`Lesson.deletedWithModule: true`) so restoring the module restores only the lessons it deleted, never one that was already independently deleted beforehand (ARCHITECTURE.md §20).
**Business/Ownership/Security:** `order` uniqueness is **not** enforced at the schema level — a bulk reorder would otherwise need a transaction just to avoid a transient duplicate-key error, though reorder operations *do* run inside a real MongoDB transaction now (the first in this codebase) for atomicity across the whole batch. `order` is never client-settable through the plain create/update endpoints — create always appends, and repositioning only happens through the dedicated reorder endpoint, which requires the payload to name every current active sibling exactly once. `courses:manage` (reused, no new `curriculum:*` permission) gates all writes; writes are additionally blocked while the parent course is `ARCHIVED` (reads still allowed).
**Query/Pagination/Search:** "modules for course X, in order" — small bounded list per course, no pagination needed; no search.
**Future Scalability:** none — bounded by course structure, never grows independently.

#### `lessons` — **Structure implemented (Phase 9B); learning content implemented (Phase 9C)**
**Purpose:** Individual structural unit within a course module — structure/sequencing plus, as of Phase 9C, its actual content.
**Fields:** `courseModuleId` (ObjectId ref `CourseModule`, required) · `courseId` (ObjectId ref `Course`, required — see below) · `title` (string, required, ≤200) · `shortDescription` (string, default `''`, ≤500) · `order` (number, required — server-controlled) · `lessonType` (enum, required — structural classification, and the discriminator selecting which content field below is populated) · `status` (enum, default `DRAFT`) · `estimatedDurationMinutes` (number \| null) · `isPreview` (boolean, default `false` — free preview lesson) · `isMandatory` (boolean, default `true`) · `prerequisiteLessonIds` (ObjectId[] ref `Lesson`, default `[]` — structure metadata only, no student unlock/progress enforcement this phase) · `contentStatus` (enum, default `EMPTY` — **server-computed only**, never client-writable, see below) · `textContent` (string \| null — sanitized HTML, populated only when `lessonType === 'TEXT'`) · `videoAsset` (embedded \| null, see below — populated only when `lessonType === 'VIDEO'`) · `documentAsset` (embedded \| null, see below — populated only when `lessonType === 'DOCUMENT'`) · `externalLink` (embedded \| null, see below — populated only when `lessonType === 'EXTERNAL_LINK'`) · `deletedWithModule` (boolean, default `false` — tombstone, see `course_modules` above).
**`videoAsset` (embedded, no `_id`):** `provider` (`'cloudinary'`) · `publicId`/`assetId` (string, required — internal, never returned to the frontend) · `resourceType` (`'video'`) · `format` (string) · `durationSeconds`/`width`/`height` (number \| null) · `bytes`/`version` (number) · `status` (enum: `UPLOADING` \| `PROCESSING` \| `READY` \| `FAILED` — this phase's synchronous verify flow only ever writes `READY`; the other values are reserved for a future async-transcoding integration) · `uploadedAt` (Date).
**`documentAsset` (embedded, no `_id`):** `provider`/`publicId`/`assetId`/`format`/`bytes`/`version` (same shape as `videoAsset`, minus video-specific fields) · `originalFilename` (string — the one client-reported field in either asset, cosmetic display only) · `uploadedAt` (Date).
**`externalLink` (embedded, no `_id`):** `url` (string, required, server-validated http(s)-only) · `label`/`description` (string \| null) · `openInNewTab` (boolean, default `true`).
**Enum — `lessonType`:** `VIDEO` \| `TEXT` \| `DOCUMENT` \| `LIVE_CLASS` \| `QUIZ` \| `ASSIGNMENT` \| `EXTERNAL_LINK`. **`status`:** `DRAFT` \| `PUBLISHED` \| `ARCHIVED` (shared `ApprovalStatus`). **`contentStatus`:** `EMPTY` \| `INCOMPLETE` \| `READY` \| `PROCESSING` \| `ERROR` \| `NOT_CONFIGURED` (the last reserved for `LIVE_CLASS`/`QUIZ`/`ASSIGNMENT`, which have no content model yet).
**Indexes:** `{ courseModuleId: 1, order: 1 }` · `{ courseId: 1, courseModuleId: 1 }` · `{ courseId: 1, status: 1 }` · `{ courseId: 1, isDeleted: 1 }` · `{ courseId: 1, contentStatus: 1 }` (Phase 9C — course launch-readiness's "any published lesson not READY" check).
**Relationships:** `courseModuleId → course_modules`. `courseId` is a **deliberate denormalization** of `courseModuleId.courseId` — read patterns like "all lessons in course X" would otherwise require a join through `course_modules` on every read; kept in sync at creation time and by the dedicated move endpoint (a lesson only ever moves between modules *within* the same course — moving across courses is structurally rejected, since the target module lookup is scoped to the source lesson's own `courseId`). `prerequisiteLessonIds → lessons` (self-referential): validated on every write to exclude self-reference, cross-course references, missing/deleted lessons, and cycles (direct and indirect) — `utils/curriculum-prerequisite.util.ts`.
**Soft Delete:** Active. Deleting a single lesson compacts the remaining siblings' `order` in the same transaction; restoring an independently-deleted lesson re-appends it to the end of its module (not its old position, which may since be occupied).
**Business/Ownership/Security:** Phase 9A's `isPublished`/`durationSeconds` scaffold fields are *replaced* by `status`/`estimatedDurationMinutes`; Phase 9C additively replaces the Phase 1 scaffold's dormant `contentType`/`contentUrl` with the typed content fields above (zero consumers existed for either replaced pair before their respective phase, verified before changing them — same replace-don't-duplicate precedent `courses.durationHours`→`durationValue`+`durationUnit` set). `courses:manage` gates structural and content writes, `courses:publish` gates the publish/unpublish actions specifically; writes blocked while the parent course is `ARCHIVED`. Changing `lessonType` on a lesson with existing content is rejected (`409`) unless the request also sets `confirmContentReset: true`, which then clears all four content fields in the same write.
**Query/Pagination/Search:** "lessons in module X, ordered" and "lessons in course X" (via denormalized `courseId`) — both small bounded lists (task's stated scale: 100-500 lessons per course), fetched in one query each for the whole-course curriculum tree endpoint (never N+1 per module); no search (discovery happens at the course level).
**Future Scalability:** none — bounded by curriculum size at the stated scale. `textContent` is capped well below any risk of approaching MongoDB's 16MB document limit (200,000-character pre-sanitization input cap, enforced at the validator).

#### `lesson_resources` — **Implemented (Phase 9C)**
**Purpose:** Downloadable materials attached to a lesson (slides, code samples, PDFs, archives, images) — independent of the lesson's own primary content.
**Fields:** `lessonId` (ObjectId ref `Lesson`, required) · `courseId` (ObjectId ref `Course`, required — denormalized, same rationale as `lessons.courseId`) · `title` (string, required, ≤200) · `description` (string \| null, ≤1000) · `resourceType` (enum, required — server-derived from the verified Cloudinary asset's format, never client-supplied) · `provider` (`'cloudinary'`) · `publicId`/`assetId` (string, required — internal, never returned to the frontend) · `filename` (string, required, ≤255 — client-reported, cosmetic display only) · `format` (string, required) · `mimeType` (string, required — server-derived from `format`) · `bytes` (number, required) · `sortOrder` (number, default `0`) · `isDownloadable` (boolean, default `true`).
**Enum — `resourceType`:** `PDF` \| `DOCUMENT` \| `SLIDES` \| `ARCHIVE` \| `IMAGE` \| `OTHER` — executable/installer formats are never mapped to any value here (verification rejects them outright).
**Indexes:** `{ lessonId: 1, sortOrder: 1 }` · `{ courseId: 1, lessonId: 1 }` · `{ lessonId: 1, isDeleted: 1 }`.
**Relationships:** `lessonId → lessons`, `courseId → courses`. Kept as its own **collection**, not embedded in `lessons` — unlike `assignments.attachments` (embedded), a lesson's resources are added/removed independently over time, can be numerous (bounded by `MAX_RESOURCES_PER_LESSON`, default 20), and embedding an unbounded array on `lessons` would also risk that document's 16MB limit.
**Soft Delete:** Active — deleting a resource soft-deletes the record and best-effort-deletes the underlying Cloudinary asset by its known `publicId` (never a client-supplied one).
**Business/Ownership/Security:** `courses:read`/`courses:manage` (reused, no new permission) gate reads/writes, matching the parent lesson's own permission model. Every asset is uploaded `type: 'authenticated'` (never publicly reachable) and independently re-verified against Cloudinary before the record is created — see ARCHITECTURE.md §21.
**Query/Pagination/Search:** "resources for lesson X, ordered" — small bounded list (max 20), no pagination; no search.
**Future Scalability:** none — bounded by the per-lesson cap.

#### `batches` — **Admin management implemented (Phase 10A)**; enrolment/roster/attendance/live-classes still pending
**Purpose:** A scheduled delivery *instance* of a course — "when and how" (ARCHITECTURE.md §22), as distinct from the course's own "what." Replaces the Phase 1 scaffold entirely (zero real consumers before this phase — verified). Capacity fields this phase are **configuration only** — there is no `enrolledCount` or any other seat-occupancy field; Phase 10B is expected to add real enrolment tracking without touching this shape.
**Fields:** `batchCode` (string, required, unique, uppercased, immutable — server-generated, format `DM-BAT-{year}-{6-digit sequence}`, same `counters`-collection mechanism as `courses.courseCode`) · `courseId` (ObjectId ref `Course`, required, immutable after creation) · `name` (string, required, ≤150) · `shortName` (string \| null, ≤60) · `description` (string, default `''`, ≤2000) · `startDate`/`endDate` (Date \| null — nullable by design, see ARCHITECTURE.md §22) · `enrollmentOpenDate`/`enrollmentCloseDate` (Date \| null — metadata only, no enrolment flow reads these yet) · `timezone` (string, required — IANA identifier, validated via the shared `Intl.DateTimeFormat`-based `isValidTimeZone` utility) · `deliveryMode` (enum, required — deliberately excludes `SELF_PACED`, unlike `courses.deliveryMode`: a batch is by definition a scheduled delivery instance) · `status` (enum, default `DRAFT` — explicit state machine, see below) · `primaryTrainerId` (ObjectId \| null ref `Trainer`) · `assistantTrainerIds` (ObjectId[] ref `Trainer`, default `[]`) · `maxStudents` (number, required, min 1, max 10,000) · `minimumStudents` (number \| null, min 0) · `waitlistEnabled` (boolean, default `false` — config only, no waiting-list records exist) · `location` (embedded, see below) · `weeklySchedule` (embedded array, see below) · `calendarExceptions` (embedded array, see below) · `tags` (string[]) · `internalNotes` (string \| null, ≤2000) · `scheduledAt`/`activatedAt`/`completedAt`/`cancelledAt`/`archivedAt` (Date \| null — set by their corresponding lifecycle action).
**`location` (embedded, no `_id`):** `meetingProvider` (enum \| null — placeholder only, never a real credential/link) · `virtualClassNotes` (string \| null, ≤500) · `venueName`/`addressLine1`/`addressLine2`/`city`/`state`/`postalCode`/`country`/`room` (string \| null) · `mapUrl` (string \| null, https-only). Fields are mode-*aware* but not mode-*exclusive* at the schema level — which fields matter for which `deliveryMode` is validator/readiness logic, not a schema branch (a `HYBRID` batch genuinely needs both halves).
**`weeklySchedule[]` (embedded, no `_id` per item):** `dayOfWeek` (enum, required) · `startTime`/`endTime` (string, required — plain `"HH:mm"` wall-clock, paired with the batch's own `timezone`, deliberately never converted to UTC — see ARCHITECTURE.md §22) · `sessionLabel`/`locationOverride` (string \| null) · `deliveryModeOverride` (enum \| null). Template recurring-timetable metadata only — never generates an actual live-class/session record. Max 30 slots; validator rejects same-day time overlaps.
**`calendarExceptions[]` (embedded, no `_id` per item):** `date` (Date, required) · `type` (enum, default `HOLIDAY`) · `title` (string, required, ≤150) · `note` (string \| null, ≤500). Simple date exclusions — no makeup classes, no generated sessions. Max 100 entries; validator rejects duplicate dates.
**Enum — `status`:** `DRAFT` \| `SCHEDULED` \| `ACTIVE` \| `COMPLETED` \| `CANCELLED` \| `ARCHIVED` — explicit state machine (ARCHITECTURE.md §22), never system-date-driven. **`deliveryMode`:** `ONLINE` \| `OFFLINE` \| `HYBRID`. **`location.meetingProvider`:** `GOOGLE_MEET` \| `ZOOM` \| `TEAMS` \| `OTHER`. **`weeklySchedule.dayOfWeek`:** `MONDAY`…`SUNDAY` (defined locally, not imported from `trainers.availability` — separate module boundaries, coincidental value overlap). **`calendarExceptions.type`:** `HOLIDAY` \| `NO_CLASS` \| `INSTITUTE_CLOSED` \| `TRAINER_UNAVAILABLE` \| `OTHER`.
**Indexes:** unique `{ batchCode: 1 }` (partial: `isDeleted: false`) · `{ courseId: 1, status: 1 }` · `{ primaryTrainerId: 1, status: 1 }` · `{ startDate: 1, endDate: 1 }` · `{ status: 1, startDate: 1 }` · `{ isDeleted: 1, status: 1 }` · `{ tags: 1 }` · text `{ name, batchCode }`. Query-driven only — no speculative indexes beyond what list/filter/conflict-detection queries actually need.
**Relationships:** `courseId → courses` (must exist, not soft-deleted at write time; must be `PUBLISHED` to move to `SCHEDULED`). `primaryTrainerId`/`assistantTrainerIds → trainers` — primary must additionally belong to the course's `eligibleTrainerIds` when that list is non-empty (empty list = no restriction). Intended future parent of `enrollments`, `attendance`, `live_classes` — none of those collections reference `batches` yet.
**Soft Delete:** Active — `isDeleted`/`deletedAt`, orthogonal to lifecycle `status`, same convention every other module uses. Guarded through the same service layer Phase 10B can later extend to block deletion when active enrolments exist, without a schema change.
**Business/Ownership/Security:** `ADMIN`/`SUPER_ADMIN` manage batches via `batches:read`/`batches:manage`/`batches:export` (`batches:manage` covers every lifecycle transition — no separate lifecycle permission); `TRAINER`/`STUDENT` get none. Lifecycle transitions only ever happen through dedicated `POST /:id/lifecycle/{action}` endpoints, never a generic `PATCH` — `batchCode`/`courseId`/`status` are never accepted by the update endpoint (`.strict()` Zod schema). Scheduling is gated by a backend-authoritative readiness check (course published, dates/trainer/schedule/location present and valid, no trainer availability/double-booking conflict). CSV export excludes `internalNotes` and the full venue address, escapes every field against CSV-formula injection, capped at 5,000 rows.
**Query/Pagination/Search:** admin list filtered by status/courseId/primaryTrainerId/deliveryMode/timezone/date-range/temporal(`upcoming`\|`current`\|`past`)/capacity-range/waitlistEnabled, offset-paginated; `search` matches `batchCode`/`name` via escaped `$regex`. Filters/sorts allowlisted, not arbitrary client-supplied fields. Trainer-conflict detection queries are indexed (`{primaryTrainerId,status}`, date range), never a full collection scan.
**Future Scalability:** none at V1 scale — bounded the same way `courses` is (thousands of courses × a handful of batches each).

### 3.4 Enrollment & Progress

#### `enrollments` — **Backend implemented (Phase 10B Part 1)**; admin UI still pending (Part 2)
**Purpose:** A student's membership in one batch — the authorization bridge between student identity and learning access (ARCHITECTURE.md §23). Replaces the Phase 1 4-state scaffold entirely (zero real consumers, verified before touching it).
**Fields:** `enrollmentCode` (string, required, unique, uppercased, immutable — server-generated, format `DM-ENR-{year}-{6-digit sequence}`, same `counters`-collection mechanism as `batches.batchCode`) · `studentId` (ObjectId ref `Student`, required) · `batchId` (ObjectId ref `Batch`, required) · `courseId` (ObjectId ref `Course`, required — always server-derived from the batch at write time, never trusted from a client) · `status` (enum, default `PENDING` — explicit 8-state lifecycle, see below) · `source` (enum, default `ADMIN`) · `enrollmentDate` (Date, default now) · `waitlistPosition` (number \| null — a monotonic per-batch sequence value, never renumbered) · `waitlistedAt`/`confirmedAt`/`activatedAt`/`suspendedAt`/`resumedAt`/`completedAt`/`cancelledAt`/`droppedAt` (Date \| null, set by their corresponding lifecycle action) · `accessStartsAt`/`accessEndsAt` (Date \| null — the access-window entitlement pair, see below) · `transferredFromEnrollmentId`/`transferredToEnrollmentId` (ObjectId \| null, self-referential) · `transferReason`/`cancellationReason`/`dropReason` (string \| null, ≤500) · `internalNotes` (string \| null, ≤2000) · `tags` (string[]).
**Enum — `status`:** `PENDING` \| `WAITLISTED` \| `CONFIRMED` \| `ACTIVE` \| `SUSPENDED` \| `COMPLETED` \| `CANCELLED` \| `DROPPED` — explicit state machine (`utils/enrollment-lifecycle.util.ts`), never a generic PATCH target. **`source`:** `ADMIN` \| `BULK_IMPORT` \| `TRANSFER` \| `SELF_SERVICE` (reserved, unwritten) \| `API` (reserved, unwritten).
**Seat-consuming statuses:** `CONFIRMED`/`ACTIVE`/`SUSPENDED` only (`doesEnrollmentConsumeSeat`) — `PENDING`/`WAITLISTED` and every terminal status never hold a seat. **Terminal statuses:** `COMPLETED`/`CANCELLED`/`DROPPED`.
**Indexes:** unique `{ enrollmentCode: 1 }` (partial: `isDeleted: false`) · unique `{ studentId: 1, batchId: 1 }` (partial: `isDeleted: false` — a hard integrity backstop; the real non-terminal-duplicate rule is enforced at the service layer, see below) · `{ batchId: 1, status: 1 }` · `{ studentId: 1, status: 1 }` · `{ studentId: 1, courseId: 1, status: 1 }` · `{ courseId: 1, status: 1 }` · `{ createdAt: 1 }` · `{ batchId: 1, waitlistedAt: 1, waitlistPosition: 1 }`.
**Relationships:** `studentId → students`, `batchId → batches`, `courseId → courses` (denormalized from the batch, never independently settable). `transferredFromEnrollmentId`/`transferredToEnrollmentId → enrollments` (self-referential transfer lineage). Intended future parent of `lesson_progress`, `quiz_attempts` — neither references `enrollments` yet.
**Soft Delete: Deliberately avoided in routine operation.** Lifecycle status carries history — cancellation/dropping/completion are status transitions, never a deletion; academic history must survive them. `isDeleted`/`deletedAt` exist for schema consistency (every collection in this app has them) but no delete endpoint is exposed at all in Part 1.
**Business/Ownership/Security:** `ADMIN`/`SUPER_ADMIN` manage enrollments via `enrollments:read`/`enrollments:manage`/`enrollments:export` (`enrollments:manage` covers every lifecycle action including transfer); `TRAINER`/`STUDENT` get none this phase. At most one *non-terminal* enrollment exists per student+batch (service-layer check, richer than the unique index) and at most one non-terminal enrollment per student+course across all its batches (same-course transfer is the only supported move between batches). Duplicate/cross-course/capacity-bypass/lifecycle-bypass are all validated server-side — see SECURITY.md §3.
**Query/Pagination/Search:** admin list filtered by status/studentId/batchId/courseId/source/date-range, offset-paginated, `$lookup`-joined with `students`/`users`/`batches`/`courses` for display fields (mirrors `students.repository.ts`'s `$lookup`+`$facet` pattern) — `search` matches enrollment code/student name/batch code/batch name/course code/course title via escaped `$regex` post-lookup. Every ObjectId-typed filter (`studentId`/`batchId`/`courseId`) is explicitly cast to `Types.ObjectId` before the aggregation `$match` — aggregation pipelines do not auto-cast the way `find()` does (a real bug found and fixed by the test suite, ARCHITECTURE.md §23).
**Future Scalability:** grows linearly with (students × courses taken) — comfortably within a single collection at PRD's stated 10k-student scale.

**Capacity/waitlist fields added to `batches` this phase (Phase 10A shipped with neither):** `occupiedSeats` (number, default `0`, min `0`) and `waitlistSequence` (number, default `0`, min `0`) — server-managed derived state, never client-writable, never generically PATCH-able. `occupiedSeats` is mutated exclusively via an atomic `findOneAndUpdate` using `$expr: {$lt: ['$occupiedSeats', '$maxStudents']}` (single-document atomicity closes the last-seat race at the database level — see ARCHITECTURE.md §23), always inside a transaction alongside the owning enrollment write. `waitlistSequence` is a monotonic per-batch counter for stable waitlist positions, atomically incremented the same way. No index was added for either — both are point-read/atomic-write fields on an already-indexed document.
**Access entitlement fields added to `enrollments`:** `accessStartsAt`/`accessEndsAt`, a nullable window (`null` end = open/lifetime access) consolidating what the task originally proposed as separate `accessGrantedAt`/`accessRevokedAt` fields — see ARCHITECTURE.md §23 for the full reasoning (the PRD does not resolve whether course access should end when a batch does).

#### `lesson_progress`
**Purpose:** One document per student per lesson — the source of truth for course-completion percentage.
**Fields:** `studentId` (ObjectId ref `Student`, required) · `lessonId` (ObjectId ref `Lesson`, required) · `enrollmentId` (ObjectId ref `Enrollment`, required) · `status` (enum, default `NOT_STARTED`) · `watchedSeconds` (number, default `0`) · `lastWatchedAt`/`completedAt` (Date \| null).
**Enum — `status`:** `NOT_STARTED` \| `IN_PROGRESS` \| `COMPLETED`.
**Indexes:** unique `{ studentId: 1, lessonId: 1 }` · `{ enrollmentId: 1 }`.
**Relationships:** `studentId → students`, `lessonId → lessons`, `enrollmentId → enrollments`.
**Soft Delete:** Dormant — a progress record has no meaningful "deleted" state; it's overwritten (updated), never removed.
**Business/Ownership/Security:** written only by the requesting student's own client session (their own `studentId`, enforced server-side, never trusting a client-supplied `studentId`); read by the student themselves, their assigned trainer, and admins.
**Query/Pagination/Search:** highest write-volume collection alongside `notifications` (updated on every video-progress heartbeat) — but bounded (one doc per student per lesson, not per event), so no pagination concern; "my progress in course X" aggregates across `lessonId`s via `enrollmentId`.
**Future Scalability:** write-heavy — if heartbeat frequency becomes a bottleneck, batching progress writes client-side (e.g. every 15s instead of continuously) is the mitigation, not a schema change.

#### `live_classes`
**Purpose:** A scheduled real-time session for a batch.
**Fields:** `batchId` (ObjectId ref `Batch`, required) · `title` (string, required, ≤200) · `scheduledStart`/`scheduledEnd` (Date, required) · `providerSessionId` (string \| null — opaque vendor ID) · `joinUrl`/`recordingUrl` (string \| null) · `status` (enum, default `SCHEDULED`).
**Enum — `status`:** `SCHEDULED` \| `LIVE` \| `COMPLETED` \| `CANCELLED`.
**Indexes:** `{ batchId: 1, scheduledStart: 1 }` · `{ status: 1, scheduledStart: 1 }`.
**Relationships:** `batchId → batches`; referenced by `attendance.liveClassId` (nullable).
**Soft Delete:** Active (a cancelled session is `status: CANCELLED`, not deleted — `isDeleted` reserved for genuine data cleanup).
**Business/Ownership/Security:** intentionally has **no vendor-specific fields** — `providerSessionId`/`joinUrl` are opaque values from whichever managed video-conferencing vendor is eventually selected (ARCHITECTURE.md §9, pending), so swapping providers later is a service-layer change, not a migration.
**Query/Pagination/Search:** "upcoming classes for batch X" (`batchId`+`scheduledStart`), "today's live classes across all batches" (`status`+`scheduledStart`) for a scheduling dashboard; no search.
**Future Scalability:** none — bounded by batch schedule density.

### 3.5 Assessment

#### `attendance`
**Purpose:** One record per student per session date.
**Fields:** `batchId` (ObjectId ref `Batch`, required) · `liveClassId` (ObjectId ref `LiveClass` \| null) · `sessionDate` (Date, required) · `studentId` (ObjectId ref `Student`, required) · `status` (enum, required).
**Enum — `status`:** `PRESENT` \| `ABSENT` \| `LATE` \| `EXCUSED`.
**Indexes:** unique `{ batchId: 1, sessionDate: 1, studentId: 1 }` · `{ studentId: 1, sessionDate: -1 }`.
**Relationships:** `batchId → batches`, `liveClassId → live_classes` (optional link for online sessions), `studentId → students`. **No separate `markedBy` field** — the audit plugin's `createdBy` already captures who marked it and `updatedBy` who last corrected it; a duplicate field would only invite drift (§2 item 6).
**Soft Delete:** Active (a correction is more commonly an update to `status`, but a mistaken record can be soft-deleted).
**Business/Ownership/Security:** only the assigned trainer for that `batchId` (or an admin) can mark/correct attendance — ownership check required, role alone is insufficient (SECURITY.md §3, IDOR prevention).
**Query/Pagination/Search:** "attendance % for student X" and "roster for session Y" both hit the compound indexes directly; no pagination needed (bounded by batch size/session count); no search.
**Future Scalability:** grows linearly with (batches × sessions × roster size) — comfortably bounded.

#### `assignments`
**Purpose:** A graded task issued to a batch.
**Fields:** `batchId` (ObjectId ref `Batch`, required) · `courseId` (ObjectId ref `Course`, required — denormalized) · `title` (string, required, ≤200) · `description` (string, ≤5000) · `attachments` (embedded array: `url`, `fileName`, `fileType`) · `dueDate` (Date, required) · `maxScore` (number, required) · `allowLateSubmission` (boolean, default `false`) · `status` (enum, default `DRAFT`).
**Enum — `status`:** `DRAFT` \| `PUBLISHED` \| `ARCHIVED`.
**Indexes:** `{ batchId: 1, dueDate: 1 }` · `{ courseId: 1 }`.
**Relationships:** `batchId → batches`, `courseId → courses`; parent of `assignment_submissions`. `attachments` is **embedded** (fixed at creation, rarely modified) — contrast with `lesson_resources`, a full collection because those are added/removed independently over time.
**Soft Delete:** Active.
**Business/Ownership/Security:** `DRAFT` assignments are invisible to students; only the assigned trainer (or admin) can publish/edit.
**Query/Pagination/Search:** "assignments due soon for batch X" (`batchId`+`dueDate`), "all assignments in course X" (`courseId`); no pagination needed at per-batch scale; no search.
**Future Scalability:** none.

#### `assignment_submissions`
**Purpose:** One document per student per assignment — a resubmission (before grading) updates this same document.
**Fields:** `assignmentId` (ObjectId ref `Assignment`, required) · `studentId` (ObjectId ref `Student`, required) · `submittedAt` (Date, default now) · `attachments` (embedded array, same shape as `assignments.attachments`) · `score` (number \| null) · `feedback` (string \| null, ≤3000) · `status` (enum, default `SUBMITTED`) · `gradedBy` (ObjectId ref `User` \| null) · `gradedAt` (Date \| null).
**Enum — `status`:** `SUBMITTED` \| `LATE` \| `GRADED`.
**Indexes:** unique `{ assignmentId: 1, studentId: 1 }` · `{ studentId: 1, status: 1 }`.
**Relationships:** `assignmentId → assignments`, `studentId → students`. `gradedBy`/`gradedAt` are kept **explicit**, not just relying on the audit plugin's `updatedBy` — grading is a distinct, significant lifecycle event that a later unrelated update (e.g. a metadata fix) must not be able to obscure (§2 item 6's stated exception).
**Soft Delete:** Dormant — a submission is corrected via resubmission (same document, unique index enforces this) or regraded, never deleted.
**Business/Ownership/Security:** a student can create/update only their own submission (and only before `status: GRADED`, service-layer enforced); grading is trainer/admin-only.
**Query/Pagination/Search:** "my submission for assignment X" (unique index direct hit); "ungraded submissions for assignment X" (`assignmentId`+`status`); no search.
**Future Scalability:** none — bounded by (students × assignments).

#### `quizzes`
**Purpose:** A configured assessment drawing from the `questions` bank.
**Fields:** `courseId` (ObjectId ref `Course`, required) · `courseModuleId` (ObjectId ref `CourseModule` \| null) · `title` (string, required, ≤200) · `description` (string, ≤2000) · `questionIds` (ObjectId[] ref `Question`, ordered) · `totalMarks`/`passingMarks` (number, required) · `timeLimitMinutes` (number \| null) · `maxAttempts` (number, default `1`) · `status` (enum, default `DRAFT`).
**Indexes:** `{ courseId: 1 }` · `{ courseModuleId: 1 }`.
**Relationships:** `courseId → courses`, `courseModuleId → course_modules`, `questionIds → questions` (**referenced, not embedded** — see §2 item 3).
**Soft Delete:** Active.
**Business/Ownership/Security:** `DRAFT` quizzes are invisible to students; `questionIds` order is the display order (service layer may randomize per-attempt without touching this array).
**Query/Pagination/Search:** "quizzes in course/module X" — small bounded lists; no search.
**Future Scalability:** none.

#### `questions`
**Purpose:** Standalone, reusable question bank — referenced by both `quizzes` and `examinations`.
**Fields:** `courseId` (ObjectId ref `Course` \| null — nullable to support a general/cross-course bank) · `type` (enum, required) · `text` (string, required, ≤2000) · `options` (embedded array: `text`, `isCorrect` — for MCQ types) · `correctAnswerText` (string \| null — for `SHORT_ANSWER`) · `marks` (number, required) · `difficulty` (enum \| null) · `explanation` (string \| null — shown post-attempt) · `tags` (string[]).
**Enum — `type`:** `MCQ_SINGLE` \| `MCQ_MULTIPLE` \| `TRUE_FALSE` \| `SHORT_ANSWER`. **`difficulty`:** `EASY` \| `MEDIUM` \| `HARD`.
**Indexes:** `{ courseId: 1 }` · `{ type: 1 }` · `{ tags: 1 }` · text `{ text }`.
**Relationships:** referenced by `quizzes.questionIds` and `examinations.questionIds` — this is the one place in the schema where reuse across two parent collections makes referencing unambiguously correct over embedding: the same question can appear in many quizzes/exams, and editing it once must not require updating N embedded copies.
**Soft Delete:** Active, but service layer should warn (not block) when deleting a question still referenced by a published quiz/exam.
**Business/Ownership/Security:** `correctAnswerText`/`options[].isCorrect` must never be sent to a student client before they've submitted an attempt (service-layer response shaping, not a schema concern — noted here because it's easy to get wrong with a naive "return the question object" endpoint).
**Query/Pagination/Search:** question-bank browsing by `courseId`+`type`+`tags`, offset-paginated; text search on `text` for bank management UIs.
**Future Scalability:** grows with content library size — comfortably within a single collection even at thousands of questions; the text index may need Atlas Search if the bank grows very large and free-text relevance matters.

#### `quiz_attempts`
**Purpose:** One document per student attempt at a quiz.
**Fields:** `quizId` (ObjectId ref `Quiz`, required) · `studentId` (ObjectId ref `Student`, required) · `enrollmentId` (ObjectId ref `Enrollment` \| null) · `answers` (embedded array — shared `IAttemptAnswer` shape, see below) · `score` (number \| null) · `attemptNumber` (number, required) · `startedAt` (Date, required) · `submittedAt` (Date \| null) · `status` (enum, default `IN_PROGRESS`).
**Enum — `status`:** `IN_PROGRESS` \| `SUBMITTED` \| `EXPIRED`.
**Indexes:** unique `{ quizId: 1, studentId: 1, attemptNumber: 1 }` · `{ studentId: 1, quizId: 1 }` (latest-attempt lookups).
**Relationships:** `quizId → quizzes`, `studentId → students`, `enrollmentId → enrollments`. `answers[].questionId → questions`.
**Soft Delete:** Dormant — an attempt is a permanent record of what happened; never deleted, only transitions `status`.
**Business/Ownership/Security:** a student may only create/update their own attempts, and only while `status: IN_PROGRESS`; `attemptNumber` cap (`quizzes.maxAttempts`) is enforced at the service layer, not the schema (retake policy is still a pending business rule — DATABASE.md §5 legacy item 3).
**Query/Pagination/Search:** "my attempts at quiz X" (unique index prefix); no pagination needed (bounded by `maxAttempts`); no search.
**Future Scalability:** grows with (students × quizzes × attempts) — bounded and predictable.

#### `examinations`
**Purpose:** Structurally close to `quizzes` but with stricter integrity needs — a fixed exam window and mandatory duration.
**Fields:** `courseId` (ObjectId ref `Course`, required) · `batchId` (ObjectId ref `Batch` \| null) · `title` (string, required, ≤200) · `questionIds` (ObjectId[] ref `Question`) · `totalMarks`/`passingMarks` (number, required) · `durationMinutes` (number, required) · `scheduledStart`/`scheduledEnd` (Date, required) · `maxAttempts` (number, default `1`) · `status` (enum, default `DRAFT`).
**Indexes:** `{ courseId: 1 }` · `{ batchId: 1, scheduledStart: 1 }`.
**Relationships:** `courseId → courses`, `batchId → batches`, `questionIds → questions`.
**Soft Delete:** Active.
**Business/Ownership/Security:** `durationMinutes`/time-boxing must be enforced server-side at attempt time (not modeled here — that's business logic for the exams module, not built in this task). Proctoring is explicitly out of scope for V1 (PROJECT-UNDERSTANDING-REPORT.md) — no proctoring fields exist.
**Query/Pagination/Search:** "exams scheduled for batch X" (`batchId`+`scheduledStart`); no search.
**Future Scalability:** none.

#### `examination_results`
**Purpose:** One document per student attempt at an examination.
**Fields:** `examinationId` (ObjectId ref `Examination`, required) · `studentId` (ObjectId ref `Student`, required) · `answers` (embedded array, shared `IAttemptAnswer` shape) · `score` (number \| null) · `passed` (boolean \| null) · `attemptNumber` (number, required) · `startedAt` (Date, required) · `submittedAt` (Date \| null) · `status` (enum, default `IN_PROGRESS`).
**Enum — `status`:** `IN_PROGRESS` \| `SUBMITTED` \| `EXPIRED` \| `DISQUALIFIED` (integrity-violation state — exams need this even though quizzes don't).
**Indexes:** unique `{ examinationId: 1, studentId: 1, attemptNumber: 1 }` · `{ studentId: 1, examinationId: 1 }`.
**Relationships:** `examinationId → examinations`, `studentId → students`. **This, not a separate `results` collection, is the durable record of exam outcomes** — the earlier design's generic `results` "materialized view" collection was folded in here since the explicit collection list doesn't include a standalone `results` collection; per-course final grade computation (if still needed) becomes a service-layer aggregation across `examination_results`, `assignment_submissions`, and `attendance`, not a stored document, avoiding a stale-cache-invalidation problem entirely.
**Soft Delete:** Dormant — permanent record.
**Business/Ownership/Security:** same ownership model as `quiz_attempts`; `DISQUALIFIED` can only be set by a trainer/admin (service-layer authorization), never by the student's own client.
**Query/Pagination/Search:** "my result for exam X"; "pass rate for exam X" (aggregation across `examinationId`); no search.
**Future Scalability:** bounded and predictable, same shape as `quiz_attempts`.

**Shared sub-shape — `IAttemptAnswer`** (used identically by `quiz_attempts.answers` and `examination_results.answers`, defined once in `src/models/shared/attempt-answer.schema.ts` to avoid duplicating the shape): `questionId` (ObjectId ref `Question`) · `selectedOptionIndexes` (number[]) · `answerText` (string \| null) · `isCorrect` (boolean \| null) · `marksAwarded` (number \| null).

### 3.6 Commerce

#### `invoices`
**Purpose:** What a student owes for an enrollment.
**Fields:** `studentId` (ObjectId ref `Student`, required) · `enrollmentId` (ObjectId ref `Enrollment` \| null) · `feeAmount` (number, required) · `currency` (enum, default `INR`) · `amountPaid` (number, default `0` — denormalized running total) · `status` (enum, default `UNPAID`) · `dueDate` (Date, required) · `gstDetails` (embedded: `gstin?`, `hsnCode?`, `taxAmount?` — all nullable).
**Enum — `status`:** `UNPAID` \| `PARTIALLY_PAID` \| `PAID` \| `OVERDUE`.
**Indexes:** `{ studentId: 1, status: 1 }` · `{ enrollmentId: 1 }`.
**Relationships:** `studentId → students`, `enrollmentId → enrollments`; parent of `payments`.
**Soft Delete:** Dormant — financial records are corrected via new documents/status transitions, never deleted.
**Business/Ownership/Security:** `gstDetails` fields are nullable by design — GST invoicing is an unconfirmed requirement (§5 legacy item 4); the shape is reserved so a future confirmation only populates previously-null fields, no migration needed.
**Query/Pagination/Search:** "my invoices" (`studentId`+`status`); admin "overdue invoices" (`status: OVERDUE`); no search.
**Future Scalability:** none at V1 scale.

#### `payments`
**Purpose:** A gateway transaction against an invoice.
**Fields:** `invoiceId` (ObjectId ref `Invoice`, required) · `studentId` (ObjectId ref `Student`, required) · `amount` (number, required) · `currency` (enum, default `INR`) · `gatewayProvider` (string, required, ≤60) · `gatewayTransactionId` (string, required, unique — the idempotency key) · `status` (enum, default `INITIATED`) · `rawGatewayPayload` (object, default `{}` — never contains raw card data, gateway-hosted checkout only, ARCHITECTURE.md §10) · `refundedAmount` (number, default `0`) · `paidAt` (Date \| null).
**Enum — `status`:** `INITIATED` \| `SUCCESS` \| `FAILED` \| `REFUNDED`.
**Indexes:** unique `{ gatewayTransactionId: 1 }` (the idempotency guarantee — enforced at the database layer, not just application logic, API-STANDARDS.md §8) · `{ studentId: 1, status: 1 }` · `{ invoiceId: 1 }`.
**Relationships:** `invoiceId → invoices`, `studentId → students`.
**Soft Delete: Dormant.** Financial records are immutable — a refund is `refundedAmount` + a new gateway transaction record, never an edit to this one. `isDeleted`/`deletedAt` exist for schema consistency only; the service layer must never soft-delete a payment.
**Business/Ownership/Security:** students can read (never write) their own payment records; writes come only from the payment-gateway webhook handler and the checkout-initiation flow (both service-layer, not direct client writes). PCI-DSS card-data scope is avoided entirely by gateway-hosted checkout.
**Query/Pagination/Search:** "my payment history" (`studentId`+`status`); webhook reconciliation via `gatewayTransactionId` direct lookup; no search.
**Future Scalability:** none at V1 scale — this collection's integrity guarantees (the unique index) matter far more than its size.

### 3.7 Credentialing & Engagement

#### `certificates`
**Purpose:** A course-completion credential.
**Fields:** `studentId` (ObjectId ref `Student`, required) · `courseId` (ObjectId ref `Course`, required) · `certificateNumber` (string, required, unique, ≥16 chars) · `issuedAt` (Date, default now) · `status` (enum, default `ACTIVE`) · `pdfUrl` (string \| null) · `revokedReason` (string \| null) · `revokedAt` (Date \| null).
**Enum — `status`:** `ACTIVE` \| `REVOKED`.
**Indexes:** unique `{ certificateNumber: 1 }` · `{ studentId: 1, courseId: 1 }`.
**Relationships:** `studentId → students`, `courseId → courses`.
**Soft Delete: Dormant.** Revocation is a `status` transition, not a deletion — the record must remain for public verification/audit history.
**Business/Ownership/Security:** `certificateNumber` **must be non-sequential and non-guessable** — generated by the service layer as a ULID/UUID, **never** the Mongo `_id` and never a sequential number — because it's the lookup key for the public, unauthenticated verification endpoint and must resist enumeration (SECURITY.md §5, §7). That endpoint is additionally rate-limited (API-STANDARDS.md §7) — the schema-level non-guessability and the API-level rate limit are deliberately layered, not either/or.
**Query/Pagination/Search:** "my certificates" (`studentId`+`courseId`); public verification is a direct unique-index hit on `certificateNumber`; no search (verification is exact-match only, by design — a searchable certificate catalog would itself be an enumeration vector).
**Future Scalability:** none.

#### `notifications`
**Purpose:** A queued/sent message to a user across channels.
**Fields:** `recipientId` (ObjectId ref `User`, required) · `channel` (enum, required) · `template` (string, required, ≤100) · `payload` (object, default `{}`) · `status` (enum, default `QUEUED`) · `failureReason` (string \| null) · `sentAt`/`readAt` (Date \| null).
**Enum — `channel`:** `EMAIL` \| `SMS` \| `PUSH` \| `IN_APP`. **`status`:** `QUEUED` \| `SENT` \| `FAILED`.
**Indexes:** `{ recipientId: 1, status: 1 }` · `{ recipientId: 1, readAt: 1 }` (unread-count queries).
**Relationships:** `recipientId → users`.
**Soft Delete:** Dormant — high write volume, short useful life once read; a TTL index on old, read notifications is the intended cleanup mechanism once a retention period is confirmed (not added yet — an arbitrary TTL now would be an undocumented business decision, same reasoning as `audit_logs`).
**Business/Ownership/Security:** a user reads only their own notifications; delivery (write) happens only from the `notifications` BullMQ queue's processor (ARCHITECTURE.md §6), never a direct client write.
**Query/Pagination/Search:** "my unread notifications" (`recipientId`+`readAt: null`), cursor-paginated by `createdAt` once volume warrants it (offset pagination is fine at V1 scale per DATABASE.md §4); no search.
**Future Scalability:** the other top candidate (alongside `audit_logs`) for needing cursor pagination and a TTL retention policy first — flagged here for whoever picks up that work.

### 3.8 Placement

#### `placement_profiles`
**Purpose:** 1:1 with `students` — a student's placement-facing profile.
**Fields:** `studentId` (ObjectId ref `Student`, required, unique) · `resumeUrl` (string \| null) · `skills`/`preferredRoles`/`preferredLocations` (string[]) · `expectedPackage` (number \| null) · `isActivelySeeking` (boolean, default `true`) · `consentGiven` (boolean, default `false`) · `consentGivenAt` (Date \| null).
**Indexes:** unique `{ studentId: 1 }` (partial: `isDeleted: false`) · `{ skills: 1 }`.
**Relationships:** `studentId → students` (1:1).
**Soft Delete:** Active.
**Business/Ownership/Security:** `consentGiven` gates whether this profile (and associated `interviews` activity) may be shared with employers at all — exact consent flow/enforcement is a pending business rule (PROJECT-UNDERSTANDING-REPORT.md §8); captured here but not yet enforced beyond the boolean existing. A student edits only their own profile.
**Query/Pagination/Search:** placement-team search by `skills`, offset-paginated; no text index yet (skills array-contains queries are sufficient at V1 scale).
**Future Scalability:** none — bounded by student count.

#### `companies`
**Purpose:** Employer catalog for the placement domain.
**Fields:** `name` (string, required, unique, ≤200) · `industry` (string \| null) · `website` (string \| null) · `contact` (embedded: `name?`, `email?`, `phone?`) · `isActive` (boolean, default `true`) · `notes` (string \| null, ≤2000).
**Indexes:** unique `{ name: 1 }` (partial: `isDeleted: false`) · `{ isActive: 1 }` · text `{ name }`.
**Relationships:** referenced by `interviews.companyId`.
**Soft Delete:** Active (`isActive: false` is the operational "not currently recruiting" signal, distinct from `isDeleted`, which is reserved for genuinely removing a bad/duplicate entry).
**Business/Ownership/Security:** placement-team (`ADMIN`/`SUPER_ADMIN`) manages this catalog; not student-writable.
**Query/Pagination/Search:** admin list filtered by `isActive`, offset-paginated; name search via text index.
**Future Scalability:** none.

#### `interviews`
**Purpose:** One document per student-company application — the placement pipeline.
**Fields:** `studentId` (ObjectId ref `Student`, required) · `companyId` (ObjectId ref `Company`, required) · `role` (string, required, ≤150) · `offeredPackage` (number \| null) · `status` (enum, default `APPLIED`) · `rounds` (embedded array: `roundNumber`, `scheduledAt`, `mode`, `feedback?`, `result`) · `appliedAt` (Date, default now).
**Enum — `status`:** `APPLIED` \| `SHORTLISTED` \| `INTERVIEW_SCHEDULED` \| `INTERVIEWED` \| `OFFERED` \| `REJECTED` \| `WITHDRAWN`. **`rounds[].mode`:** `ONLINE` \| `OFFLINE` \| `PHONE`. **`rounds[].result`:** `PENDING` \| `PASS` \| `FAIL`.
**Indexes:** `{ studentId: 1, status: 1 }` · `{ companyId: 1 }`.
**Relationships:** `studentId → students`, `companyId → companies`. `rounds` is **embedded** — a small, bounded list always read/written together with its parent application, never queried independently across interviews.
**Soft Delete:** Active.
**Business/Ownership/Security:** a student sees only their own applications; placement-team sees all, filtered by `companyId`/`status` for pipeline management. Requires `placement_profiles.consentGiven` to be true before an application can be created (service-layer check).
**Query/Pagination/Search:** "my applications" (`studentId`+`status`); "candidates for company X" (`companyId`); no search.
**Future Scalability:** grows with (students × applications) — bounded and predictable.

### 3.9 Platform

#### `reports`
**Purpose:** A record of an async, generated report export (CSV/PDF) — not live dashboard data.
**Fields:** `reportType` (string, required, ≤100) · `requestedBy` (ObjectId ref `User`, required) · `parameters` (object, default `{}` — the filters used to generate it) · `status` (enum, default `PENDING`) · `resultFileUrl` (string \| null) · `failureReason` (string \| null) · `generatedAt`/`expiresAt` (Date \| null).
**Enum — `status`:** `PENDING` \| `PROCESSING` \| `COMPLETED` \| `FAILED`.
**Indexes:** `{ requestedBy: 1, createdAt: -1 }` · `{ status: 1 }` · TTL `{ expiresAt: 1 }` (`expireAfterSeconds: 0`).
**Relationships:** `requestedBy → users`. Produced by the `reports` BullMQ queue's processor (ARCHITECTURE.md §6) — live dashboard aggregations are never written here, only exports a user explicitly requested and will download.
**Soft Delete:** Dormant — the TTL index is the real lifecycle mechanism (a report past its download-link expiry has no ongoing value), same reasoning as `user_sessions`.
**Business/Ownership/Security:** a user sees only reports they requested (plus `SUPER_ADMIN` sees all, for audit purposes — who generated what, when); `resultFileUrl` should itself be a signed, time-limited Cloudinary/storage URL (SECURITY.md §6), not a public link.
**Query/Pagination/Search:** "my report history" (`requestedBy`+`createdAt` desc), cursor-friendly; no search.
**Future Scalability:** naturally self-limiting via TTL, same pattern as `user_sessions`.

#### `application_settings`
**Purpose:** System-wide configuration, one document per config key.
**Fields:** `key` (string, required, unique, ≤150) · `value` (mixed, required) · `description` (string \| null) · `category` (string \| null).
**Indexes:** unique `{ key: 1 }` · `{ category: 1 }`.
**Relationships:** none — a flat key-value store, deliberately not one collection per setting *type* (CLAUDE.md: "never create unnecessary collections"). One document per config *key* (not a single giant singleton document) avoids write contention between unrelated settings (e.g. editing `attendance.minPercentage` never risks a merge conflict with `fees.latePenaltyPercent`) and lets each be audited/CRUD'd independently via the shared audit fields.
**Soft Delete:** Active.
**Business/Ownership/Security:** `SUPER_ADMIN`-only writes; any authenticated service/route may read the keys relevant to it.
**Query/Pagination/Search:** "settings in category X" (`category`); direct `key` lookup for individual reads; small collection, no pagination needed.
**Future Scalability:** none — stays small by nature.

#### `counters` — **Implemented (Phase 6)**
**Purpose:** Generic atomic-sequence store, one document per named counter (`_id` is the counter's name, e.g. `'student'`) — infrastructure, not a business record, hence no audit fields.
**Fields:** `_id` (string, the counter name) · `seq` (number, default `0`).
**Indexes:** none beyond the default `_id` index (already unique).
**Relationships:** none — referenced only by name (a plain string) from whichever service needs a sequence, currently `student-id.service.ts` (`_id: 'student'`), `trainer-id.service.ts` (`_id: 'trainer'`, added Phase 7), `course-id.service.ts` (`_id: 'course'`, added Phase 9A), `batch-id.service.ts` (`_id: 'batch'`, added Phase 10A), and `enrollment-id.service.ts` (`_id: 'enrollment'`, added Phase 10B).
**Soft Delete:** N/A.
**Business/Ownership/Security:** no direct API — written only via `findOneAndUpdate(..., {$inc:{seq:1}}, {upsert:true})`, which is the single atomic operation that makes this collection concurrency-safe in the first place (counting existing documents instead would race under concurrent inserts).
**Query/Pagination/Search:** point lookups by `_id` only.
**Future Scalability:** trivially small (one row per named sequence) regardless of how many documents the sequence has produced.

#### Admin Dashboard (Phase 8) — deliberately **no new collection**
**Purpose:** `GET /api/v1/dashboard/admin` (ARCHITECTURE.md §18) is computed live from `users`/`students`/`trainers`/`audit_logs` on every request (subject to the 60-second best-effort Redis cache, SECURITY.md) — there is no persisted "dashboard stats" or "dashboard snapshot" collection. A cached/precomputed stats document would be a second, driftable source of truth for numbers those collections already hold, and at this data volume a handful of parallelized aggregations comfortably meets the phase's <500ms target without one.
**Query pattern:** one `$lookup`(`users`)+`$facet` aggregation per profile collection (`students`, `trainers`) computing active-count, new-in-period count, and profile-completion distribution together; one `$facet` aggregation on `users` for status counts/distribution; a small `find().sort().limit()` for each recent-records list and the activity feed — five queries total, `Promise.all`-parallelized, not sequential, and not a single mega-pipeline joining all four collections at once (would be far less readable for no efficiency gain at this scale). Distinguish this from `reports` above, which persists an async, user-requested *export* — this dashboard is always a live read.
**Future Scalability:** if per-request aggregation cost ever becomes a real bottleneck (well beyond current projected scale), the next step is a materialized, periodically-refreshed stats document — not sharding — but that hasn't been needed yet and shouldn't be built speculatively.

## 4. Indexing Strategy

- Every foreign-key-style reference field used in a query filter is indexed (see per-collection notes above).
- Compound indexes are ordered by selectivity: equality filters first, range/sort fields last (e.g. `{ batchId: 1, status: 1 }`, not the reverse, when `batchId` is always present in the query).
- No index is added speculatively — CLAUDE.md's "measure before optimizing" applies to indexes too; new indexes are added when a query pattern (from Reports/Analytics or a slow-query log) demonstrates the need, and are documented here when added.
- Unique indexes double as data-integrity constraints (`enrollments` student+batch, `payments` gateway transaction ID, `certificates` certificate number, `attendance` batch+date+student) — these are correctness guarantees, not just performance.
- Partial filter expressions (`{ isDeleted: false }`) are used on unique indexes for collections where soft delete is Active, so a deleted document's "unique" value (email, slug, name) can be reused by a new one.

## 5. Pagination

Default: **offset-based** (`page`, `limit`) for all V1 admin/list endpoints — simplest to implement correctly and sufficient at the stated scale (10k students, 1k courses). `limit` is capped server-side (default 20, max 100) regardless of client request, per API-STANDARDS.md. Cursor-based pagination is called out per-collection above where a collection's write volume makes it the more likely first candidate (`audit_logs`, `notifications`) — deferred until actually needed, not built speculatively.

## 6. Search Strategy

MongoDB text indexes cover V1 search needs: `courses` (title/description/tags), `students`/`trainers` (name), `questions` (text), `companies` (name). None of these are expected to need a dedicated search service (e.g. Atlas Search, Elasticsearch) at PRD's stated scale (1,000+ courses, 10,000+ students) — flagged per-collection above as a future upgrade path if relevance quality becomes a problem, which would be a service-layer/infra change, not a schema change.

3. Retake policy for `quiz_attempts`/`examination_results` — is `attemptNumber` capped beyond `maxAttempts`, and can it be overridden?
4. GST invoicing requirement for `invoices.gstDetails`?
5. Retention periods for `notifications` and `audit_logs` (both currently TTL-free pending this decision).
6. Exact consent-enforcement mechanics for `placement_profiles.consentGiven` gating `interviews` creation.
7. Malware/virus scanning for `lesson_resources` uploads (Phase 9C) — no scanning provider is integrated yet; current mitigations are a strict format allowlist, independent Cloudinary re-verification, size caps, and private (`type: 'authenticated'`) storage. ## 8. Backup & Retention

MongoDB Atlas automated daily backups, minimum **7-day** point-in-time recovery window for V1 (Atlas M10+ tier or above required for PITR — cluster tier selection is a DevOps decision, see DEPLOYMENT.md). `audit_logs` and `payments` are excluded from any future data-purge policy regardless of what's decided for other collections — financial and audit records are retained per applicable statutory requirements (⚠ exact retention period pending legal/compliance confirmation, tied to PROJECT-UNDERSTANDING-REPORT.md Q4).
