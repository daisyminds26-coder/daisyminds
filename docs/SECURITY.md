# Daisy Minds LMS — Security Standards

Baseline derived from CLAUDE.md's Security Standards section, made concrete. Items marked **⚠ Pending Confirmation** require a stakeholder decision — see [PROJECT-UNDERSTANDING-REPORT.md](./PROJECT-UNDERSTANDING-REPORT.md) §10.

---

## 1. Authentication — **Implemented (Phase 2)**

- **JWT access tokens**, short-lived (`JWT_ACCESS_EXPIRES_IN`, default 15 minutes). Carried in `Authorization: Bearer`, never stored in `localStorage`/`sessionStorage` (XSS-exfiltration risk) — held in memory only on the frontend (`frontend/src/shared/lib/auth-session-store.ts`, a Zustand store with no `persist` middleware — **implemented, Phase 4**). Payload is a snapshot of `{ sub, roleId, role, permissions, sessionId }` taken at issuance (login/refresh) — see ARCHITECTURE.md's RBAC note on the accepted staleness tradeoff (≤ access-token TTL) in exchange for zero DB hits on every authenticated request.
- **Frontend refresh handling — implemented, Phase 4:** `frontend/src/shared/lib/api-client.ts`'s Axios response interceptor transparently refreshes on a `401` from any endpoint except the public auth endpoints themselves (never recurses into refreshing off `/auth/refresh`'s own `401`), deduplicates concurrent refreshes into a single in-flight request, retries the original request at most once, and on refresh failure clears local auth state and broadcasts a `SESSION_INVALIDATED` event to other tabs (`frontend/src/shared/lib/multi-tab-sync.ts`, `BroadcastChannel` — the event name only, never the token). `403` responses never trigger a refresh attempt.
- **Frontend route guards are UI-only** (`frontend/src/shared/guards/`) and are documented as such directly in code — see §3's last bullet. The post-login "return to intended route" flow (`frontend/src/features/auth/utils/redirect.ts#resolvePostLoginPath`) validates the target against the authenticated user's own role-area prefix before navigating to it, preventing an open redirect via a crafted `location.state`.
- **Refresh tokens**, long-lived (`JWT_REFRESH_EXPIRES_IN`, default 7 days) — **not JWTs**, opaque high-entropy random values. Stored as an **httpOnly, `Secure` (production), `SameSite=Strict` cookie**, scoped to `${API_PREFIX}/auth` only (not sent on unrelated routes). The cookie value is `sessionId.rawToken` — an O(1) lookup by `sessionId` before hash-comparing the token, rather than scanning `user_sessions` for a hash match. The hash (SHA-256 — see below for why not Argon2) is what's persisted server-side (`user_sessions.refreshTokenHash`, DATABASE.md §3.1) — a database read alone can never yield a usable token.
- **Rotation + reuse detection:** every `/auth/refresh` call replaces the stored hash with a new one (`user-session.repository.ts#rotate`). A presented token whose hash doesn't match the session's *current* hash means an already-rotated (stale) token was replayed — treated as a compromise signal: that session is revoked immediately (`revokedAt` set) and an `audit_logs` entry (`auth.refresh.reuse_detected`) is written, forcing re-authentication.
- Refresh/verification/reset tokens are hashed with **SHA-256, not Argon2/bcrypt** — deliberately: those algorithms are slow specifically to resist brute-forcing a *guessable* low-entropy password, but a 256-bit random token is already infeasible to brute-force regardless of hash speed, so a slow hash here would only add latency for no benefit (`token.service.ts`).
- **Account status gates login**, not just password correctness: `PENDING_VERIFICATION` accounts are rejected with a distinguishable `EMAIL_NOT_VERIFIED` code (revealed only *after* a correct password — see §2), `SUSPENDED` accounts are rejected with a visible reason (`403 FORBIDDEN`), `LOCKED` accounts are rejected with a distinguishable `401 ACCOUNT_LOCKED` code and `details.lockedUntil` (checked *before* password verification — see §2 lockout), and `DEACTIVATED` accounts get the exact same `401 UNAUTHORIZED` / "Invalid email or password" response as a wrong password or unknown email (no disclosure — this is deliberate and is not weakened by the `ACCOUNT_LOCKED`/`EMAIL_NOT_VERIFIED` codes, which only exist because those two statuses are already meant to be actionable/visible to the account owner). See `auth.service.ts#login` for the full ordering rationale.
- **MFA/TOTP for `SUPER_ADMIN` and `ADMIN` roles — ⚠ Pending Confirmation, strongly recommended, not yet implemented.** `users.mfaEnabled`/`mfaSecret` fields are reserved. These roles hold financial and system-config access; password-only auth is insufficient at that privilege level.

## 2. Password Policy — **Implemented (Phase 2)**

- Hashed with **Argon2id** (`memoryCost: 19456, timeCost: 2, parallelism: 1` — OWASP's current documented baseline, `password.service.ts`) — chosen over bcrypt as the more current OWASP recommendation; never reversible encryption, never stored plaintext even transiently in logs.
- Minimum 10 characters, at least one number and one letter (complexity rules kept simple and NIST-aligned — length matters more than mandatory special characters), enforced by a Zod schema (`validators/auth.validator.ts`), not the password service — validation stays in the validator layer per CODING-STANDARDS.md's split.
- Passwords checked against a breached-password list (e.g., HaveIBeenPwned k-anonymity API) at signup/reset — ⚠ still pending confirmation on external-call approval; not yet implemented.
- **Account lockout — implemented:** `LOGIN_MAX_ATTEMPTS` (default 5) failed attempts within the account's history sets `status: LOCKED` and `lockedUntil` (`LOGIN_LOCKOUT_MIN`, default 15 minutes) — auto-clears on the next login attempt once `lockedUntil` has passed. A login attempt against a still-locked account returns `401` with `code: "ACCOUNT_LOCKED"` and `details.lockedUntil` (ISO timestamp) so the frontend can render a real retry-after time (`ApiError.locked()`) — this is per-account, not per-account+IP (see ROADMAP for a future per-IP refinement if abuse patterns demand it).

## 3. Authorization (RBAC) — **Implemented (Phase 2)**; admin user-management guards — **Implemented (Phase 5)**

- Every route is **default-deny** — protected by a shared `requireAuth` middleware applied to every feature router; only the explicitly public routers/routes (login, refresh, forgot/reset-password, verify/resend-verification, health, certificate verification) are mounted before it, per API-STANDARDS.md §6. Within `/auth` specifically (which inherently mixes public and protected endpoints), `requireAuth` is applied per-route rather than router-wide — see `routes/auth.routes.ts`. `/users` and `/roles` (Phase 5) instead apply `requireAuth` once, router-wide, since every endpoint in both routers requires authentication.
- Role checks (`requireRole(...)`) and permission checks (`requirePermission(...)`) both read from the access-token payload (§1) — never a DB lookup, never `req.user.role` checked inline in a controller.
- **Ownership checks — `requireOwnership()` middleware, `middlewares/ownership.middleware.ts`:** a generic owner-or-404 factory. Loads the target resource, compares `resource.userId` to `req.user.id`, and returns **404, not 403**, when they don't match — confirming a resource ID exists to a non-owner is itself an information leak. Used today for `DELETE /auth/sessions/:id`; the same factory is reusable by future LMS modules (e.g., a trainer accessing only their own batch's attendance).
- Permission checks happen server-side only. Frontend role-based UI hiding (UI-DESIGN-SYSTEM.md §6) — implemented via `RequireRole`/`RequirePermission` route guards and the `usePermission`/`Can` helpers (`frontend/src/shared/guards/`, `frontend/src/features/auth/hooks/use-permission.ts`) — is a UX convenience, never a security boundary. **Phase 5 closed a real gap here:** `app/router.tsx`'s `/admin`, `/trainer`, `/student` route trees had `RequireAuth` but no role gate at all — any authenticated user (including a `STUDENT`) could previously reach `/admin` in the UI, relying entirely on the (correctly enforced) backend checks below to reject the actual requests. Each area is now additionally wrapped in `RequireRole`.
- **Admin user-management privilege guards (Phase 5, enforced in `user-management.service.ts`, not middleware — they depend on request-body content and target-resource state, not just the actor's own token):**
  - *Self-protection:* an actor cannot deactivate or soft-delete their own account (`assertNotSelf`) — the delete/deactivate button is simply absent on your own row in the UI, and the backend independently rejects it regardless.
  - *Cross-role protection:* `ADMIN` cannot act on a `SUPER_ADMIN` account at all — deactivate, delete, role-change (`assertCanActOnTarget`) — and cannot grant the `SUPER_ADMIN` role to anyone (`assertRoleGrantAllowed`). Only a `SUPER_ADMIN` can touch a `SUPER_ADMIN` account or hand out that role.
  - *Last-active-SUPER_ADMIN protection:* deactivating, deleting, or role-changing a `SUPER_ADMIN` away is blocked if it would leave zero `ACTIVE` `SUPER_ADMIN` accounts (`countActiveByRole`, counted fresh from the DB per request — deliberately not trusted from the actor's own access-token claims, since a token issued before an out-of-band deactivation remains valid for its full TTL, §1).
  - *Bulk actions* (`POST /users/bulk`) run the same per-item guarded functions in a loop rather than a separate bulk code path — a blocked item is reported in the response's `failed: [{id, reason}]` array, the rest of the batch still proceeds.
  - *Sessions and audit-log access* (`GET/POST /users/:id/sessions*`, `GET /users/:id/audit`) are `requireRole('SUPER_ADMIN')`-gated — stricter than the `users:manage`/`users:read` permissions `ADMIN` otherwise holds for this module, since forcing another user's logout or reading their full audit history is higher blast-radius than the rest of the CRUD surface.
  - *Permissions stay role-based, not per-user:* there is deliberately no per-user permission-override mutation. "Assign Permissions" is satisfied by role assignment (which carries the role's permission set) plus a read-only "effective permissions" view; adding a per-user override field was rejected as unrequested schema expansion that would also make a role's permission set editable from the wrong screen (see ARCHITECTURE.md §14).

**Admin Student Management (Phase 6)** reuses this module's `users`-level machinery directly rather than re-implementing guards:
  - Activate/deactivate/soft-delete/restore/resend-invitation/sessions/audit for a student call the exact same `userRepository`/`userSessionRepository`/`auditLogRepository` methods described above, keyed by the student's linked `userId` — not a parallel implementation.
  - No self-protection/last-active-SUPER_ADMIN/privilege-escalation guards exist in `student-management.service.ts` — a student can never hold `SUPER_ADMIN`, so those checks are structurally unreachable and were deliberately not copied over.
  - Mass-assignment protection is entirely schema-driven: `student.validator.ts`'s create/update schemas never declare `email`/`password`/`role`/`studentId`/any audit field, so there is nothing for an `ADMIN` actor to escalate via the student endpoints even without an explicit runtime guard — verified by an integration test that sends `role`/`studentId`/`passwordHash` in a create/update body and asserts a `400`.
  - Sessions/audit access for a student is `requireRole('SUPER_ADMIN')`-gated, identical to the `users` carve-out above.
  - `students:read`/`students:manage`/`students:export` are additive, separate permission-catalog entries — not folded into `users:*` — so a narrower role (e.g. a future read-only registrar role) can be granted student access without also granting user-account management.

**Admin Trainer Management (Phase 7)** follows the exact same pattern as Student Management above, not a new set of guards:
  - Activate/deactivate/soft-delete/restore/resend-invitation/sessions/audit/bulk-action for a trainer call the same `userRepository`/`userSessionRepository`/`auditLogRepository` methods, keyed by the trainer's linked `userId`.
  - No self-protection/last-active-SUPER_ADMIN/privilege-escalation guards exist in `trainer-management.service.ts`, for the same structural reason as students — a trainer can never hold `SUPER_ADMIN`.
  - Mass-assignment protection is schema-driven: `trainer.validator.ts`'s create/update schemas never declare `email`/`password`/`role`/`trainerId`/any audit field or a salary/compensation field (none exists in the schema at all — see §7 below), verified by the same class of integration test the students module uses.
  - Sessions/audit access for a trainer is `requireRole('SUPER_ADMIN')`-gated, identical to the `users`/`students` carve-out above.
  - `trainers:read`/`trainers:manage`/`trainers:export` are additive, separate permission-catalog entries, matching the students module's three-permission shape exactly. Two more granular permissions floated in the task spec (`trainers.internal_notes.read`/`.update`) were deliberately not added — `trainers:manage` already covers the `notes` field and no consumer needs a finer split.

**Admin Dashboard (Phase 8)** uses a single `dashboard:read` permission (held by `ADMIN` and `SUPER_ADMIN`) rather than the task spec's suggested three (`dashboard.admin.read`/`.audit.read`/`.security.read`):
  - The base operational dashboard (summary/distributions/recent records/alerts) is gated by `dashboard:read` alone.
  - The audit-derived `recentActivity` feed is instead gated by the exact `requireRole('SUPER_ADMIN')` carve-out §3's students/trainers sessions/audit access already uses — permission-aware response shaping within one endpoint (`recentActivity: null` for `ADMIN`), not a second permission or a second route. See API-STANDARDS.md's dashboard reference-implementation note.
  - No separate "security indicators" permission was added — the phase's own session/account-security signals (locked/suspended/pending-verification counts) are already covered by the base `dashboard:read` summary, and anything requiring the deeper per-session view stays behind `/users/:id/sessions*`'s existing `SUPER_ADMIN`-only gate, not duplicated here.

**Admin Course Management (Phase 9A)** is structurally different from §3's other admin modules — a course is not a `users` document, so there is no self-protection/cross-role/last-active-`SUPER_ADMIN` guard class to reuse or reimplement (a course has no role of its own):
  - `courses:read`/`courses:manage`/`courses:publish`/`courses:export` extend the permission catalog, held by `ADMIN`/`SUPER_ADMIN`. `courses:publish` is kept separate from `courses:manage` deliberately — moving a course into the public catalog is a materially higher-stakes action than editing draft metadata, even though both are currently granted to the same roles.
  - Publication itself is authorization- **and** state-gated: even a `courses:publish`-holding actor cannot publish a structurally incomplete course — `checkReadiness()` (ARCHITECTURE.md §19) is the single source of truth enforced server-side regardless of what the client believes is ready, returning a `422` with structured blockers rather than a generic `400`/`403`.
  - Mass-assignment protection is schema-driven: `course.validator.ts`'s create/update schemas are `.strict()` and never declare `courseCode`/any audit field — an unknown or forbidden field in the request body fails validation before reaching the service layer, verified by an integration test.

**Curriculum Builder (Phase 9B)** reuses `courses:read`/`courses:manage`/`courses:publish` directly — no new `curriculum:*` permission catalog entries were added, and consequently no `seed-roles.ts` change or live-database re-seed was needed for this phase:
  - Mass-assignment protection mirrors courses: `curriculum.validator.ts`'s create/update schemas are `.strict()` and never declare `order`/`courseId`/`courseModuleId`/any audit field — `order` can only ever change through the dedicated reorder/move endpoints, never the plain update endpoint, and moving a lesson's `courseModuleId` can only happen through the dedicated move endpoint.
  - Every single-lesson route is nested under `.../modules/{moduleId}/lessons/{lessonId}/...`; the service layer independently re-verifies the lesson actually belongs to that `moduleId` (`assertLessonInModule`) rather than trusting the URL segment silently — a stale or manipulated `moduleId` in the path 404s instead of the request being routed against the wrong module's context.
  - Cross-course manipulation is structurally prevented, not just checked: every module/lesson lookup is scoped to `{_id, courseId}` from the URL, so a manipulated module/lesson id belonging to a *different* course simply isn't found (404) — there's no separate "does this belong to me" branch to forget. The lesson-move endpoint's target-module lookup uses the same scoped query, so moving a lesson to a module in a different course is impossible by construction, not by an explicit ownership check.
  - Reorder payload abuse is bounded: module reorder capped at 200 items, lesson reorder capped at 500 items (Zod schema `.max()`), and a reorder payload must name every current active sibling exactly once — an unknown id, a missing id, or a duplicate id/order value is rejected with `400` before any write.

**Learning Content Management (Phase 9C)** reuses `courses:read`/`courses:manage` directly — `courses:media:manage` was considered and rejected as permission bloat absent a genuine need to let some `courses:manage` holders touch content but not structure. No `seed-roles.ts` change, no live-database re-seed:
  - Every content/resource route is nested the same way Phase 9B's lesson routes are (`.../modules/{moduleId}/lessons/{lessonId}/content/...`) and reuses the identical `assertLessonInModule`/scoped-lookup pattern — cross-course or cross-lesson manipulation is structurally prevented, not just checked, by construction.
  - Content-type mismatch is rejected server-side: `PUT .../content/text` on a non-`TEXT` lesson (etc. for video/document/external-link) returns `409`, regardless of what the client's UI otherwise allows — the discriminator is enforced at the write path, not just the read side.
  - Resource-count abuse is bounded: `MAX_RESOURCES_PER_LESSON` (env-driven, default 20) is enforced both at signature-issuance and at verify time, so a client can't race past the cap by requesting many signatures before any single upload completes.
  - Mass-assignment protection mirrors curriculum: every content/resource validator schema is `.strict()`; `contentStatus` is never an accepted field on any write schema — it is exclusively server-computed (`utils/lesson-content-status.util.ts#computeContentStatus`), the same "server-computed, never client-writable" discipline `profileCompletionStatus` (students/trainers) already established.

**Admin Batch Management (Phase 10A)** adds `batches:read`/`batches:manage`/`batches:export` — a new three-permission catalog entry (not reused from `courses:*`, since a batch is a distinct resource with its own lifecycle), held by `ADMIN`/`SUPER_ADMIN` only; `TRAINER`/`STUDENT` get none, even though a trainer may be assigned to a batch — batch *scheduling* is an admin operation, distinct from a trainer's own future teaching-content/attendance permissions:
  - `batches:manage` covers every lifecycle transition (schedule/unschedule/activate/complete/cancel/archive/restore/delete) — no separate lifecycle permission, matching the "consistency over artificial granularity" reasoning §3's other modules already establish.
  - Lifecycle transitions only ever happen through dedicated `POST /:id/lifecycle/{action}` endpoints (ARCHITECTURE.md §22) — the generic `PATCH /:id` update schema explicitly excludes `status`, `batchCode`, and `courseId` (`.strict()`, and `courseId` additionally `.omit()`-ed entirely from the update schema's shape), so a lifecycle bypass or an immutable-field overwrite via the plain update endpoint is structurally impossible, not just discouraged. Verified by an integration test sending each of `status`/`batchCode`/`courseId` in a PATCH body and asserting `400`.
  - Scheduling (`DRAFT → SCHEDULED`) is authorization- **and** readiness-gated, the same pattern §3 established for course publication: even a `batches:manage`-holding actor cannot schedule a batch that is missing a required field, references an unpublished/archived/deleted course, has an inactive/ineligible/unavailable trainer, or has a trainer schedule conflict — `batch-readiness.service.ts#checkReadiness` is the single source of truth enforced server-side, returning a `422` with structured blockers.
  - Cross-course/cross-trainer manipulation is structurally prevented: a batch's `courseId` is validated to exist and not be soft-deleted at write time; `primaryTrainerId`/`assistantTrainerIds` are validated to exist and not be soft-deleted (existence-only check at write time — `trainerRepository.countExisting`, additive); duplicate assistant trainer IDs and a primary trainer also listed as an assistant are both rejected server-side (Zod `superRefine`), never silently deduplicated.
  - Mass-assignment protection is schema-driven throughout: `batch.validator.ts`'s create/update schemas are `.strict()`. Trainer-conflict detection (availability/double-booking) is read-only validation, never a distributed lock — documented explicitly as such in code, since two admins racing to assign the same trainer to overlapping batches is a low-stakes collision the trainer resolves afterward, not data corruption requiring a lock.
  - `meetingProvider` is an enum placeholder only — no real meeting credential/URL/join-link is ever stored on a batch this phase (no live-class integration exists yet), so there is no meeting-access secret to leak via the batch API or its CSV export.
  - CSV export explicitly excludes `internalNotes` and the full venue address (`location.addressLine1`/`addressLine2`/etc.), reuses the existing `escapeCsvField` formula-injection guard for every user-controlled text field (`name`, `tags`), and is capped at 5,000 rows — identical to every other module's export.

**Student Enrollment Engine (Phase 10B Part 1, backend only)** adds `enrollments:read`/`enrollments:manage`/`enrollments:export` — a new three-permission catalog entry, `ADMIN`/`SUPER_ADMIN` only; `TRAINER`/`STUDENT` get none (a future self-scoped "My Enrollments" API is a separate, unbuilt surface, not a grant of this admin permission set):
  - `courseId` is **never** accepted from the client on any enrollment write path (create, bulk-enroll, transfer) — always resolved server-side from the batch, closing off a class of cross-course-manipulation attempts the task explicitly flagged.
  - Lifecycle transitions only happen through dedicated `POST /:id/{action}` endpoints, gated by `utils/enrollment-lifecycle.util.ts#canTransitionEnrollment`'s explicit transition table — an illegal transition (including any move out of a terminal status) is a structurally-enforced `409`, not just a discouraged one. No generic status PATCH exists for enrollments at all.
  - **Capacity oversubscription is prevented at the database level, not just checked in application code** — `batchRepository.reserveSeat` is a single atomic `findOneAndUpdate` with an `$expr` comparing `occupiedSeats` against `maxStudents` on the same document; MongoDB's own single-document write serialization is what actually closes the race, verified by a concurrent-request integration test (ARCHITECTURE.md §23). `occupiedSeats`/`waitlistSequence` are never client-writable and never generically PATCH-able — the only writers are `enrollment-capacity.service.ts`'s exclusive callers of the atomic repository methods.
  - Duplicate/same-course-different-batch enrollment is blocked at the service layer (`enrollmentRepository.findByStudentAndBatch`/`findNonTerminalByStudentAndCourse`) — the schema's own unique index is a backstop, not the primary control, since "unless terminal" can't be expressed in a plain unique index.
  - Transfer is cross-course-blocked server-side (`400` if the target batch's `courseId` differs) and fully transactional — a failed target-seat reservation rolls back the source seat release too, verified by an integration test asserting the source enrollment and its seat are untouched after a rejected transfer.
  - **New delete-protection guards on three existing modules** — batch/course/student soft-delete now each check for non-terminal enrollment (and, for courses, non-archived batch) references before proceeding, returning `409` rather than orphaning enrollment history. See ARCHITECTURE.md §23.
  - The capacity-reconcile maintenance endpoint (`POST /batches/:id/capacity/reconcile`) is `requireRole('SUPER_ADMIN')`-gated, not a permission check — matching this app's existing stricter-than-module-permission carve-out for sensitive operational actions (this section's own students/trainers sessions-access precedent above).
  - Mass-assignment protection is schema-driven: `enrollment.validator.ts`'s schemas are `.strict()` and never declare `status`, `courseId` (on update paths), `occupiedSeats`, `waitlistPosition`, or any audit field.
  - CSV export excludes `internalNotes`, reuses the existing formula-injection guard, capped at 5,000 rows.
  - **Found and fixed during test-writing:** `EnrollmentModel.aggregate()`'s `$match` stages don't auto-cast query values against the schema — a plain string `studentId`/`batchId`/`courseId` filter silently matched zero rows until explicitly wrapped in `new Types.ObjectId(...)`. Not an injection-class bug (no unintended data was ever exposed — the failure mode was "matches nothing," not "matches too much"), but recorded here since the same mistake in a future aggregation-based repository could just as easily fail the other direction. See ARCHITECTURE.md §23.

## 4. Input Validation & Injection Protection

- **NoSQL injection:** all request bodies pass through a strict Zod schema (API-STANDARDS.md §5) before touching Mongoose — raw client input is never interpolated into a Mongo query object; Mongoose query builders are used exclusively (no `$where`, no raw query string construction from user input).
- **XSS:** Helmet sets a strict Content-Security-Policy; any user-generated rich text (e.g., trainer lesson descriptions, assignment feedback) is sanitized server-side (allowlist-based HTML sanitization) before storage, and rendered by React's default escaping on the frontend (no raw `dangerouslySetInnerHTML` of user content).
- **CSRF:** primary defense is that the access token lives in memory and is sent via an explicit `Authorization` header (not an ambient cookie the browser auto-attaches), which already defeats classic CSRF for authenticated API calls. The refresh-token cookie (§1) uses `SameSite=Strict`, which prevents it being sent on cross-site requests at all.
- **CSV/formula injection (Phase 6):** `utils/csv.ts#escapeCsvField` now also neutralizes a leading `=`, `+`, `-`, `@`, tab, or CR with a prefixed `'` before the existing RFC 4180 quoting — several spreadsheet applications treat a cell starting with one of those characters as a formula. This hardening was added specifically because the student CSV export is the first export in the app to include user-controlled free text (name, tags) rather than only system-generated fields (email, status, dates); it applies to every export using this shared helper, including the pre-existing `/users/export` and the Phase 7 `/trainers/export`.
- **Mongoose embedded-subdocument response leak (found and fixed, Phase 7):** spreading a Mongoose embedded-array subdocument with `{...item}` does **not** yield a clean plain object — it copies internal bookkeeping properties (`$__`, `_doc`, `$isNew`, `__parentArray`, `__index`, `$__parent`) into the response, which can expose the entire parent document's data through a nested field. Found via manual testing of `student-management.service.ts`'s emergency-contact/education-record mapping, fixed with explicit field-by-field DTO mapper functions (and a regression test asserting the leaked keys are absent), and applied preventatively from the start in the new `trainer-management.service.ts`. Any future module mapping a Mongoose embedded array to a DTO must use an explicit mapper function, never a spread.
- **IANA timezone validation (Phase 7, extracted to a shared helper in Phase 8):** any future field validating a timezone string must use `Intl.DateTimeFormat(undefined, {timeZone: value})` construction (wrapped in try/catch), never `Intl.supportedValuesOf('timeZone').includes(value)` — the latter's canonical list contains legacy ICU aliases instead of the modern preferred names most systems and users actually use (e.g. it lacks `Asia/Kolkata`, only `Asia/Calcutta`), causing valid input to be rejected. This is a correctness note, not an injection-class vulnerability, but is recorded here alongside the other Phase 7 validation lessons. Now lives in `backend/src/utils/timezone.ts`, shared by `trainer.validator.ts` and `dashboard.validator.ts` rather than duplicated a second time.
- **Dashboard date-range bounds (Phase 8):** `GET /dashboard/admin`'s `range=CUSTOM` request is capped at 366 days at the Zod validation layer (`adminDashboardQuerySchema`, `backend/src/validators/dashboard.validator.ts`) — an unbounded custom range would let a caller force an arbitrarily expensive aggregation scan; the cap keeps every dashboard aggregation's underlying date-filtered scan bounded regardless of caller input.
- **Alert action routes are allowlisted, never request-derived (Phase 8):** each dashboard alert's `actionRoute` comes from a fixed `Record<AlertType, string>` (`ALERT_ROUTES` in `dashboard.service.ts`) — never built from any part of the incoming request — so an alert link can never become an open redirect. The frontend's `AlertsPanel` renders `alert.actionRoute` directly into a `<Link>` on that same trust basis.
- **Zod `.partial()` on an already-refined schema throws at module load, not at request time (found and fixed, Phase 9A):** Zod v4 disallows calling `.partial()` on a schema that already carries a `.superRefine()`. `course.validator.ts`'s `updateCourseSchema` is built from an unrefined `courseBaseSchema.partial()`, with the cross-field refinement (`courseProfileSchema`'s `.superRefine()`) reapplied afterward — never `.partial()` called directly on the already-refined create schema. Any future module deriving a "partial update" schema from a refined "create" schema must follow the same split, or the entire route file fails to load (not a runtime validation failure — a startup failure affecting every endpoint in the file).
- **Course pricing cross-field rules enforced backend-only (Phase 9A):** paid-requires-positive-price, discount-below-base-price, sale-end-after-sale-start, and free-clears-stale-paid-fields are all Zod `superRefine` checks in `course.validator.ts`'s `pricingSchema` — never trust-the-frontend, and in this case also worked around a frontend Zod/RHF type-inference interaction (see ARCHITECTURE.md §19) by simply not duplicating the refinement client-side. A violation surfaces as a generic API-error toast on submit, not an inline field error — an acceptable tradeoff since pricing rules are rarely violated by an admin filling out a guided wizard in order.
- **CSV export field allowlist (Phase 9A):** `GET /courses/export` explicitly excludes `internalNotes` and any Cloudinary public IDs/credentials from the exported columns, and reuses the existing `escapeCsvField` formula-injection guard (§ above) for every user-controlled text field (`title`, `tags`, `category`). Capped at 5,000 rows, same as students/trainers.
- **Prerequisite cycle injection prevented at every write, not just checked (Phase 9B):** a lesson prerequisite is rejected server-side if it self-references, points outside the course, points at a missing/deleted lesson, or would close a direct or indirect cycle (`utils/curriculum-prerequisite.util.ts#findCyclicPrerequisite`, a graph walk over every other lesson's current edges) — a malicious or buggy client can never get a cyclic prerequisite graph stored, and the curriculum readiness check re-verifies the whole graph (`hasCycle`) as a defense-in-depth safety net rather than just trusting that invariant forever.
- **Curriculum's first real database transactions (Phase 9B):** reorder, move, duplicate, and cascading module-delete all wrap their multi-document writes in `utils/transaction.ts#withTransaction` (`mongoose.startSession()`/`session.withTransaction()`) — every prior module's writes were single-document and didn't need this. Requires a replica set (MongoDB Atlas always is one in production); local tests use a dedicated `MongoMemoryReplSet` helper (`tests/setup-db.ts#setupTransactionalTestDatabase`), kept entirely separate from every other test file's standalone `MongoMemoryServer` helper.
- **A Zod `.default()`/`.partial()` interaction silently wiped fields on partial updates — found by the test suite and fixed before shipping (Phase 10A).** `.partial()` does not suppress a field's own `.default()`; Zod substitutes the default the instant a key is `undefined`, regardless of the field's optionality elsewhere. `updateBatchSchema` was originally `batchBaseSchema.omit({courseId:true}).partial()`, and several base fields (`weeklySchedule`, `calendarExceptions`, `assistantTrainerIds`, `tags`, `waitlistEnabled`) carried a `.default(...)` — so a bare `{name: "..."}` PATCH silently parsed with those fields reset to empty/`false`, and since `updateBatch` spreads the parsed input into its `$set`, every partial update that didn't re-send them **wiped real data** (and fired their field-specific audit events on every PATCH, not only genuine changes). Fixed by keeping the shared base schema entirely bare (`.optional()`, no `.default()` anywhere in it) so `.partial()`'s "omitted key ⇒ leave unchanged" semantics actually hold, and re-adding `.default(...)` only on the create schema via `.extend()`, where "omitted at creation" genuinely should mean "start empty." Any future module deriving an update schema from `<baseSchema>.omit(...).partial()` where the base schema has `.default()`-bearing fields must apply this same split, or risk silent data loss on partial updates — not just a validation-shape mistake, a real production data-integrity bug.

## 5. Rate Limiting & Abuse Protection

- Global throttle via `express-rate-limit` (`middlewares/rate-limit.middleware.ts`); stricter explicit limiters implemented for auth (`middlewares/auth-rate-limit.middleware.ts`, Phase 2) — `loginRateLimiter` (10/15min) on `/auth/login`, `passwordResetRateLimiter` (5/15min) on `/auth/forgot-password`, `/auth/reset-password`, and `/auth/resend-verification`. `/certificates/verify/:certificateNumber` will get the same tighter treatment when the certificates module is built (public enumeration risk flagged in the understanding report).
- Certificate verification will additionally use a **non-sequential, non-guessable `certificateNumber`** (DATABASE.md §3.7) so even an unthrottled request can't be used to enumerate valid certificates by incrementing an ID.
- Login enumeration is defended at the response-shape level, not just rate limiting: wrong password, nonexistent email, and a deactivated account all return the identical `401` `"Invalid email or password"` — see §1. `forgot-password` and `resend-verification` return an identical generic success response regardless of whether the account exists (`auth.service.ts`).
- **Cache privilege isolation (Phase 8):** the admin dashboard's Redis cache key (`dashboard-cache.service.ts`, ARCHITECTURE.md §18) includes the caller's permission scope (`super_admin` vs `admin`) alongside the resolved period — a `SUPER_ADMIN`'s cached response (which includes the audit-derived `recentActivity` feed) can never be served back to an `ADMIN` requesting the same date range. The cache is best-effort only (never blocks a request, never the sole source of truth for authorization) — every cache read still passes through the same `requirePermission`/`requireRole` checks on the way in.

## 6. File Upload & Media Security

- All Cloudinary uploads use **signed upload parameters generated server-side** with a short expiry — the frontend never holds Cloudinary API secrets, and cannot upload arbitrary unsigned content.
- Server-side validation of file type (allowlist by module: video/mp4 for lessons, pdf/image for assignments and certificates) and size limits before issuing a signed upload token — rejecting after upload wastes storage and bandwidth.
- **Malware/virus scanning on assignment uploads and lesson resources — ⚠ Pending, explicit production-readiness gap (not fabricated as covered anywhere in the stack).** No scanning provider (e.g. ClamAV, a Cloudinary add-on) is integrated. Cloudinary itself performs **no** malware/virus scanning — this must never be implied by documentation or UI copy. Current mitigations for Phase 9C's lesson-resource upload surface: a strict per-content-type format allowlist (never "any file," executable/installer formats are never in any allowlist), independent server-side re-verification of format/size/resource-type against Cloudinary's own Admin API response (never trusting a client-reported upload as proof), environment-driven size caps, and private (`type: 'authenticated'`) storage with no public hotlinking. Required before this upload surface is opened to any less-trusted uploader than today's `ADMIN`-only flow.
- **Secure video access:** enrolled-content video URLs (student-facing, once the Learning Player exists) are intended to be Cloudinary **signed, time-limited delivery URLs**, generated per-request against the requesting student's active enrollment — a URL leaked outside the session expires quickly and cannot be replayed indefinitely. Phase 9C builds the reusable half of this (`media-delivery.service.ts#generateSignedDeliveryUrl` — see below), used today only for the **admin content-preview** flow; the enrollment-gated student-facing check is deferred to the Learning Player phase, which will call the same service rather than a parallel implementation.
- **Content protection (DRM/watermarking) — ⚠ Pending Confirmation.** Not currently in the stack; relevant if course video piracy is a business concern (flagged in understanding report §6.3).
- **Student profile photo upload — Implemented (Phase 6), the first real instance of the signed-upload pattern above:** `cloudinary-upload.service.ts` generates the signature scoped to a server-chosen `folder`/`publicId`/format-allowlist/size-cap; critically, the backend **never trusts the client's claim that an upload succeeded** — `PATCH /students/{id}/photo` independently re-verifies the asset via the Cloudinary Admin API (`cloudinary.api.resource`) before persisting anything, rejecting a `publicId` outside the expected folder or one Cloudinary can't resolve. Allowed formats: `jpg`/`jpeg`/`png`/`webp`; max 5MB, enforced both in the signature and client-side. A replaced photo's previous asset is deleted server-side (`cloudinary.uploader.destroy`) only after the new one is confirmed. See ARCHITECTURE.md §15 for the full request flow.
- **Trainer profile photo upload — Implemented (Phase 7):** reuses `cloudinary-upload.service.ts` and the identical signed-upload/re-verify/safe-replace flow as the student photo above, scoped to `daisy-minds/trainers/{id}`. Professional-document upload (qualification/certification attachments) was deliberately deferred to metadata-only — `documentUrl`/`documentPublicId` fields exist and are always `null`, no upload endpoint was built this phase, matching the students module's academic-document precedent.
- **Course thumbnail/banner upload — Implemented (Phase 9A):** reuses `cloudinary-upload.service.ts` and the identical signed-upload/Admin-API-reverify/safe-replace/delete flow, scoped to `daisy-minds/courses/{id}/thumbnail` and `daisy-minds/courses/{id}/banner`. No course-video upload exists — `promoVideoUrl` is a dormant schema field, unwritten by any endpoint this phase (ARCHITECTURE.md §19); building it is explicitly deferred to a future Learning Content module.
- **Lesson video/document upload and downloadable resources — Implemented (Phase 9C).** `cloudinary-upload.service.ts` is generalized (never duplicated) to accept `resourceType`/`type`/`allowedFormats`/`maxFileSize`, defaulting to the exact Phase 9A image behavior for every existing caller. New callers scope uploads to `daisy-minds/courses/{courseId}/lessons/{lessonId}/{video|document|resources}` and use `type: 'authenticated'` — never `type: 'upload'` (public) like thumbnails/banners/photos — so no lesson video/document/resource asset is ever reachable at a permanent public URL. Allowed formats: video `mp4`/`webm`/`mov`; document `pdf` only; resource `pdf`/`doc(x)`/`ppt(x)`/`xls(x)`/`zip`/`jpg`/`jpeg`/`png`/`webp` — never an executable/installer format in any allowlist. Every upload is independently re-verified against Cloudinary's Admin API (existence, exact `resource_type`, exact expected folder, size/duration limits) before any lesson/resource record is written — matching the Phase 9A/6/7 "never trust a client-reported upload" pattern exactly. Replacing an existing video/document deletes the previous Cloudinary asset only after the new one is confirmed (same ordering as the student-photo flow); deletion always resolves the asset from the server's own stored record, never a client-supplied `publicId`.
- **Signed delivery URLs — Implemented (Phase 9C), reusable service.** `media-delivery.service.ts#generateSignedDeliveryUrl` mints a short-lived (5-minute default), HMAC-signed Cloudinary URL entirely locally (no network call) for a `type: 'authenticated'` asset. Every DTO returned to the frontend (video/document/resource) omits `publicId`/`assetId`/`version`/`provider` — preview/delete/replace are always lesson- or resource-ID-scoped server-side, so the client is never given a raw Cloudinary identifier to misuse. No signed delivery URL is ever cached, persisted, or embedded in another response — each caller requests a fresh one at render time.
- **TEXT lesson content — sanitized server-side on every write, frontend sanitization never trusted.** `utils/html-sanitize.ts#sanitizeLessonHtml` (the `sanitize-html` package, actively maintained) enforces an explicit allowlist — headings/paragraphs/bold/italic/strike/lists/links (forced `rel="noopener noreferrer nofollow"`)/code-blocks/blockquotes/tables — and always strips `script`/`style`/`iframe`/`object`/`embed`/`form`, every event-handler attribute (`onclick` etc.), and `javascript:`/`data:` URLs, regardless of what the client submits. The stored value is always the sanitized output; the pre-sanitization input is capped at 200,000 characters server-side to keep a lesson document nowhere near MongoDB's 16MB limit.
- **EXTERNAL_LINK lesson content — server-validated, never fetched (no SSRF surface).** Only `http`/`https` schemes are accepted; `javascript:`/`data:`/`file:`/`ftp:` are explicitly rejected server-side regardless of what URL-parsing would otherwise accept. The backend never makes an outbound request to the submitted URL — validation is shape-only. The frontend performs the identical scheme check for immediate UX feedback, but the backend re-validates independently and is the actual security boundary.
- **Lesson-type-change content-reset guard (Phase 9C):** changing a lesson's `lessonType` away from one that already has content is rejected (`409`) unless the request explicitly sets `confirmContentReset: true` — prevents an admin from silently discarding an authored video/text/document/link by relabeling the lesson's type.

## 7. Data Privacy & Compliance

- **⚠ Pending Confirmation — India DPDP Act 2023 applicability**, especially given a likely-minor student population (coaching-center/college audience). Until confirmed, the system defaults to privacy-conservative behavior: minimal PII collection, explicit consent capture for the `placements.consentGiven` field (DATABASE.md §2.7) before sharing student data with employers, and no third-party data sharing beyond what's operationally required (payment gateway, SMS/email provider).
- Personal data is never logged in application/audit logs beyond what's needed for the audit trail (e.g., log a user ID, not a full profile dump).
- A data-retention and deletion policy is **not yet defined** and is required before production launch if DPDP applies — this is a legal/compliance decision, not purely an engineering one.
- **Government ID (Aadhaar) storage — deliberately not implemented (Phase 6).** The Admin Student Management module (ARCHITECTURE.md §15) was built without any Aadhaar/government-ID field, and the pre-existing `students.kycDocuments` array (generic `{type, url, verifiedAt}`, Phase 1 scaffold) is left unpopulated by its create/update paths. This was flagged as a high-risk business decision needing explicit sign-off — encryption-at-rest, field-level masking in list/export/log output, restricted read access, and a retention/consent policy would all need to be designed *before* any government-ID field is added, not retrofitted after. Do not populate `kycDocuments` with government-ID data until the DPDP question above is resolved and this design is done. The same applies to `trainers` (Phase 7) — no government-ID field was added there either, for the identical reason.
- **Trainer salary/compensation — deliberately not implemented (Phase 7).** No salary, compensation, or payroll-related field exists anywhere in the `trainers` schema — this was an explicit scope exclusion in the Phase 7 task, not an oversight or an "exists but unexposed" case. Trainer payroll is a distinct future module and should be designed with its own access controls (narrower than general `trainers:manage`) when built.

## 8. Audit Logging

- Every state-changing action on: user accounts, role/permission changes, payments/refunds, certificate issuance/revocation, and settings changes is written to `auditLogs` (DATABASE.md §2.1) — actor, action, entity, before/after where practical, IP address, timestamp.
- Audit logs are **append-only** (no update/delete API exists for them, even for `SUPER_ADMIN`) — an audit trail that can be edited is not an audit trail.
- **Phase 5** is the first module to expose a *read* path for this data to an admin UI: `GET /users/:id/audit` (SUPER_ADMIN-only, §3) powers the user-detail "Audit Timeline," backed by `audit-log.repository.ts`'s `findByEntity('user', userId, ...)` and mapped to an explicit `AuditLogEntryDto` before leaving the service — raw Mongoose documents are never returned to a client. `GET /students/:id/audit-log` (Phase 6) is the same pattern against `entityType: 'student'`. Every state-changing student action writes an entry (`student.created`/`updated`/`activated`/`deactivated`/`soft_deleted`/`restored`/`invitation_resent`/`session.force_revoked`/`logout_all_forced`/`bulk_action`/`exported`/`photo_changed`/`photo_removed`) — verified by an integration test asserting the created-entry's metadata never contains a password or token. `GET /trainers/:id/audit-log` (Phase 7) is the same pattern again against `entityType: 'trainer'`, including the same event set plus `trainer.availability_changed` (written whenever an update includes an `availability` change) and `trainer.employment_status_changed` (written whenever an update actually changes `employmentStatus`) — a single `updateTrainer` call can write up to 3 audit entries in one request when multiple things change at once.
- Retention period for audit logs: ⚠ pending, but no shorter than the retention period ultimately set for `payments` records (§ DATABASE.md §6), since payment-related audit entries must outlive the transactional record's own retention floor.
- **Admin Dashboard "recent activity" feed (Phase 8)** is a second, cross-entity read path over the same `audit_logs` collection, distinct from the per-entity `GET /:id/audit-log` pattern above — `dashboard.repository.ts#getRecentActivity` queries the most recent entries across *all* entities (allowlisted to a fixed operational-action set, ARCHITECTURE.md §18), not one entity's history. Every row leaving `dashboard.service.ts` is `{id, action, entityType, entityLabel, actorLabel, createdAt}` only — `metadata`, `ipAddress`, and `userAgent` never leave the repository layer, verified by an integration test asserting those keys are absent from the response. `entityLabel`/`actorLabel` are resolved via a small batched lookup (`resolveDisplayNames`), not a lookup per row, so the feed can't become an N+1 query.
- **`GET /courses/:id/audit` (Phase 9A)** is the same per-entity pattern as `/users`/`/students`/`/trainers`, against `entityType: 'course'`. Course events: `course.created`/`updated`/`pricing_changed`/`visibility_changed`/`eligible_trainers_changed`/`published`/`unpublished`/`archived`/`restored`/`soft_deleted`/`bulk_action`/`exported`/`media_changed` (thumbnail/banner attach, remove, and replace all write `media_changed` with a `metadata: {field: 'thumbnail' | 'banner'}` discriminator, rather than four separate action strings). Unlike the `users`/`students`/`trainers` carve-out, course audit access is gated by `courses:manage` (not `requireRole('SUPER_ADMIN')`) — a course has no personal/sensitive data comparable to a user's session history, so the stricter role gate wasn't warranted here.
- **Curriculum mutations (Phase 9B) deliberately reuse `GET /courses/:id/audit` rather than a new endpoint** — every curriculum event is recorded with `entityType: 'course'`, `entityId: courseId` (the specific module/lesson affected travels in `metadata`), so it shows up in the exact same course audit timeline as Phase 9A's own events, with no second audit-read surface to build or secure. Events: `curriculum.module.created`/`updated`/`reordered`/`duplicated`/`archived`/`restored`/`deleted`, `curriculum.lesson.created`/`updated`/`reordered`/`moved`/`duplicated`/`archived`/`restored`/`deleted`, `curriculum.prerequisites.changed`, and `curriculum.item.published`/`unpublished` (shared by both modules and lessons, discriminated by `metadata.itemType`).
- **Learning content mutations (Phase 9C) reuse the identical `entityType: 'course'` pattern** — no third audit-read surface. Events: `lesson.content.text_updated`, `lesson.content.external_link_updated`, `lesson.video.verified`/`replaced`/`removed`, `lesson.document.verified`/`replaced`/`removed`, `lesson.resource.added`/`updated`/`reordered`/`removed`, `lesson.content.readiness_changed` (fired whenever a write actually changes the computed `contentStatus`), `lesson.content.reset_on_type_change` (fired only when a `lessonType` change actually discards existing content). Metadata is always structural (byte counts, format, ids, before/after status) — full lesson-body HTML is never written to an audit record, verified by an integration test.
- **`GET /batches/:id/audit` (Phase 10A)** is a new per-entity audit surface, `entityType: 'batch'`, gated by `batches:manage` (not `requireRole('SUPER_ADMIN')`) — the same reasoning §8's course-audit note gives: a batch has no personal/sensitive data comparable to a user's session history. Events: `batch.created`/`updated`/`scheduled`/`unscheduled`/`activated`/`completed`/`cancelled`/`archived`/`restored`/`soft_deleted`/`duplicated`/`trainers_changed`/`timetable_changed`/`calendar_exceptions_changed`/`capacity_changed`/`location_changed`/`bulk_action`/`exported`. Field-specific events (`capacity_changed`/`timetable_changed`/`calendar_exceptions_changed`/`location_changed`) are only fired when that field's value actually differs from its current one (the exact behavior verified by the §4 regression test above, after the `.default()`/`.partial()` fix) — never on every `PATCH` regardless of what changed. A deliberate `batch.readiness_checked` event was **not** added, matching §8's restraint around read-only checks elsewhere in this app; metadata never contains `internalNotes` or the full venue address.

## 9. Infrastructure & Transport Security

- HTTPS enforced everywhere via Let's Encrypt (Nginx-terminated) + Cloudflare proxy (also providing basic DDoS/WAF protection at the edge).
- Helmet applied globally (HSTS, X-Content-Type-Options, X-Frame-Options, CSP as noted in §4).
- Secrets (JWT signing keys, DB connection strings, Cloudinary/gateway API keys) live in environment variables, never committed — `.env` is gitignored, `.env.example` documents required keys with placeholder values only. A managed secrets store (beyond plain VPS env vars) is a future hardening step once infra grows beyond a single VPS.
- Dependency vulnerability scanning (`npm audit` / GitHub Dependabot) runs in CI (see DEPLOYMENT.md) — no dependency with a known critical CVE is merged without an explicit, documented exception.

## 10. Incident Response (Baseline)

At minimum before production launch: a documented process for (1) revoking a compromised user's sessions immediately — **implemented**: `authService.logoutAll()` revokes every `user_sessions` row for a user, and is what such a response should call, (2) rotating `JWT_ACCESS_SECRET` without a full outage — not yet designed (a single-secret rotation today invalidates every outstanding access token at once; a future key-ID-aware rotation is a pre-launch improvement), (3) an escalation contact for a suspected data breach. A full incident-response plan is a pre-launch deliverable, not yet written — tracked in ROADMAP.md Phase 19.
